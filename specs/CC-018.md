# CC-018 · Close the scorer's output-path and duplicate-key gaps

## Goal

The scorer can't be steered into writing `evals/baseline.json` or anything under `evals/scenarios/`, `evals/golden/` or `gates/`, and a JSON file with a repeated key in one object (a baseline above all) is refused.

## Context

- Ticket: `tasks/hardening.md`, section `CC-018` (not in `docs/implementation-tickets.md`). Findings are from the G5 review of CC-016 (2026-10-12), both confirmed by a probe test; neither was introduced by CC-016.
- **Finding 1, symlink then `..`.** `outputCandidates` (`baseline.go`) runs `filepath.Abs`, which cleans `..` as text, and only then `EvalSymlinks`. `writeFileAtomic` (`result.go`) hands the raw path to `os.CreateTemp` and `os.Rename`, and the OS resolves `l/..` through the real directories. With `out/l -> repo/evals/scenarios/sub`, `WriteBaseline("out/l/../x.json")` passed the check and wrote `repo/evals/scenarios/x.json`; with `out/l2 -> repo/evals/sub2`, `out/l2/../baseline.json` created `repo/evals/baseline.json`. `eval noise --out` is affected the same way, and `os.MkdirAll(f.Out)` (`cmd/eval/score.go`) can create an empty directory under a protected folder. Exploiting it needs control of a CLI flag and a planted symlink.
- **Finding 2, duplicate keys.** `readStrict` (`score.go`), used by `LoadBaseline`, `LoadScore` and `LoadNoise`, rejects unknown fields and trailing data but the last copy of a repeated key wins, so a hand-edited baseline could show a reviewer one section while the gate compares against another.
- **Chosen design (owner-delegated approval covers it; the ticket allows either):** refuse any output path that has a `..` component in the path as given. This is simpler and safer than resolving the path "as the OS would walk it", and one check covers every caller (`--out`, `--baseline-out`, `noise --out`, `--fixtures-dir`, `WriteScore`, `WriteSummary`, `WriteBaseline`, `WriteNoise`), including the `MkdirAll` that runs after the CLI check. Nothing in the repo or in `.github/workflows/eval.yml` passes `..` in an output path (they use `$RUNNER_TEMP/...`).
- Invariants to keep: the scorer never writes `evals/baseline.json` or anything under `evals/scenarios/`, `evals/golden/`, `gates/`; `ErrProtectedBaseline` and `ErrProtectedOutput` keep their meaning and `errors.Is` still matches them. A path that today is refused for another reason is still refused. Do not touch `.github/**`, `evals/baseline.json`, `evals/scenarios/**`, `gates/**`, `docs/**` or `CLAUDE.md`.
- Existing tests `TestBaselineOutputGuard` (`baseline_test.go`) and `TestScoreCLIProtectedOutputs` (`cmd/eval/score_test.go`) use paths such as `tmp/../evals/scenarios/suite-test/ground_truth` and expect a refusal. They must keep passing (the refusal now comes from the `..` rule); keep their error assertions satisfied by wrapping `ErrProtectedOutput`.

## Notes

- No new dependencies.
- Residual risk, to record in the PR summary: a symlink with no `..` pointing straight into a protected folder was already caught by `EvalSymlinks` and still is. A symlink planted between the check and the write (TOCTOU) is not addressed; the output folders are the operator's own, and `os.Root` is a later hardening.
- `encoding/json` matches struct field names case-insensitively, so `{"Items":..., "items":...}` is two keys to the walk but one field to the decoder. Not in scope; mention it in the PR summary.
- Also record in the PR summary: manifest and result files are still read leniently (`readJSONFile`, `score.go`), and `internal/evals/runner.go` writes results and the manifest with no `CheckOutputPath` (pre-existing). Owner follow-up: decide whether the runner's output folder gets the same guard.
- `writeFileAtomic` is shared with the runner (`runner.go`) and the fixture recorder (`fixtures.go`), whose paths are built with `filepath.Join`, which keeps a *leading* `..`. After this change `eval run --out ../runs` and a fixture stage under `../` are refused (intended; nothing in the Makefile or `eval.yml` does it). Record it in the PR summary. The `writeFileAtomic` check is a backstop for future callers, not a second line against the probe, since in-tree callers pass already-cleaned paths.
- Owner follow-up, outside this ticket: a dangling symlink as the last component is allowed by `CheckOutputPath` (`EvalSymlinks` fails) but the write then fails; a `Readlink` in `outputCandidates` would make the guard itself refuse it.
- Regulated: the output guard is a protected invariant. G5 and the Opus diff review run before merge.
