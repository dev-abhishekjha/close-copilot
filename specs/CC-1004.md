# CC-1004 · Maker-checker approvals

## Goal

A maker turns a finding's proposal into a pending journal proposal; a different user with the checker role approves it, which posts it to ERPNext once, or rejects it with a reason.

## Context

Plan row: Phase 4, IMP (owner reviews), regulated, ERPNext lock; check "Asha proposes, Ravi approves, entry posted; self-approval refused". Guardrail row "Write-capable MCP tools stay out of the answer path": the admin token is held only by the approvals service; checker != maker; G5 "agent token gets 401"; G6 for every change under `internal/approvals`.
- Quoted from the ticket: "the server enforces separation of duties (checker != maker), not the UI. Approval calls the admin MCP tool `post_approved_journal_entry` with the admin token held only by the agent service. Posting is idempotent, so a double click or a retry can't create two entries." Roles are explicit sets, not a ladder: maker routes allow only makers, checker routes only checkers. ## Notes

- Regulated: `approved_by` stays empty here; `/build` records the owner's delegated approval after `ticket-reviewer` passes the spec.
- Design choice: approve is two steps on purpose. Step 1 commits `approved` + `checker` under the row lock. Step 2 calls the tool, which takes its own lock and does the ERPNext work. If step 2 fails or the process dies, the row stays `approved` and the same checker can retry; the tool's `copilot_ext_id` lookup prevents a double post. The tool re-checks checker != maker, so the separation of duties is enforced twice (service and tool).
- Migration `0006` is the only schema change. If the unique index conflicts with data already in a dev database, the migration may not simply drop rows; report it instead.
- The payload comes from model output and is copied to ERPNext. Check where the explainer stores it relative to CC-710 pseudonymisation; if tokens could reach `remark` or account names, refuse them in `ValidatePayload`, otherwise state in the PR summary that stored payloads are de-pseudonymised.
- `internal/approvals/**` is protected: G1's protected check needs the owner approval recorded in `approved_by`.
- No new dependencies (the MCP SDK and `uuid` are already in `go.mod`). Report any in the PR summary.
- Risks to raise in the PR summary: the approvals service holds both a Postgres connection and an MCP session during approve (bounded by the 100 s deadline); the posting key comes from CC-1007; `proposal_id`s travel only server to server.
