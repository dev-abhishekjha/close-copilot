# CC-607 · Variance calculator

## Goal

Flag income and expense accounts whose month moved sharply against the average of the previous three months, as informational `variance` findings with the five largest GL entries of the month as evidence, linkable to another finding on the same account and month.

- **Integer arithmetic (no floats anywhere; `internal/money` is the only place that converts):**
  - Orient the sign so a normal balance is positive: Expense `cur = Net`, Income `cur = -Net` (that is credit minus debit). Do this for the month and for the three prior months.
  - Let `sum3` = the three prior oriented nets added, `cur` = this month's oriented net, all `int64` paise (`money.Paise`). The average is `sum3/3`; do **not** divide. Let `d3 = 3*cur - sum3` (three times the change) and `|x|` its absolute value.
  - Absolute test: `|d3| > 3 * AbsThresholdINR * 100` (rupees to paise by integer multiply). Percentage test: `|d3| * 100 > PctThreshold * |sum3|`. When `sum3 == 0` the percentage is unbounded, so the percentage test passes and the absolute test decides. Flag only when both pass (strictly greater, per "exceeded").
  - Finding amount = `|d3| / 3` (integer division, truncating) as a positive `money.Paise`; the sign and direction go in the title ("up" when `d3 > 0`, "down" otherwise). Show money with `Paise.Format()` (`internal/money/money.go:289`). Add a short comment on the overflow bound: `|d3|*100` stays inside int64 while a net is below about 3e16 paise; guard by returning an error rather than wrapping if `|d3| > math.MaxInt64/100`.

## Design: how `keys.related` gets filled

A `Check` sees only `Inputs`; it cannot see another check's findings, and finding IDs are assigned by the runner after `Run` (`internal/checks/runner.go:100-110`). So the link cannot be set inside `Run`. Implement it as two pieces in `variance.go`:

1. `VarianceCheck.Run` emits variance findings with `Keys{account, month}` and no `related`. Its evidence includes (a) `get_account_history` (args `{company, account, through_month, months: 4}`, no IDs), (b) `list_gl_entries` (args `{company, from_date, to_date, account}`) with the IDs of the five largest GL entries of the month on that account (largest by `|Debit-Credit|`, ties broken by `Name`; cancelled entries ignored), and (c) when some of the account's month GL entries have `VoucherType == "Purchase Invoice"`, a `list_purchase_invoices` ref (args `{company, month}`) whose IDs are those `VoucherNo` values (sorted, deduped, at most 20, largest entries first). (c) is what lets a prepaid finding, which has only an `invoice` key, be matched to the account.
2. `func LinkVariances(findings []Finding) []Finding`: a pure function over the runner's output (IDs already set). For each `variance` finding, find the first (in input order) non-variance finding that matches either (i) `Keys["account"] == v.Keys["account"]` and `Keys["month"] == v.Keys["month"]`, or (ii) `Keys["invoice"]` is in the IDs of the variance's `list_purchase_invoices` evidence ref. Set `v.Keys["related"]` to that finding's `ID.String()`. If none, leave `related` unset. It returns a new slice and does not mutate its input's maps in place; a variance finding already carrying `related` is left alone; deterministic. `related` is not part of the matching keys (CC-607's matching keys are `account` + `month`); note `DedupeKey` includes all keys, so call `LinkVariances` **after** `DedupeFindings`.
   Wiring it into the runner or the workflow is out of scope (see Out of scope); this ticket proves the link in unit tests by calling `Run` then `LinkVariances` the way the runner will.

## Subtasks

- [ ] `type VarianceCheck struct{}`; `Name()` returns `"variance"`; `var _ Check = (*VarianceCheck)(nil)`. Parse `in.Month` (error wrapping `%w` on a bad month).
- [ ] Enumerate accounts: one `TrialBalance` call from the first day of the month three months earlier to the last day of `in.Month`; keep rows with `RootType` Income or Expense and any activity (`Debit+Credit != 0`), sorted by `Account`.
