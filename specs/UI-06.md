# UI-06 · Findings list, filters and bulk accept

## Goal

A page that lists the findings of the company and month selected in the top bar, with filters, sorting and paging, and lets a maker accept several findings at once, using exactly the rules, checks and audit trail that accepting one finding uses today.

## Context

- Ticket: `tasks/frontend-plan.md` sections 4 and 10 (`UI-06`). **Scope change from the plan table**, for the reasons below: "cross-run list" becomes "the run for the selected company and month" (there is no cross-run store query and none is added), and bulk **dismiss** is dropped (a dismissal needs its own reason, so it stays a per-finding action on the finding page). Bulk **accept** stays.
- Data-sensitive: it adds a state-changing path (finding status) with an audit entry, so G5 runs. **A bulk accept is N single accepts, never a new write path.** Extract the body of `decideFinding` (`finding.go:333`) into a function usable per finding (for example `s.decideOne(ctx, p, findingID, to, tool, reason) (decision, error)` returning the new status or a typed refusal reason such as already decided, live proposal, not found, store error); `decideFinding` becomes a thin wrapper that keeps its exact responses, status codes, audit calls (`finding.accept`, `finding.dismiss`) and messages, and `finding_test.go` passes unchanged. The bulk handler calls the same function per id. The live-proposal rule, the open or needs-review rule, the audit entry per finding and the maker-only role all apply per id.
- **Existing tests that must change because the route now exists:** `routes_hooks_test.go` `TestRouteHooksEmpty` must no longer expect `findingsListRoutes` to be empty (remove that entry; leave the other hooks), and `shell_test.go` `TestShellNavByRole` and `TestShellNavOmitsUnroutedPages` must expect `/findings` as routed and visible for every role. These are the only allowed edits in those two files; list them in the PR summary.
- Routes: add in `routes_findings.go` via `findingsListRoutes()` (do not edit `routes.go`): `GET /findings` (`anyRole`) and `POST /findings/accept-selected` (`makerOnly`). Both are wrapped like the other findings routes (501 page or JSON as the existing wrappers do when the backend is not configured, after the role check). `/findings/{id}` and the other `/findings/...` rows are untouched; confirm Go's mux resolves `/findings/accept-selected` (a literal segment) ahead of `/findings/{id}/accept`. The nav item "Findings" appears automatically.
- CSRF and same-site checks come from the existing wrapper for the POST. Body capped at 16 KiB through `routeBodyLimits`-style handling is not possible here without editing `routes.go`, so the handler itself bounds the number of ids (below) and relies on the server-wide 1 MiB cap.
- Hooks: reuse the findings table hooks UI-05 established (`table.findings` wrapper, `tr[data-finding]` with `data-severity`, cells `severity type title amount status verified detail`) so existing styles and tests carry over.
- CSP, escaping and no-inline rules from UI-01/02. Finding titles, types and company names are data: escaped.
- Shared files are owned by earlier tickets: do not edit `ui*.templ`, `ui.go`, `components.css`, `app.css`, `routes.go` or `design_test.go`.

## Behaviour

- **Which run:** the context company and month (`contextFor`, overridable by `?company=&month=` which are validated like elsewhere: month by `monthRE`, company must be in the company list, else ignored). The newest run for that pair from `ListCloseRuns(ctx, 200)` (no extra store method); then one `ListFindingsByRun`. No run: `EmptyState` "No close run for COMPANY MONTH yet" with a link to `/runs` for makers.
- **Filters** (GET query, all optional, validated against the values present or the known sets, unknown values ignored): `severity` (`high|medium|low`), `type`, `status`, `verified` (`yes|no`), `q` (case-insensitive substring of the title, max 100 bytes). **Sort**: `sort` in `severity` (default: high first), `amount`, `type`, `status`, `title`, with `dir` `asc|desc`; table headers are links that set it (`aria-sort`). **Paging**: 25 per page, `page` (1-based, clamped); a "Showing x-y of N" line and previous/next links that keep the other parameters (query-escaped). Variance children stay nested under their parent as on the run findings page and count with it.
- **Summary tabs** above the table: `Tabs` for All, Open, Needs review, Accepted, Dismissed with counts, driven by `status`.
- **Bulk accept (maker only):** rows have a checkbox (`name=ids`, value the finding id) only for makers and only for findings that are `open` or `needs_review`; a "Mark selected accepted" button posts the form to `POST /findings/accept-selected` with the CSRF token and the current filter query as a hidden `return` value (validated through `safeNext` and restricted to `/findings?...`). The handler: requires 1 to 50 ids (more: 400 with a message), each a valid UUID (any invalid id: 400, nothing done), **each id must belong to the run being listed for the posted company and month** (re-derived server side, never trusted from the form; an id from another run is skipped as "not in this view"), then accepts them one by one with `decideOne`, never in a transaction across items, continuing after a refusal. It redirects (303) back to the list with a result summary carried in a short-lived flash value that cannot be forged into other content: simplest is to render the result page directly (200) with the list below and an alert card listing "N accepted" and each refusal as "TITLE: reason" (escaped); do not use a query parameter or cookie to carry text.
- A selection that includes a finding with a live proposal is refused for that finding with the existing message, and the others proceed.
- Viewers and checkers see the list without checkboxes or the bulk button, and the POST is refused 403 by the route table as for other maker routes.
