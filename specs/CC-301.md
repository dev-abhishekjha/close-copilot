# CC-301 · Company profiles, rules config and GSTIN generator

## Goal

Two company profiles and `config/rules.yaml`, loaded and validated in Go, plus a generator of synthetic GSTINs that ERPNext with India Compliance will accept.

## Context

- Ticket: `docs/implementation-tickets.md`, section `CC-301`. Formats: the shared specs "Company profile: `config/companies/<id>.yaml`" and "Rules: `config/rules.yaml`" in the same doc. Read all three; they are the contract.
- This is the second **Gate A pilot** ticket. It must merge through G0–G3 with no hand edits.
- **Synthetic data only.** No real company, person, PAN or GSTIN. Use invented names, and PANs from the generator.
- **No floats in `internal/seed`.** The CC-002 `nofloat` analyzer covers this package, and `go run ./gates/cmd/lint ./...` fails on any `float32`/`float64`, including a decoded YAML float.
  - Parse the decimal fields `gateway_share` (e.g. `0.4`) and `gateway_fee_pct` (e.g. `2.0`) as **strings** into an integer fixed-point type, e.g. `BasisPoints int64` (0.4 → 4000, 2.0% → 200). Use a custom `UnmarshalYAML` that reads the scalar's text and parses digits by hand or with `strconv.ParseInt`. Reject more than 4 decimal places.
  - Amounts in `_inr` fields are whole rupees as `int64`. Conversion to paise happens later (`internal/money`, CC-203); don't create `internal/money`.
- **YAML library:** `go.yaml.in/yaml/v3`, already in `go.mod` and pinned in `internal/deps/deps.go` with a `// CC-301` comment. Once `profile.go` imports it, delete that one line from `deps.go`. **No new dependencies.**
- The company "Sharma Traders Pvt Ltd" (abbr `STPL`) already exists in ERPNext (CC-102). Mehta is created later by CC-303. This ticket doesn't touch ERPNext.

## Subtasks

- [ ] **`config/companies/sharma.yaml`**:
  - `id: sharma`, `erp_company: Sharma Traders Pvt Ltd`, `abbr: STPL`, `state_code: "29"` (Karnataka), trading business.
  - 15–20 suppliers.
- [ ] **`config/companies/mehta.yaml`**:
  - `id: mehta`, `erp_company: Mehta Tech Services Pvt Ltd`, `abbr: MTSPL`, `state_code: "27"` (Maharashtra), IT services.
  - 15–20 suppliers.
- [ ] **Each profile follows the shared-spec shape**:
  - id, erp_company, abbr, state_code, pan, opening_bank_balance_inr, seed, customers, sales{…}, suppliers[…], payroll{…}, bank{…}.
  - At least one supplier of every kind: `rent`, `utility`, `subscription` (at least one `billing: annual`), `goods`, `services`.
  - At least one `registered: false` supplier.
  - Registered suppliers both in the company's own state (CGST + SGST) and in other states (IGST).
  - Different seeds for the two companies.
  - Each profile's `pan` is a synthetic company PAN: 4th letter `C`, 5th letter the first letter of the company name.
- [ ] **`config/rules.yaml`**: exactly the shared-spec keys and values.
- [ ] **`internal/seed/profile.go`**:
  - Types `Profile`, `Supplier`, `Sales`, `Payroll`, `Bank`, `Rules`. A `Range` type accepts a scalar (`150000`) or a two-element list (`[18000, 26000]`). `Day` accepts 1–28 or `last`.
  - Loaders: `LoadProfile(path)`, `LoadProfiles(dir)` (sorted by id), `LoadRules(path)`.
  - Unknown YAML keys are an error (`KnownFields(true)`).
  - **Validation reports every problem at once** (`errors.Join`), each naming the file and field:
    - `id` matches the file name;
    - supplier ids are unique within a profile;
    - `state_code`, for the company and for registered suppliers, is a valid two-digit GST state code (01–38, or 97);
    - PAN format (5 letters, 4 digits, 1 letter);
    - `kind` and `billing` are known values;
    - `gst_rate` is one of 0, 5, 12, 18, 28; `sales.gst_rates` uses the same set;
    - every range has min ≤ max and positive amounts;
    - `renew_month` is 1–12; `day` is 1–28 or `last`;
    - any month field written as `YYYY-MM` is a valid month;
    - `registered: false` suppliers carry no `state_code` or `gst_rate` (unless 0);
    - the counts and mixes required above.
  - Rules validation:
    - thresholds are positive;
    - the keyword lists are non-empty;
    - `bank_match.date_window_days` is 0–15;
    - `gstr2b.amount_tolerance_paise` is ≥ 0;
    - `accruals.min_occurrences` ≤ `lookback_months`.
- [ ] **`internal/seed/gstin.go`**:
  - `CheckDigit(prefix14 string) (byte, error)`: Luhn mod 36, with the ticket's algorithm and alphabet `0-9A-Z`.
  - `PAN(seed int64, key string, entity byte) string`: deterministic for `(seed, key)`, with `entity` as the 4th letter (`C` for companies).
  - `GSTIN(stateCode, pan string) (string, error)`: state code + PAN + `1` + `Z` + check digit.
  - `ValidGSTIN(s string) error`: length, character classes, state code and check digit.
  - Use `math/rand/v2` with a seeded source. No global rand, no time.
  - Supplier PANs and GSTINs derive from the company seed plus the supplier id, so they are stable across runs and different between companies.
- [ ] **Tests** (`profile_test.go`, `gstin_test.go`; build broken YAML inline in the tests, not as new testdata files):
  - `TestLoadShippedProfiles`: both shipped profiles load cleanly. Every registered supplier's derived GSTIN passes `ValidGSTIN`, and its state code matches the supplier's.
  - `TestLoadRules`: the shipped `rules.yaml` loads and equals the shared-spec values.
  - `TestBrokenProfileReportsAll`: one profile with at least five different problems returns an error naming each one.
  - `TestCheckDigit`: table cases, including a prefix whose check digit is `0` and one whose digit is a letter. Also a round trip: for 1,000 generated GSTINs, `ValidGSTIN` passes and changing any single character fails it.
  - `TestGSTINStable`: same seed and key give the same PAN and GSTIN; a different key gives a different PAN; every result is 15 characters, with characters 13 and 14 being `1Z`.
  - `TestValidGSTIN`: rejects wrong length, a lowercase letter, a bad state code and a bad check digit.

## Acceptance (human-readable)

- Both profiles load without errors. A broken profile reports every problem at once.
- Generated GSTINs are 15 characters, carry a correct check digit and are stable for a seed.
- CC-303 provides the final proof: India Compliance accepts a Supplier created with a generated GSTIN. The worker may also check a few generated GSTINs against India Compliance's own validator in the running backend container (read-only `bench execute`) and report the result. That isn't required, and it must not create anything.

- `internal/money` (CC-203).
