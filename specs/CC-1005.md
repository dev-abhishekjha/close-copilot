# CC-1005 · Audit log and run metrics pages

## Goal

Reviewers can see who did what, and what each run cost.

## Context

- Ticket: docs/implementation-tickets.md, section `CC-1005` (do not open it; quoted below).
- Plan row: Phase 4, implementer, standard, depends on CC-1004; gate-run check "Every demo action shown with its actor".
- Ticket subtasks, verbatim:
  - Audit page: filters by actor, server, tool and date; columns time, actor, tool, arguments (truncated), rows returned, latency, error; paginated.
  - Run metrics: tokens by step (explain, investigate), cost, duration, verified rate, trace link.
  - A summary on the runs page: the last run's verified rate and open high-severity findings.
- Ticket acceptance: every approval and tool call from the demo flow appears on the audit page with the right actor.
- `audit_log` table (migrations/0002_runs.sql, append-only for `copilot_app` since 0005; this ticket only reads it): `id bigserial, at timestamptz, actor text NOT NULL, server text, tool text, args jsonb, result_count int, latency_ms int, error text`.
- Who writes audit rows today (all already merged; do not change them):
  - MCP tool calls: `mcpkit.AddTool` with `EnableAudit`, server `"evidence"`, `"books"` or `"books-admin"`, actor `agent:run/<run id>` (or the admin/checker name), tool = MCP tool name, `args` capped at 8 KiB.
  - Finding accept/dismiss (`internal/web/finding.go:380`): actor = web user, `server` NULL, tool `finding.accept` or `finding.dismiss`, args include `reason` on dismiss.
  - Approvals (`internal/approvals/approvals.go:485`): actor = maker or checker username, server `approvals`, tool `proposal.create`, `proposal.approve` or `proposal.reject`, args carry the proposal id and a result (`ok`, `refused:<code>`, `error`).
- Run metrics sources: `close_runs` (`input_tokens, output_tokens, cache_read_tokens, cost_usd, trace_id, started_at, finished_at`), `run_steps.kind` (`explain`, `investigate`, `verify`, `check.<name>`, ...; `explain` and `investigate` subjects are finding ids), `llm_calls` (`step_id, input_tokens, output_tokens, cache_read_tokens, cost_usd, latency_ms`), `findings.verified` and `findings.severity` (`high|medium|low`) and `findings.status` (`open|needs_review|accepted|dismissed`).
- Verified rate = findings with `verified = true` divided by all findings of the run; a run with no findings shows "n/a", never 0% or a divide error.
- Roles: pages are HTML only (no new JSON API rows in the shared HTTP API spec). Audit rows hold de-pseudonymised proposal data and tool arguments, so `/audit` is `checkerOnly` (a reviewer role). `/runs/{id}/metrics` is `anyRole` like the run page. Both answer 501 after the role check while their backend is nil (copy `runsHTML` / `approvalsRoute`).
- Conventions: templ components are generated with `make generate` and the `*_templ.go` files are committed; all output is HTML-escaped by templ (arguments are untrusted JSON, render as text in a `<code>`); money is `int64` paise, but `cost_usd` here is a USD decimal already formatted by `formatCost` (`internal/web/runs.go`); `context.Context` first; errors wrapped with `%w`.

## Subtasks

- [ ] Store: `AuditFilter{Actor, Server, Tool string; From, To *time.Time; Limit int; Before int64}` and `ListAuditPage(ctx, f) (rows []AuditLogEntry, next int64, err error)`. Exact match on actor, server, tool; `at >= From` and `at < To`; newest first (`at DESC, id DESC`); keyset pagination on `id` (`Before` = last id of the previous page, `next` is 0 when no more); `Limit` clamped to 1..200, default 50. All filters are SQL parameters, never concatenated.
- [ ] Store: `ListAuditFacets(ctx) (actors, servers, tools []string, err error)` (distinct values, sorted, capped at 200 each) to fill the filter dropdowns.
- [ ] Web audit page `GET /audit` (checker only): query params `actor, server, tool, from, to (YYYY-MM-DD, UTC; "to" is inclusive of that day), before`. Bad dates or a non-numeric `before` give 400 with a message, not a 500. Columns: time (UTC, RFC3339), actor, server, tool, arguments (compact JSON truncated to 120 characters with an ellipsis, with the full JSON in a `<details>`, never in a `title` attribute), rows returned (`result_count`, blank when NULL), latency (ms, blank when NULL), error. An "Older" link carries the filters plus `before=<next>`. Empty result prints "No audit entries match."
- [ ] Store: `RunMetricsByStep(ctx, runID) ([]StepUsage, error)`: per `run_steps.kind` family (`explain`, `investigate`, `verify`; every other kind rolled into `other`), the sum of input, output and cache-read tokens, cost (canonical decimal string), the LLM call count, and total `llm_calls.latency_ms`. Only kinds with at least one call appear, in the order explain, investigate, verify, other.
- [ ] Store: `RunsSummaryStats(ctx) (LastRunStats, error)`: for the newest run by `started_at` that is `done` or `partial`: run id, company, month, findings total, verified count, and open high-severity count (`status = 'open' AND severity = 'high'`). `Found=false` when no such run.
- [ ] Web metrics page `GET /runs/{id}/metrics` (any role): the run's status, duration (`runDuration`), total tokens and cost (from `close_runs`), the by-step table, verified rate as `N of M (P%)`, and the trace ID as text with a "trace" label. No external link: there is no Langfuse base-URL setting yet (see Notes). Unknown run id gives 404; a malformed id gives 400, as the run page does. Link to it from the run page.
- [ ] Runs page summary card (above the table): the last finished run's company and month, verified rate and open high-severity findings, each a link to the run; "No finished runs yet." otherwise. The existing runs-page assertions must keep passing.
- [ ] Wire: `Options.Audit AuditStore` (the two audit store methods plus what the metrics page needs, as one small interface `AuditStore`; `var _ AuditStore = (*store.Store)(nil)`), set from `*store.Store` in `cmd/agent/serve.go`. Add "Audit log" (checker) to the home page links. Update the role-matrix test rows.
- [ ] Demo-flow test (the ticket's acceptance): drive an in-memory fake through accept, dismiss, propose, approve and an MCP-style row, then assert each appears on `/audit` with the right actor, and that filtering by actor, server, tool and date narrows the list.

## Acceptance (human-readable)

- The commands above pass.
- A checker opening `/audit` after a demo run sees one row per tool call and per approval action, each with the user who did it (maker, checker, or `agent:run/<id>`).
- A maker or viewer gets 403 on `/audit`; an anonymous request goes to login.
- `/runs/<id>/metrics` shows explain and investigate token splits that add up to the run's totals (within the verify and other rows) and a verified rate that matches the findings table.
- The runs page shows the last finished run's verified rate and high-severity open count.

## Out of scope

- Writing audit rows, changing `audit_log`, or changing `internal/mcpkit` and `internal/approvals` (protected).
- A JSON audit API, CSV export, or charts.
- Marking a finding accepted after its entry posts, and the dismiss-versus-propose race (both need `internal/store` and `internal/approvals` changes; they stay in `tasks/hardening.md` for a hardening ticket).
- A Langfuse link (needs a config setting and `.env.example` entry; add one later).
- Rate limiting (CC-1102).

## Notes

- Decision for the owner to confirm: `/audit` is checker-only because audit arguments can hold unmasked synthetic proposal data. Widen to `anyRole` by changing one table row if wanted.
- Keyset pagination (not OFFSET) keeps pages stable while new rows arrive; `before` is an opaque row id.
- Truncate by runes, not bytes, so a multi-byte character is never cut.
- No new dependencies. Regenerate templates with `make generate`; do not hand-edit `*_templ.go`.
- Unit tests use a fake `AuditStore`; only the `integration`-tagged store tests need Docker. Keep integration tests from touching rows they did not create (filter on a unique actor).
