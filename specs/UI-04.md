# UI-04 · Dashboard

## Goal

The page you land on says where the close stands for the selected company and month, which runs exist for each company, and what is waiting on you, with buttons to act, replacing the old list of API paths.

## Context

- Ticket: `tasks/frontend-plan.md` sections 4 and 10 (`UI-04`). **No new store query** (the plan's "one store query" is dropped): everything comes from the interfaces the web layer already has, with fixed bounds, so there is no new SQL, no protected path and no new write.
- Route unchanged: `GET /` is the `GET /{$}` row (handler `s.handleHome`, now in `home.go` after UI-03b). Roles unchanged (any signed-in role). Do not edit `routes.go`. The catch-all `GET /` row and `GET /{$}` must both stay `anyRole` (a comment in `navTable` says so).
- Every data source is optional: with `s.runs == nil` (Runs not configured) or `s.approvals == nil` the page still answers 200 and shows that section as an `EmptyState` ("Close runs are not configured on this server"); a store error in one section shows that section's error state and logs, and never breaks the others or the page.
- Existing tests that must keep passing: `TestHomeActions` (every `data-action="<id>"` for the actions the role may take, none for others, user name and `data-role` shown) and `TestShellHomeLinks` (links inside `<main id="main">` to `/runs` for every role, `/approvals` and `/audit` only for the checker, no `/api/` text). Keep those hooks. If an assertion checks exact old home markup that changes only cosmetically, adapt component output first and the assertion only if unavoidable; list each change (this ticket may edit `routes_test.go` and `shell_test.go` only for that).
- CSP, escaping and no-inline rules from UI-01/02: no inline style, so any bar or gauge uses `<meter>` or `<progress>` elements or tokenised CSS classes, never a `style` attribute.

## Data and limits

- **Context**: company and month from `contextFor` (UI-03).
- **Latest run per company**: one `ListCloseRuns(ctx, 50)`; group by company id keeping the newest per company (the list is newest first); at most 12 companies are shown, with "and N more" text. Companies come from the same call plus `ListCompanies` so a company with no run still appears ("No runs yet").
- **Context run summary**: the newest run for the context company and month (from the same list, no extra query); then one `ListFindingsByRun` for that run only, giving counts by severity and by status and the number unverified (the finding's verified flag as the findings page uses it) and needs-review.
- **Waiting on you**:
  - checker: the count of `s.approvals.Pending` (one call; show the first 5 as links to `/proposals/{id}` only if that route exists, else to `/approvals`);
  - maker: findings in the context run still `open` or `needs_review` (from the same findings list), with a link to the run's findings page;
  - viewer: no queue, text "Nothing is waiting on you".
- Bound every list at 50 rows and every call at the request context (no goroutines, no caches).

## Layout

- `PageHeader` "Dashboard"; subtitle "COMPANY MONTH" (escaped); actions: for makers a primary "Start a close" link `Button` to `/runs?company=…&month=…` (query-escaped), and an "Ask a question" link `Button` to `/ask` when the user may follow it (`allows`).
- Row of `StatTile`s for the context run: Status (a `StatusChip` inside, the tile links to the run), Findings, High severity, Needs review, Unverified; with no run for the context: one `EmptyState` "No close run for COMPANY MONTH yet" with the Start button for makers.
- "Findings by severity": the three severities as `SeverityBadge` + count + a `<meter>`; "By status" as a small `DataTable`.
- "Latest run per company": a `DataTable` (company link to its run, month, `StatusChip`, findings count, started time or "Queued").
- "Waiting on you": a `Card` per role as above.
- "Quick actions": keep every existing `data-action="<id>"` element for the actions the role may take (link `Button`s where a page exists, plain descriptive text where only an API exists, no method or path shown).
- Narrow screens: one column, tiles wrap two per row.

## Subtasks

- [ ] `dashboard_view.go` view types; `home.go` handler builds them from the sources above (one helper per section so a failure in one is isolated); `home.templ` renders the dashboard.
- [ ] `css/dashboard.css` (tokens only, `<meter>` styling).
- [ ] Tests `TestDashboard*` in `dashboard_test.go` (fakes from `helpers_test.go`, `runs_test.go`, `approvals_test.go`):
  - `TestDashboardContextSummary`: counts by severity, status, unverified and needs-review for the context run; a hostile company name escaped.
  - `TestDashboardLatestPerCompany`: newest run per company, "No runs yet" for a company without one, "and N more" beyond 12.
  - `TestDashboardWaitingByRole`: checker sees the pending count and links, maker the open findings, viewer the empty text; one `Pending` call and one `ListFindingsByRun` call only (count the fake's calls).
  - `TestDashboardNotConfigured`: no runs backend or no approvals backend still gives 200 with the section empty states.
  - `TestDashboardSectionErrors`: a failing store in one section shows that section's error and the rest renders; the error text is generic and the cause is logged.
  - `TestDashboardQuickActions`: `data-action` hooks and Start button per role, Start link query-escaped.
  - `TestDashboardNoQueryCountGrowth`: with 40 runs across 12 companies the fake store sees exactly one `ListCloseRuns` call, one `ListCompanies` call and one `ListFindingsByRun` call.
  - `TestDashboardNoAPIPaths`: the page text shows no `/api/` path.
  - `TestDashboardEscaping`: hostile strings in company, month, run error and finding titles never appear raw.

## Acceptance (human-readable)

- A maker lands on the dashboard, sees where the selected close stands and what needs action, and starts a close with one click.
- A checker sees how many proposals await them and goes there with one click; a viewer sees status only.
- With backends missing the page still loads.

## Out of scope

- New store queries, history charts, per-user company filtering, auto-refresh.
