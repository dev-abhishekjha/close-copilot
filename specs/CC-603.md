# CC-603 · Duplicate vendor payment detector

## Goal

Flag supplier invoices that were paid more than once, as `duplicate_vendor_payment` findings keyed on the original Purchase Invoice.

## Context

- Ticket: `docs/implementation-tickets.md`, section `CC-603` (you need not open it; it is quoted below).
- Plan row: Phase 2, implementer, standard risk, depends on CC-601 and CC-306; gate-run acceptance `duplicate_vendor_payment.recall>=6/6; clean month 0`.
- ERPNext won't allocate a payment beyond an invoice's outstanding amount, so a duplicate shows up as an **unallocated advance** to the same supplier. Detect:
  1. an unallocated Pay entry with the same supplier and amount as an allocated one within 30 days, or
  2. an unallocated Pay entry whose remarks name an invoice that is already fully paid.
- How the planter builds one (CC-306, tickets doc): "Pay the same invoice again as an unallocated advance ('Payment for CLD/2026/0912')", changed in books and bank. The remark carries the supplier's **bill number** (`PurchaseInvoice.BillNo`), while the finding key must be the **ERPNext name** of the original Purchase Invoice.
- Finding key: `invoice` = the ERPNext name of the original Purchase Invoice. Amount = the duplicate payment's paid amount. Ground-truth shape: `{"type": "duplicate_vendor_payment", "keys": {"invoice": "ACC-PINV-2026-00044"}, "amount_paise": 4500000}`.
- Subtasks quoted from the ticket: group the month's Pay entries by supplier and find allocated/unallocated pairs with equal amounts within 30 days; parse invoice numbers out of remarks with a regex, normalised; cross-check the bank (two withdrawals of that amount whose narrations name the same party); a legitimate second payment for a different invoice of the same amount must not be flagged.
- Data you get from the readers (`internal/ledger/models.go`):
  - `PaymentEntry{Name, PaymentType, PartyType, Party, PaidAmount, PostingDate, Remarks, UnallocatedAmount, References []PaymentEntryReference}`; a reference has `ReferenceDoctype`, `ReferenceName`, `AllocatedAmount`.
  - `PurchaseInvoice{Name, Supplier, BillNo, GrandTotal, OutstandingAmount, PostingDate}`.
  - `store.BankLine{TxnID, TxnDate, Narration, Ref, AmountPaise}`; withdrawals are negative.
- Readers return submitted documents only, and filter by posting date. Read payments from 30 days before the month start to the month end, so an original paid in the prior month still pairs; read purchase invoices from a wider window (start with 6 months before the month start) so the original invoice is found. Report suspects only for payments **posted in the month**.
- Invoice-number normalisation: `NormInvoiceNo` is CC-403's and is not merged. Do not wait for it and do not import `internal/evidence` (`internal/checks` must not reach `internal/frappe`, `internal/books` or `internal/seed`, enforced by `deps_test.go`). Write a small unexported `normInvoiceRef` in `duplicates.go` (upper-case; keep letters and digits only). Add a comment that it is to be replaced by the shared function once CC-403 lands.
- Replay recordings serve only the argument sets that were recorded (`ErrFixtureMissing` otherwise). This check is not wired into the workflow in this ticket, so it needs no recordings; do not edit `evals/fixtures/**`.

## Subtasks

- [ ] `DuplicatePaymentCheck` (`Name()` returns `"duplicates"`), implementing `Check`.
- [ ] Select suspects: Pay entries to a Supplier, posted in the month, with `UnallocatedAmount > 0`.
- [ ] Rule A: an allocated Pay entry (it has references; it is not the suspect itself) to the same supplier, with equal paid amount, posted within 30 days either side. The original invoice is that entry's Purchase Invoice reference.
- [ ] Rule B: parse invoice numbers from the suspect's remarks with a regex; normalise; match to a purchase invoice of the same supplier by normalised `BillNo` that is fully paid (`OutstandingAmount == 0`). The original invoice is that invoice's `Name`.
- [ ] When both rules fire and disagree, prefer Rule B's invoice. When no Purchase Invoice name can be resolved, emit no finding (the key would be empty); cover this in a test.
- [ ] Bank cross-check: two withdrawals of the paid amount whose narrations name the same party (case-insensitive supplier name or a word of it). It corroborates: `SeverityHigh` and an `EvidenceEvidence("list_bank_lines", ...)` ref when found, `SeverityMedium` when not. It never suppresses a finding.
- [ ] One finding per original invoice: if several suspects point at the same invoice, one finding, all payment names in evidence. Output order is deterministic.
- [ ] Fixed 30-day window as a package constant (no new rules.yaml field).
- [ ] Tests, table-driven with fakes: Rule A hit, Rule B hit, both agree, both disagree, a legitimate second payment for a different invoice of the same amount (allocated, not flagged), same amount to a different supplier, outside 30 days, remarks naming an invoice with outstanding > 0 (not flagged), bank corroboration on and off, unresolvable invoice, two suspects for one invoice, error from each reader wrapped with `%w`, a clean month returning no findings, six planted duplicates all found with the right `invoice` keys and amounts.

- A clean month gives zero findings.
