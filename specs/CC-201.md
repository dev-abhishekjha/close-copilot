# CC-201 · API users, keys and schema discovery

## Goal

Dedicated ERPNext API credentials, plus a committed dump of the fields of every DocType the project touches, so later tickets code against real field names.

## Context

- Ticket: `docs/implementation-tickets.md`, section `CC-201`. Plan: risk class data-sensitive (it holds credentials).
- The stack from CC-102 is running. Run `make up`, then `deploy/wait-healthy.sh 900` if it isn't.
  - Site `erp.localhost`, company Sharma Traders Pvt Ltd, frappe/erpnext 15.122.0 with India Compliance 15.32.0.
  - The backend container: `docker compose -f deploy/erpnext/docker-compose.yaml exec -T backend bench --site erp.localhost ...`. See `deploy/erpnext/lib.sh` for helpers and the dev Administrator password.
- `.env.example` already lists `ERP_BASE_URL`, `ERP_SITE`, `ERP_API_KEY`, `ERP_API_SECRET`, `ERP_SEED_API_KEY` and `ERP_SEED_API_SECRET`. `internal/config` already loads them. Don't change either.
- **Secrets:**
  - Never read or write `.env` (CLAUDE.md).
  - Keys go only into `tmp/erp-keys.env`. It's git-ignored and must be mode 600, with `KEY=value` lines for the four `ERP_*_KEY`/`SECRET` variables plus `ERP_BASE_URL` and `ERP_SITE`. The owner copies them into `.env`.
  - Never print a secret to stdout or a log. Print key IDs only if you have to.
- **Outbound HTTP must use `internal/httpx.New(cfg)`.** The CC-002 `egress` analyzer fails any raw `http.Client` or `http.Get`. Every request carries:
  - `Authorization: token <key>:<secret>`
  - `Accept: application/json`
  - `Host: <ERP_SITE>` (or rely on the frontend's `FRAPPE_SITE_NAME_HEADER`)
- **No ERPNext writes beyond the users and keys.** Don't create Journal Entries or other documents, because the books must stay clean for the seeder (CC-303 onwards).
- Unit tests never call ERPNext: use `httptest` fakes and recorded fixtures. The live checks are the acceptance commands.

## Subtasks

- [ ] `deploy/erpnext/api-users.sh`, run through bench inside the backend container:
  - Creates `copilot-bot@example.com` (enabled, user type System User, role **Accounts User** only) if it's missing.
  - Generates API keys for that user and for Administrator if either has none, and writes all four values to `tmp/erp-keys.env` (umask 077).
  - Is idempotent: a second run changes nothing and leaves the file as it is.
  - `--rotate` regenerates both key pairs and rewrites the file.
  - Frappe v15's `frappe.core.doctype.user.user.generate_keys` returns the secret only once, so capture it then.
- [ ] `cmd/probe`, replacing the stub and keeping `cli.Main`. Subcommands:
  - `auth`: calls `GET /api/method/frappe.auth.get_logged_user` with the bot key, prints the user and exits non-zero unless it is `copilot-bot@example.com`.
  - `perms`: as the bot, checks four things and exits non-zero if any fails:
    - (a) it can read GL Entry, Purchase Invoice and Payment Entry (list with `limit_page_length=1`; an empty list is fine);
    - (b) it holds create and submit rights on Journal Entry, checked through Frappe's permission API **without creating a document**;
    - (c) it is **refused** (403 or `PermissionError`) on an Administrator-only DocType, e.g. `System Settings` or `User`;
    - (d) it is refused on a write to `System Settings`.

    Print one line per check, and document which endpoints you used.
  - `schema --out <dir>`: for each DocType in the list below, fetches `GET /api/resource/DocType/<name>` (standard fields) and `GET /api/resource/Custom Field?filters=[["dt","=",<name>]]` (custom fields; India Compliance adds many, e.g. `supplier_gstin`). It writes `<dir>/<kebab-name>.json`.
    - Keep only stable keys: name, module, istable, is_submittable, and for each field fieldname, fieldtype, label, options, reqd, read_only and hidden, with custom fields marked.
    - Sort the fields by fieldname, use 2-space indent and a trailing newline, so that two runs give identical bytes.
    - Use the bot key. If Accounts User can't read DocType or Custom Field meta, use the seeder key for `schema` only, and say so in the README and your report.
  - Unit tests with `httptest` for every subcommand: header format, refusal detection, deterministic output, and secrets never appearing in output or errors.
- [ ] DocTypes to dump: Company, Account, Address, Supplier, Customer, Item, Purchase Invoice, Purchase Taxes and Charges, Sales Invoice, Payment Entry, Payment Entry Reference, Journal Entry, Journal Entry Account, GL Entry.
- [ ] Commit the dumps under `docs/erpnext-schema/`. `docs/erpnext-schema/README.md` covers:
  - how they were made (`go run ./cmd/probe schema --out docs/erpnext-schema`), with the frappe, erpnext and india_compliance versions;
  - a table of every field the project relies on, with its DocType and which later ticket uses it. Start from the ticket's examples, e.g. Purchase Invoice: `supplier`, `bill_no`, `bill_date`, `supplier_gstin`, `taxes[].account_head`, `taxes[].tax_amount`. Then cover GL Entry (`account`, `debit`, `credit`, `posting_date`, `voucher_type`, `voucher_no`, `party`, `company`), Payment Entry and Journal Entry Account.

## Acceptance (human-readable)

- The bot user exists with only Accounts User. Its key can read the three DocTypes and has Journal Entry create and submit rights, and it is refused on an admin-only DocType and on a System Settings write.
- Schema JSON for all 14 DocTypes is committed, regenerates byte-for-byte, and the README names each field used and where.
- `tmp/erp-keys.env` is mode 600 and holds working keys; nothing secret is committed or printed.
- The owner copies the four key lines into their `.env` (`docs/erpnext-schema/README.md` or the script's last message says how).
