# UI-05 · Close runs rework: start form, status chips, live stepper, re-run

## Goal

The close-run pages use the new design system and a user can start a close, watch it progress, reach its findings and run it again from buttons, with the behaviour and security of today's pages unchanged.

## Context

- Ticket: `tasks/frontend-plan.md` sections 4 and 10 (`UI-05`, summary row in section 6). **Deviation from the table:** the "start-close modal" is an inline Start card on `/runs`: a modal cannot carry the selected company and month, and an inline form needs no JavaScript. Say so in the PR summary.
- Pages and routes stay as they are (`routes.go` is not touched): `GET /runs`, `POST /runs`, `GET /runs/{id}`, `GET /runs/{id}/progress` (htmx fragment), `GET /runs/{id}/findings`. Handlers keep their status codes, redirects (`303 /runs/{id}`, `HX-Redirect` to the findings page when a run ends), error rendering (400, 409, 429 with `Retry-After`) and role rules.
- **Hooks that existing tests and htmx rely on must survive.** Before editing, run `go test ./internal/web/ -run 'Runs|RunProgress|RunFindings' -v` and `grep -n` the test files for the selectors they use. At least these stay present with the same meaning: `form.start-run` with `select[name=company]` and `input[name=month]` and a hidden `csrf_token`; `table.runs` and `tr[data-run]` with cells `td.status`, `td.findings`, `td.cost`, `td.duration`; `#runs-summary`, `.summary-run`, `.summary-verified`, `.summary-high`; `#run-progress` with `data-status`, and `hx-get`/`hx-trigger="every 2s"`/`hx-swap="outerHTML"` only while polling; `li[data-step]` for each step with the current one marked as today (`stepClass`); `ul.counts li[data-type]`; `.duration`; `.tokens` with `.input`, `.output`, `.cache`, `.cost`; `p.error` for run errors; on the findings page `form.filters` (GET, `select[name=type]`, `select[name=status]`), `table.findings`, `tr[data-finding]` with `data-severity`, and cells `td.severity`, `td.type`, `td.title`, `td.amount`, `td.status`, `td.verified`, `td.detail`, plus the nested-row marker for variance children. Use `Cell.Class` and `Step.Key` (UI-03a) to keep them. If a test asserts exact old visible text that changes only in case or wrapping (for example a severity label), adapt the component output first (a lower-case label via the cell text) and only then, if truly unavoidable, the assertion; list every changed assertion in the PR summary. No assertion about behaviour, escaping or roles is weakened or removed.
- CSP, escaping and no-inline rules as in UI-01/02. Run, company and error text is data: escaped. The run `Error` string is shown in a `Card` tone `danger`, escaped.
- Shared files are owned by UI-03a: do not edit `ui*.templ`, `ui.go`, `components.css`, `app.css` or `design_test.go`. Page rules go in `static/css/runs.css`.

## Pages

**`/runs`** (`Runs` template): `PageHeader` "Close runs". A Start card (maker only, `p.CanStart`): `SelectField` company, `Field` month (type `month` with `pattern` and `placeholder="YYYY-MM"` kept as fallback, value from `p.Month`), primary `Button` "Start close" (`type=submit`). Prefill comes from the page as today (query, else shell context). Error text from the failed start sits above the form as an alert. A summary row (`ShowSummary`): up to three `StatTile`s (last finished run, verified rate, open high-severity findings), each a link, keeping the `.summary-*` anchors. The runs list is a `DataTable` (columns Company, Month, Status, Findings, Cost, Duration), company cell a link to the run, status a `StatusChip`, numeric cells `Num`. No runs: `EmptyState` with the Start card visible for makers.

**`/runs/{id}`** (`Run`, `RunProgress`): `PageHeader` with the company and month, a `StatusChip`, and actions: "Findings" (link `Button`), "Metrics" (link `Button`, the existing metrics URL), and for a maker, on a finished run (`done`, `partial` or `failed`) a **Re-run** button: a small POST form to `/runs` with hidden `company`, `month` and `csrf_token`, submit `Button` "Run again". The run page needs `CanStart` and a CSRF token in `RunPage` (add fields in `runs_view.go`); the server still decides: a viewer or checker posting gets today's 403, and a company with a run in flight still answers 409 as today (the 409 page shows the error with the Start card).

The progress partial renders inside `#run-progress`: a `Stepper` of the real lifecycle (queued, running, then one final step labelled with the terminal status: done, partial or failed, in `failed` state if failed), `Step.Key` set to the status so `li[data-step]` hooks stay; then `StatTile`s for Findings total, Duration, Cost and the three token counts (keep the `.tokens` and `.duration` hooks inside them or alongside), then the type counts as chips in `ul.counts`. While polling, `role="status"` text names the current step; the fragment is not announced on every poll (no `aria-live` on the replaced container). Terminal runs have no `hx-*` attributes as today.

**`/runs/{id}/findings`** (`RunFindings`, `findingRow`): `PageHeader` with run links, the filter form restyled with `SelectField`s and a secondary `Button`, then a `DataTable` with `SeverityBadge`, `StatusChip`, `VerifiedBadge` and the amount right-aligned; variance children stay nested under their parent as today. Empty: `EmptyState` "No findings match".

## Acceptance (human-readable)

- A maker starts a close from `/runs`, lands on the run page, sees the stepper advance and reaches the findings by the link or the automatic redirect; after it finishes can run it again with one click.
- Viewers and checkers see the same pages without any Start or Re-run button.
- Every existing test passes; the PR summary lists any assertion that had to change and why.
