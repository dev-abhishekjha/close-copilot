# CC-806 · Citations: retrieve before explaining

## Goal

Explanations cite the exact policy section, contract clause or close note, and retrieved text never reaches a model that can call tools.

## Context

- Ticket: `docs/implementation-tickets.md`, section `CC-806` (do not open it; everything needed is quoted here). Plan row: phase 3, llm-engineer, data-sensitive, depends on CC-805 and CC-705. Check: "Citation precision at or above baseline".
- Ticket description (quoted): "retrieval is a workflow step, not a tool the model chooses. Before explaining, the workflow builds a query from the finding, runs the search, stores the passages as a `retrieval` artifact, and hands them to the explainer, whose only tool is the forced `emit_explanation`. Passages are fenced as DOCUMENTS and treated as data (CC-704 rule 3)."
- Ticket subtasks (quoted): the `retrieving` state: one `retrieve` step per finding, with a query built from its type, supplier and account; keep the top three passages. Store the passages (`doc_id`, section, text, content hash) as a `retrieval` artifact and list it in the explain step's `input_refs`. Citation format `[POL-001 §4.2]`; the CC-705 verifier checks each citation against the passages it was given. Score citation validity and precision against `evals/golden/citations.yaml` (CC-907).
- Ticket acceptance (quoted): across `suite-v1`, prepaid, capitalisation and GSTR-2B findings cite the matching policy section, and duplicate-payment findings cite the supplier's contract. Citation validity is 100%; citation precision is at or above the baseline.
- Hardening note (tasks/hardening.md, from the CC-704 G5): "`validator.documents` is never filled, so every citation is rejected today. Fill it from the same DOCUMENTS slice sent to the model and check `section` as well as `doc_id`."
- **Invariants (CLAUDE.md, plan guardrail):** retrieved document text never reaches a model that can call tools; the explainer's only tool is `emit_explanation`; the investigator has no `search_documents` and no admin tool and never sees document text; every MCP call is scoped to the run's company and month (CC-506); GSTINs, PANs and person names are pseudonymised before any model call (CC-710).
- **The tool (CC-805, merged).** MCP `evidence/search_documents` on `/mcp` only. Input `{query (required), company?, doc_types?, k? (default 5)}`. Output rows `{doc_id, doc_type, section, title, snippet, score}`; `snippet` is whitespace-collapsed, at most 600 characters (`evidence.MaxSnippetChars`); `score` is a JSON number (decode as `json.Number`). The company filter is forced to the run scope's company; an explicit other company returns `out_of_scope`. The call needs a valid run scope on the ctx (`agent.WithRunScope`, already applied by the workflow's `scopeRun`). Its schema golden is `internal/evidence/testdata/schemas/search_documents.json`; read it for the exact output shape (is it a bare array or an object wrapping `results`; copy what the golden says).
- **Corpus ids (CC-801/803).** `doc_id` is the file stem: `POL-001-accounting-policy` (shared, `doc_type` policy), `CON-<supplier-id>` (contract), `NOTE-<company>-<YYYY-MM>` (close_note). `section` is the heading text including its number, e.g. `§4.2 Spread annual costs monthly`. A citation is `store.Citation{DocID, Section}` and must match a passage's pair **exactly**.
- **Golden set (CC-907, drafted by the owner's eval engineer; read-only here).** `evals/golden/citations.yaml`: one case per planted type, e.g. `prepaid_not_spread` expects `POL-001-accounting-policy / §4.2 Spread annual costs monthly`; `misclassified_expense` expects `§3.1` or `§3.2`; `gstr2b_missing_in_2b` expects `§6.1` or `§6.2`; `unrecorded_bank_charge` `§7.1`; `missing_accrual` `§5.1`; `wrong_period_posting` `§8.1`; `duplicate_vendor_payment` expects `CON-vaani-telecom` `§3` or `§7`. Use these as the realistic queries for your tests; never edit the file.
- **Verifier side is done (CC-705).** `CodeVerifier.checkCitations` (`internal/agent/verify.go:426`) reads `ExplanationArtifact.DocumentRefs` (retrieval artifacts), collects every object with string `doc_id` and `section` fields from their JSON (`collectPassages`), and flags a citation not in that set (`citation_not_supplied`) or absent from `doc_chunks` for the company (`citation_unknown`). With empty `document_refs` any citation is a violation. So your retrieval artifact must keep `doc_id` and `section` as string fields on each passage object, and the explanation must carry the refs.
- Run states and steps: `queued -> preflight -> checking -> retrieving -> explaining -> verifying -> ...` Step kinds include `retrieve` (shared spec: `run_steps.kind: router | check.<name> | retrieve | explain | verify | investigate | synthesize`). Today the workflow records one skipped `retrieve/close` step (`reasonRetrieve = "retrieval arrives with CC-806"`, `workflow.go:128`, called at `workflow.go:619`).

## Subtasks

- [ ] `retrieve.go`: `type Passage struct{DocID, DocType, Section, Title, Text string; SHA256 string}`; `type RetrieveRequest struct{Company, Month string; Finding store.Finding; Query string}`; `type Retriever interface{ Retrieve(ctx, RetrieveRequest) ([]Passage, error) }`; `MCPDocuments` calling `evidence/search_documents` through `Registry.callJSON` with `{query, company: req.Company, k: 3}`, keeping at most three passages (`maxPassages = 3`), cutting to the top three even if the tool returns more. `SHA256` is the hex SHA-256 of the passage text. Compile-time assertion `var _ Retriever = (*MCPDocuments)(nil)`.
- [ ] `buildQuery(f store.Finding) string` (pure, unit-tested): the finding type in words (`prepaid_not_spread` → "prepaid not spread"), then the supplier (`Keys["supplier"]` when present) and the account, if the finding's keys carry one. Cap at 300 characters. No amounts, no GSTINs, no invoice numbers (they add noise, and identifiers stay out of queries). Table-test one query per type in the golden set.
- [ ] Workflow: when `Retriever` is set and a model/explainer exists, the retrieving state runs one `retrieve` step per finding (subject = finding ID), at most `Parallel` at a time, before explaining. A tainted finding gets a skipped retrieve step (`reasonTainted`) and no passages. On success, store `{"query": ..., "passages": [{doc_id, doc_type, section, title, text, sha256}]}` via `PutArtifact(store.ArtifactRetrieval, runID, stepID, ...)` and finish the step done with that ref as output. Zero hits is a done step with an empty `passages` list (the explainer then gets empty DOCUMENTS and cites nothing). A search error fails that step with a fixed reason (no text from the tool), the finding is still explained with empty DOCUMENTS, and the run is not failed (record it in the run's partial notes only if the existing pattern does the same for other worker errors; otherwise just log counts). With no Retriever, keep today's single skipped `retrieve/close` step so stored runs, report fixtures and the eval replay stay unchanged.
- [ ] Workflow: pass the finding's retrieve-step output refs to the explainer as `ExplainRequest.DocumentRefs`, reusing them on every explain attempt (retries do not re-search). On resume a done retrieve step is not re-run (`begin` returns it done).
- [ ] Explainer: load each `DocumentRefs` artifact (`artifactReader`, hash-verified), build the `Documents` slice from its passages (cap each text with `capText`; at most three), put them in DOCUMENTS, and set `validator.documents` from the **same slice** sent to the model. `validate` checks the `(doc_id, section)` pair exactly, not `doc_id` alone. A citation naming anything else is `malformed` (field `citations`), with the existing one retry. Set `art.DocumentRefs = req.DocumentRefs` (never nil; `[]string{}` when none).
- [ ] Masking: DOCUMENTS goes through `pseudo.Mask` with the rest of the user message. Validate the model's citations against the masked slice it saw, then `unmask` each citation's `doc_id` and `section` before storing, so the stored citation equals the retrieval artifact's unmasked pair (the verifier compares unmasked pairs). Test with a fake masker that rewrites passage text and leaves ids intact, and one that would also rewrite a section heading, to show the stored citation still equals the artifact's.

## Out of scope

- **Citation scoring.** The ticket's last subtask ("score citation validity and precision against `evals/golden/citations.yaml`") needs code in `internal/evals` (a scorer, a baseline metric, a `--require` key) and recorded or live retrieval in `cmd/eval`. `llm-engineer` never touches `internal/evals`, `evals/baseline.json` or `cmd/eval`, and no ticket in `tasks/graph.yaml` owns it. It is split off to an eval-engineer follow-up (suggested ID `CC-806b`; the owner adds it to the graph). Until then the eval's `Workflow.Retriever` stays nil and its runs keep the single skipped `retrieve/close` step, so recorded fixtures and the replay baseline are unaffected.
- The `internal/store` API gap: the ticket says to list the retrieval artifact in the explain step's `input_refs`, but `Store.Begin` has no way to set input refs on a first attempt (it only moves outputs of earlier attempts there). The retrieval artifact is reachable through the retrieve step's `output_refs` and the explanation's `document_refs` (CC-709 rebuild holds). If the owner wants `input_refs` literally, that is a small `internal/store` ticket; do not touch the store here.
- Ingest-time quarantine and a retrieval-time suspicious-text check (CC-1103 Phase 3 pass), the poisoned-contract case, and fencing inside the corpus. Passages are only fenced by DOCUMENTS and rule 3 here.
- `/api/ask` (CC-707) and its two-stage answer.
- Any change to `evals/golden/**`, `evals/scenarios/**`, `evals/baseline.json`, `internal/approvals/**`, `docs/**`.

- No new dependencies. Use `crypto/sha256` and `encoding/hex` from the standard library.
- `retrieve.go` is not in the graph's `files` (which list `explain.go` and `workflow.go`); a new file keeps the tool name out of `explain.go` so CC-805's source scan stays meaningful. - G5 focus for the reviewer: no retrieval path to the investigator; company comes from the run, never from the finding; DOCUMENTS content is masked and capped; the tool name only in `retrieve.go`; no passage text in logs or errors.
