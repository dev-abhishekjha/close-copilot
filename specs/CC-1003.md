# CC-1003 · Finding detail page

## Goal

One page that lets an accountant decide about a finding in under a minute: what is wrong, the proof, the rule, and the proposed fix.

## Context

- Ticket: docs/implementation-tickets.md, section `CC-1003` (quoted here; don't open it).
- Plan row: phase 4, implementer, standard, depends on CC-1002 (merged). Check: "Evidence rows and ERPNext links for every finding type". Needs no ERPNext lock.
- **Ticket text.** Show the evidence as the raw rows the tools returned, not as prose, and link each ERPNext document to its page in the ERPNext UI (`http://localhost:8080/app/purchase-invoice/<name>`), so a reviewer can check the source directly. Subtasks: (1) header: type, severity, amount, status, verified badge, or a "needs review" banner with the verifier's reasons; (2) explanation and suggested action; each citation shows its snippet when expanded (`<details>`); (3) evidence panel: bank lines, GL entries and GSTR-2B rows rendered from `EvidenceRef`s, with ERPNext links; (4) investigation trail for agent findings: each tool call with its arguments and row count; (5) proposal preview: a balanced debit and credit table with totals; (6) actions for makers: "Create proposal", "Mark accepted", "Dismiss" with a required reason. Acceptance: for every finding type in the suite, the detail page shows evidence rows and working ERPNext links.

  - htmx is the vendored `internal/web/static/htmx.min.js` (2.0.4) under CSP `script-src 'self'`. The base layout already loads it and sends the CSRF token on every htmx request through `hx-headers`. No inline script, no `hx-on`, no CDN. Every `hx-*` target is a same-origin path.

  - Model-written fields (`explanation`, `action`, citation snippets) and every evidence value render as plain text through templ's escaping, never as HTML or Markdown. No `templ.Raw`, no `innerHTML`.

- **Finding** (`internal/store/runs.go:78`): `id`, `run_id`, `type`, `severity` (`high|medium|low`), `title`, `amount_paise *money.Paise`, `keys map[string]string`, `evidence []EvidenceRef`, `explanation *string`, `action *string`, `citations []Citation`, `proposal *JournalProposal`, `verified bool`, `status` (`open|needs_review|accepted|dismissed`).
- **EvidenceRef** (`runs.go:39`): `server` (`books|evidence`), `tool`, `args` (raw JSON), `ids []string` (doc names, bank txn ids, chunk ids), `artifact` (sha256 of the stored tool-result snapshot). **`artifact` can be empty** for a finding whose snapshot was not stored (a deterministic finding before the explain step ran): then show the tool, args and ids and the text "snapshot not stored", no rows. **`Citation`**: `doc_id`, `section`.
- **Tool-result snapshot** (`store.Artifact`, kind `tool_result`, read with `GetArtifact(ctx, sha)`; a missing artifact wraps `store.ErrNotFound`, a hash mismatch `store.ErrArtifactMismatch`): `Content` is JSON `{"server","tool","args":{...},"result":...}`. `result` is an array of records, or an object whose array-valued fields hold the records (read those keys in sorted order), or any other value (one record). A record is an object.
- **Which rows to show for a ref** (same rule as the verifier's `selectRecords`, `internal/agent/explain.go:646`, which you must **reimplement** in `internal/web/evidence.go`; the web package cannot import `internal/agent`): a record is shown if one of its top-level string fields equals one of `ref.ids`. With no ids, show every record. Cap at 50 rows per ref and say "N more not shown". If ids are set and nothing matches, show "no matching rows in the snapshot" plus the ids.
- **Tool catalog** (record fields, shared spec):

  | Server | Tool | Record fields |
  | --- | --- | --- |
  | books | `list_gl_entries` | `name`, `voucher_type`, `voucher_no`, account, debit, credit, posting date, party |
  | books | `list_purchase_invoices` | `name`, supplier, supplier_gstin, bill_no, bill_date, posting_date, taxable, igst, cgst, sgst, lines, remarks |
  | books | `list_sales_invoices` | `name`, customer, posting_date, grand_total, collected_via |
  | books | `list_payments` | `name`, payment_type, party, amount, reference_no, posting_date, invoices |
  | books | `get_trial_balance`, `get_account_history`, `list_recurring_suppliers` | account/month/supplier rows, no ERPNext document |
  | evidence | `list_bank_lines` | `txn_id`, date, narration, ref, amount (signed paise), balance |

  Amounts in records are paise. Show integer-valued money fields (`amount`, `debit`, `credit`, `balance`, `taxable`, `igst`, `cgst`, `sgst`, `grand_total`) through `money.Paise.Format()` and everything else as text. Decode with `json.Decoder.UseNumber` so no float is involved; only `internal/money` converts.
- **ERPNext links.** Base URL comes from `ERP_BASE_URL` (`config.Config.ERPBaseURL`, default `http://localhost:8080`). The link is `<base>/app/<doctype-slug>/<name>` where the slug is the doctype lowercased with spaces turned into hyphens (`Purchase Invoice` → `purchase-invoice`), and `<name>` is path-escaped. Which records link:
  - `list_purchase_invoices` record → `purchase-invoice`, name from `name`.
  - `list_sales_invoices` → `sales-invoice`; `list_payments` → `payment-entry`; name from `name`.
  - `list_gl_entries` record → the doctype in `voucher_type` and the name in `voucher_no` (not the GL Entry's own `name`).
  - Evidence-server rows (bank lines, GSTR-2B) and the trial balance, account history and recurring-supplier rows have **no** ERPNext link.
  - A proposal's `erp_name` (posted entry) links to `journal-entry`.
  - Only render a link when the base URL parses as `http` or `https` with a host and the name is non-empty; otherwise show the name as text. A `voucher_type` that is not letters and spaces is shown as text, not linked. Open links with `rel="noopener noreferrer" target="_blank"`.
- **Verifier reasons.** For a finding with status `needs_review` (or `verified == false` with an explanation), find the step in `ListSteps(runID)` with `Kind == "verify"` and `Subject == finding.ID.String()`; among its `OutputRefs` read the artifact whose kind is `verdict` (`store.ArtifactVerdict`). Its content has `pass bool` and `violations: [{code, field, value_paise?, detail}]`. Define a small local struct for the JSON in `finding.go`; don't import `internal/agent`. Show each violation as `code`, `field` and `detail` (plain text; amounts via `Paise.Format`). If no verdict is found, show the banner with "the verifier recorded no reasons". A run whose verify step was skipped (status `skipped`) shows "not verified: step skipped".
- **Investigation trail.** An agent-investigated finding carries `keys["resolution"]` (CC-706), and its evidence holds the tool calls the investigator made, in call order. For such a finding, render the trail section: one line per `EvidenceRef` with `server.tool`, the args as compact JSON text, and the row count (the number of records in the snapshot; `n/a` when there is no artifact). Findings without `keys["resolution"]` have no trail section (their evidence appears in the evidence panel only). The trail's refs also appear as full rows in the evidence panel.
- **Proposal** (`store.JournalProposal`, `runs.go:62`): `payload.posting_date`, `payload.lines[] {account, debit, credit}` (paise, `money.Paise`), `payload.remark`, `status` (`proposed|approved|posted|rejected`), `maker`, `checker`, `reason`, `erp_name`. Preview: a table of account, debit, credit, a totals row, and a "Balanced" or "Unbalanced: difference ₹x" note (computed in integer paise). `Finding.Proposal` is a suggestion from the explainer; it is shown even when no maker has created it.
- **Finding types** (`internal/checks/finding.go:36`): `unrecorded_bank_charge`, `unmatched_bank_line`, `unmatched_ledger_entry`, `duplicate_vendor_payment`, `gstr2b_missing_in_2b`, `gstr2b_amount_mismatch`, `gstr2b_missing_in_books`, `gstr2b_wrong_period`, `gstr2b_not_eligible`, `missing_accrual`, `prepaid_not_spread`, `misclassified_expense`, `wrong_period_posting`, `variance`, `suspicious_instruction_text`. The page is **generic over the evidence refs**; no per-type branches, so a new type works unchanged. Tests walk this list.
- Invariants that apply: `internal/web` must not import `internal/frappe`, `internal/agent` or `internal/approvals`, and mustn't mention `MCP_ADMIN`, `MCP_TOKEN*` or `MCPTokenAdmin`. The page reads only Postgres through the store; it never calls ERPNext or MCP. A `suspicious_instruction_text` finding quotes document text: render it as escaped plain text and never as a link target.
- Money: `money.Paise.Format()` gives `₹1,23,456.78`.

## Design (decided; don't re-litigate)

- **Backend.** Add to `internal/web/finding.go`:

  ```go
  // FindingsStore is the slice of *store.Store the finding pages use.
  type FindingsStore interface {
      GetFinding(ctx context.Context, id uuid.UUID) (store.Finding, error)
      GetCloseRun(ctx context.Context, id uuid.UUID) (store.CloseRun, error)
      ListSteps(ctx context.Context, runID uuid.UUID) ([]store.Step, error)
      GetArtifact(ctx context.Context, sha string) (store.Artifact, error)
      SetFindingStatus(ctx context.Context, findingID uuid.UUID, status string) error
      InsertAuditLog(ctx context.Context, e store.AuditLogEntry) (int64, error)
  }
  ```

  Add `Findings FindingsStore` to `RunsBackend` (runs.go), and `ERPBaseURL string` to `Options` (set from `cfg.ERPBaseURL` in `OptionsFromConfig`). A nil `Findings` (or nil `Runs`) means not configured: the finding routes answer 501 after the role check, like CC-1002's. The 14 CC-1002 and 17 CC-1001 tests keep passing unchanged except `helpers_test.go` (shared helpers only). `*store.Store` must satisfy `FindingsStore` (add a compile-time assertion in a non-test file only if it needs no new import cycle; `internal/web` already imports `internal/store`).
- **Routes** (add to `routeTable`, `routes.go`):

  | Method | Path | Role | What |
  | --- | --- | --- | --- |
  | GET | `/findings/{id}` | viewer | Finding detail page |
  | POST | `/findings/{id}/accept` | maker | Mark accepted, then 303 to `/findings/{id}` |
  | POST | `/findings/{id}/dismiss` | maker | Form field `reason` (required), then 303 to `/findings/{id}` |

  An `{id}` that isn't a UUID or doesn't exist gets 404 (same body for both). CSRF applies to the POSTs through the existing middleware. These are HTML rows; don't add JSON rows (the `/api/findings/{id}/proposals` stub stays for CC-1004).
- **Layout of the page**, top to bottom, each as its own `<section>` with a stable `id` for tests: `header` (type, severity, amount, status, verified badge; link back to `/runs/{run_id}/findings`; company and month from the run), `review` (banner, only when status is `needs_review` or the finding is unverified with an explanation), `explanation` (explanation and action as `<p>` plain text; "no explanation yet" if nil), `citations` (each as `<details><summary>doc_id, section</summary>…</details>`; the snippet text is **not stored on the finding**, so the body shows doc_id and section only, with the text "snippet not stored on the finding" and a note in the PR summary that the snippet needs a later store or retrieval ticket), `evidence`, `trail` (only for investigated findings), `proposal`, `actions`.
- **Evidence panel.** One block per `EvidenceRef` in order: heading `server.tool`, the args as compact JSON text, then a table of the selected rows (columns are the union of the rows' keys, sorted, with `name`/`txn_id`/`voucher_no` first when present; nested values shown as compact JSON text), each row's ERPNext link in a "Source" column where the rules above give one. Reading the snapshot: load each distinct `artifact` once per request; an unreadable artifact (`ErrNotFound`, `ErrArtifactMismatch`, bad JSON) renders "snapshot unavailable" and logs `slog` at WARN with the finding id and a short sha, never the content. Verify the snapshot's `server` and `tool` equal the ref's; if not, show "snapshot does not match the reference" and no rows.
- **Actions** (makers only; viewers and checkers see no action buttons):
  - "Create proposal": rendered only when the finding has `proposal != nil` and the proposal status is empty or `proposed`; it is a **disabled** button labelled "Create proposal (available with approvals)". CC-1004 wires it. No handler.
  - "Mark accepted": POST form; allowed from `open` or `needs_review`; calls `SetFindingStatus(..., "accepted")`.
  - "Dismiss": POST form with a required `reason` (trimmed, 1 to 500 runes, no control characters other than newline); allowed from `open` or `needs_review`; calls `SetFindingStatus(..., "dismissed")`. Re-validation failure re-renders the page with status 400 and the message.
  - A finding already `accepted` or `dismissed` refuses both with 409 and the page shows its status; no buttons.
  - Each successful action writes one `InsertAuditLog` row: `Actor` = the user's name, `Tool` = `finding.accept` or `finding.dismiss`, `Args` = JSON `{"finding_id","run_id","from","to"}` plus `"reason"` for dismiss. If the audit insert fails after the status change, log the error and still redirect; if the status change fails, return 500 and write nothing. The status change and the audit row are not atomic (no store transaction for it); say so in a comment and in the PR summary.
  - Never log the reason text. The page shows the dismissal reason? **No**: the finding has no column for it; the reason lives in `audit_log` and the audit page (CC-1005) shows it.
- **Findings list link.** Make the title cell of each row in `runs_findings.templ` a link to `/findings/{id}` (plain `<a href>` with the id from `FindingRow.ID`); the list stays otherwise unchanged and `TestRunFindingsTable` must pass unchanged.
- **CSS.** Small additions to `static/app.css` for the evidence tables and the banner; no new files, no external fonts or scripts.
