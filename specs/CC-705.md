# CC-705 · Verifier

## Goal

Reject any explanation that states a number, citation or journal entry not grounded in the evidence. The verifier is plain Go, not another LLM call, and it reads only stored artifacts, so it can run again offline.

## Context

- **Ticket:** `docs/implementation-tickets.md`, section `CC-705`, including its "Plan changes" (`cmd/audit rebuild`, the `COPILOT_FAULT` flag and the action-enum check).
- **Plan:** `docs/orchestrated-implementation-plan.md`.
  - Task-graph row: regulated; check "All crafted bad outputs rejected; retry loop exercised".
  - Agent table, row "Critic / Evaluator": no tools. It reads the explanation artifact and the *snapshots* it cites. It must never accept a number not found in a snapshot, or a citation it didn't supply.
  - Gate B: "a fault flag corrupts one explanation; the verifier fails it, the Explainer retries with the violations, and the second attempt passes".
  - Guardrail "Every answer reconstructible for audit": `cmd/audit rebuild`.
  - G3 note: 80% coverage on the verifier.
- **It plugs into CC-703 and CC-704 (both merged).**
  - Implement `agent.Verifier` (`internal/agent/workflow.go`): `Verify(ctx, VerifyRequest) (StepResult, error)`.
  - `VerifyRequest.ExplanationRefs` are the explain step's `output_refs`; `EvidenceRefs` are the finding's tool_result snapshots.
  - `LLMExplainer` (`internal/agent/explain.go`):
    - Uses `FastModel` for attempts 1–2 and `StrongModel` when `req.Attempt >= 3`.
    - Renders `req.Feedback` as the `VERIFIER_FEEDBACK` section through `feedbackJSON`.
    - Retries a *malformed* answer once inside the call.
    - Stores an `ExplanationArtifact`.
  - Malformed-answer retries are the explainer's job. Ungrounded answers are this ticket's job.
- **Provenance rule (from the CC-709 G5, `tasks/hardening.md`):**
  - `artifacts.run_id` and `artifacts.produced_by` keep the *first* writer, because artifacts are content-addressed. Never use them for tenancy or provenance.
  - Which explanation belongs to which finding and run is decided only by `run_steps.output_refs` of that run's `explain/<finding id>` step. This applies to the verifier, the workflow and `cmd/audit`.
- **Gap from the CC-704 G5 (`tasks/hardening.md`):**
  - The explainer checks `cited_amounts_paise` and proposal line amounts only as integers ≥ 0.
  - **The verifier must trace every `cited_amounts_paise` value and every proposal line's debit or credit back to EVIDENCE.** This is in addition to the amounts written in the explanation text.

## Design

### What the verifier checks (`internal/agent/verify.go`, `verify_amounts.go`)

Load each artifact with `store.GetArtifact`, which verifies the hash, and check the following.

1. **Provenance and scope:**
   - Exactly one explanation ref is given, and it has kind `explanation`.
   - Its `run_id` and `finding_id` fields equal the request's run and finding.
   - Every evidence ref has kind `tool_result`. Where its `args` carry a `company`, it equals `req.Company`. Where its args carry a date range, the range lies within `req.Month`, or within the history window a check asked for. Don't fail on an arg the snapshot lacks.
   - A missing artifact or a hash mismatch is an **error** (integrity failure, the step fails), not a violation.
2. **Action:** `suggested_action` is in `SuggestedActions`.
3. **Amounts:**
   - Gather the candidates:
     - every amount in `explanation` and `action_note`;
     - every `cited_amounts_paise` value;
     - every non-zero debit or credit on a proposal line.
   - Each candidate must be within ₹1 (100 paise, inclusive) of one of:
     - an evidence amount;
     - the sum or absolute difference of two evidence amounts;
     - `finding.amount_paise`.
   - Compare absolute values, and use exact int64 arithmetic only.
   - Evidence amounts:
     - Money-valued leaves of the snapshot records the finding's evidence names. Reuse the explainer's projection (`selectRecords`), so the verifier sees what the model saw.
     - Money keys are the JSON names of the `money.Paise` fields in `internal/ledger` and `internal/evidence` (`amount`, `balance`, `debit`, `credit`, `opening`, `closing`, `net`, `taxable`, `igst`, `cgst`, `sgst`, `grand_total`, `median_amount`, …), plus any key ending in `_paise`.
     - Keep that list in one tested table, and add a test that fails if a new `money.Paise` JSON field in those packages is missing from it. Use reflection over the exported record types, so the table can't drift silently.
     - Don't treat every integer as money.
   - Cap the number of evidence amounts (for example 2,000) so the pair search stays bounded. Above the cap, check only single amounts and add a NOTE violation. Never pass silently.
4. **Text extraction (`extractAmounts`):**
   - Read amounts prefixed by `₹`, `Rs`, `Rs.` or `INR` (with or without a space), and bare Indian- or Western-grouped numbers with at least one comma (`1,18,000`, `118,000.50`).
   - Convert only with `money.ParseRupees`. No floats.
   - Up to two decimals. `₹1,180.5` is 118050 paise. `₹1,180.505` is an `amount_unparseable` violation, not a rounded value.
   - Ignore dates (`2026-08-31`, `31/08/2026`), months, GSTIN-like tokens and plain integers without a comma or a currency prefix.
   - Known limitation, write it in Notes: amounts written in words ("one lakh") or as "1.18 lakh" aren't extracted. The prompt already tells the model to use digits.
5. **Citations:**
   - Each `(doc_id, section)` must have been in the DOCUMENTS given to the model. That comes from the explanation artifact's new `document_refs` (retrieval artifacts, empty until CC-806). With none supplied, any citation is a violation.
   - The pair must also exist in `doc_chunks` with `company_id = req.Company` or `company_id IS NULL` (shared policy): `store.CitationExists`, behind a small interface so unit tests use a fake.
6. **Proposal:**
   - Balances (debits = credits, each line one-sided, at least two lines).
   - Every account is in the company's account list *as snapshotted* (see below).
   - `posting_date` lies in the run month or the next month. The ticket allows the next month for accruals. The explainer is stricter today; keep the verifier's window as the ticket states and test both edges.
7. **Model's own flag:** if verification passes but the artifact's `needs_review` is true, the verdict passes and returns `NeedsReview: true` (conservative).

### Accounts offline

The explainer reads accounts live today, so they can't be replayed.

- In `explain.go`, record the account list's source as an artifact. Snapshot the trial-balance result as a `tool_result` artifact in the explain step: use `NewSnapshots`, or put it directly with server `books`, tool `get_trial_balance` and args `{company, from, to}`.
- Store its ref in the new `ExplanationArtifact.AccountsRef` field.
- The verifier rebuilds the account set from that snapshot. It checks the snapshot's company and month and verifies its hash, and never calls ERPNext.
- An explanation without `AccountsRef` but with a proposal is a violation (`accounts_unverifiable`).
- Keep the account list identical to what the model saw. Add a test.

### Verdict and violations (the VERIFIER_FEEDBACK contract)

- **Verdict artifact:** a new artifact kind `verdict`. Add it to `ValidateArtifactKind`; the column has no CHECK constraint, so no migration is needed. Its fields:
  - `{run_id, finding_id, explanation_ref, explain_attempt, pass, violations[], checked: {amounts, citations, proposal_lines}, verifier_version}`.
- **Violation:** `{code, field, value_paise?, detail}`.
  - `code` comes from a closed set: `amount_not_in_evidence`, `amount_unparseable`, `cited_amount_not_in_evidence`, `proposal_amount_not_in_evidence`, `proposal_unbalanced`, `proposal_unknown_account`, `proposal_date_out_of_window`, `accounts_unverifiable`, `action_not_allowed`, `citation_not_supplied`, `citation_unknown`, `scope_mismatch`, `evidence_truncated`.
  - `detail` is fixed text per code, plus at most the offending number or field path.
  - It never carries evidence text, document text or model text beyond the offending amount or `doc_id`/`section`, and every string is capped. Feedback goes back into a prompt and into `run_steps.feedback`.
- **The verifier is deterministic and idempotent.** Same artifacts in, same verdict bytes out: sort violations, and add no timestamps to the verdict content.
- **`StepResult`:** the verify step is `done` with `OutputRefs: [verdict sha]` whether the verdict passes or fails.
  - Add a field `Violations json.RawMessage` (or `Feedback []byte`) to `StepResult`. Non-empty means it failed.
  - The workflow, not the verifier, decides whether to retry.

### The retry loop (`workflow.go`)

At most two retries (three explain attempts), then `needs_review`.

- **Per finding:** explain, then verify. If the verdict fails and the explain step's attempt is below 3:
  - `store.ReopenStep(ctx, explainStep, feedback)` sets the done explain step back to a restartable status and stores the violations in `run_steps.feedback`. It's guarded on the step's current `attempt`, so a stale reopen gets `ErrStaleAttempt`.
  - Re-explain: `Begin` bumps `attempt` and the explainer gets `Feedback`. Attempt 3 selects `StrongModel`.
  - Re-verify on a fresh verify-step attempt. Reopen the verify step the same way, or keep it running across the loop; pick one and document it.
- **After the third failed verification:**
  - Set the finding to `checks.StatusNeedsReview` before finishing the verify step. That ordering exists today.
  - The verify step ends `done` with the failing verdict.
- **Resume:** a crash anywhere in the loop resumes correctly with `ResumeClose`.
  - A reopened explain step with feedback re-runs with that feedback.
  - A done verify step with a passing verdict isn't re-run.
  - Test a crash between reopen and re-explain.
- **Parallelism:** unchanged (`Parallel` findings at a time). A finding's loop is sequential.
- **Budget:** every explain and verify call still goes through `stepModel` (RecordingProvider and run token cap). The verifier itself makes no model call: assert `VerifyRequest.Model` is never used, with a fake provider that fails the test if called.

### Fault flag (`fault.go`)

- **`COPILOT_FAULT`:**
  - An optional env var, read by `internal/config`.
  - Accepted values: empty or `corrupt_explanation`. Anything else is a config error.
  - Add it to `.env.example`, commented out, with a one-line warning.
- **Behaviour with `corrupt_explanation`:**
  - On attempt 1 of exactly **one** explain step per process (the first one to finish, `sync.Once`), append a fixed sentence with an invented amount (`₹9,87,654.32`) to the stored explanation *after* the explainer's own validation and *before* the artifact is written.
  - Mark the artifact `fault_injected: true`.
  - Log a warning, and put a line in the run report.
- **Hard limits:**
  - It never touches proposals, accounts, citations or anything written to ERPNext.
  - It can only make verification fail, never pass.
- **Wiring:** in `cmd/agent` only; library defaults are off.

### Report and CLI

- **`report.go`:** add a "Verification" line: `verified N of M explanations (pass rate P%), R retried, K needs_review`, plus the fault line when it applies. Update the golden files under `testdata/report/`.
- **`cmd/agent`:**
  - Wire `agent.CodeVerifier` into the workflow with its store and citation lookup.
  - `--no-explain` still skips both explaining and verifying.
- **`cmd/audit rebuild <finding-id>` (`cmd/audit/main.go`, `args.go`):**
  - Load the finding (`store.GetFinding`) and its run. Find the run's `explain/<id>` and `verify/<id>` steps through `ListSteps`, and take their artifacts from `output_refs` only.
  - Load the explain step's LLM calls (`ListLLMCalls`) and their prompt and response artifacts.
  - Print the evidence records, the prompt, the response, the explanation, the stored verdict and a **re-computed** verdict from the same artifacts.
  - Exit codes: 0 when the re-computed verdict equals the stored one byte for byte; 1 on a mismatch; 2 on a usage or store error.
  - It needs Postgres (`DATABASE_URL`) only: no ERPNext, no model, no MCP.
  - It prints what the model saw and said. That is synthetic data today. Note for CC-710 that the output must stay local.

## Tests (unit tests use fakes only: no Docker, no ERPNext, no model)

- **`TestVerifyRejectsCraftedOutputs`** is a table with one case per violation code, at least these:
  - an invented number in the text;
  - an invented `cited_amounts_paise` value;
  - an invented proposal line amount that balances (₹5,000 Dr / ₹5,000 Cr with no ₹5,000 in evidence);
  - an unbalanced entry;
  - an unknown account;
  - an account that exists only in *another* company's snapshot;
  - a posting date before the month;
  - a posting date two months later;
  - an action outside the enum;
  - a fake citation (not supplied);
  - a citation supplied but missing from `doc_chunks`;
  - a citation to another company's chunk;
  - an explanation artifact whose `run_id` or `finding_id` differs from the request (wrong run);
  - an evidence snapshot whose args name another company or month;
  - `₹1,180.505` (unparseable precision);
  - a missing evidence or explanation artifact, and a hash mismatch: each returns an error, not a pass.
- **`TestVerifyAcceptsGroundedOutputs`:**
  - exact amounts, Indian grouping (`₹1,18,000`), `Rs.1,180.50`, `INR 1180` (prefix without comma), Western grouping;
  - ±100 paise at the tolerance edge (accept), and 101 paise off (reject);
  - the sum and the difference of two evidence amounts;
  - `finding.amount_paise`;
  - a negative evidence amount matched by absolute value;
  - a date and a GSTIN in the text that are not read as amounts;
  - a proposal posting in the next month.
- **Determinism:** the same inputs give an identical verdict sha. The verifier never calls `req.Model`.
- **`TestExtractAmounts`:** a table of text-to-paise cases, including no amounts, several amounts, a trailing period, Unicode `₹` and `Rs` with no space.
- **`TestWorkflowVerifyRetry`** (fake explainer and verifier, or the real `CodeVerifier` with a fake LLM):
  - (a) attempt 1 fails, attempt 2 passes: two explain calls; the second request carries `VERIFIER_FEEDBACK` with the violation codes; the finding stays open; the report counts one retry.
  - (b) all three fail: the third explain uses `StrongModel`, the finding is `needs_review` and there's no fourth attempt.
  - (c) a crash between reopen and re-explain, then `ResumeClose`, completes correctly.
  - (d) a passing verdict on resume is not re-run.
- **`TestFaultCorruptExplanation`:**
  - With the flag, exactly one finding is corrupted on attempt 1, fails with `amount_not_in_evidence`, and passes on attempt 2.
  - Without the flag, nothing is altered.
  - An invalid flag value is a config error.
- **Integration (`-tags=integration`, testcontainers Postgres):**
  - `ReopenStep` with a stale attempt returns `ErrStaleAttempt`.
  - `CitationExists` respects company and NULL company.
  - `GetFinding`.
  - Verdict artifacts round-trip.
  - On the skeleton month with fakeerp and a fake LLM plus `COPILOT_FAULT=corrupt_explanation`, the run ends `done` with three verified explanations and one retry. `cmd/audit rebuild` on each finding exits 0. Tampering with a stored verdict row makes it exit 1.

- **Risks:**

  - The fault flag in production: off by default, rejected unless the value is exact, reported in every run report and marked in the artifact.
- No new dependencies are expected; use `regexp` and the existing `money`. Any new dependency goes in the PR summary.
