# CC-1102 · API rate limits and security pass

## Goal

Limits on how fast any user or token can call the API and the MCP servers, and a clean security scan.

## Context

- Ticket: `docs/implementation-tickets.md`, section `CC-1102`. Plan row: Phase 5, implementer, data-sensitive; graph check "429s past the limit, no 5xx; govulncheck and gosec clean".
- Quoted ticket subtasks:
  - Per-user token bucket on the JSON API with `golang.org/x/time/rate` (e.g. 5 requests a second, burst 10); at most one running close per company and two in total.
  - Per-token limits on both MCP servers; 429 with `Retry-After` when exceeded.
  - Security headers on HTML responses: CSP, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`.
  - Request body size limits; input validation on every API handler.
  - `gosec` and `govulncheck` in CI with zero high findings; check no secret is logged (grep tests on log output).
- Acceptance quoted: a load test gets 429s past the limit and no 5xx; `govulncheck ./...` and `gosec` pass.
- **Already done, don't rebuild** (`internal/web/middleware.go`): `securityHeaders` sets `X-Content-Type-Options`, `Referrer-Policy: same-origin`, CSP, `X-Frame-Options: DENY`; `limitBody` caps bodies at 1 MiB; `recoverPanics`; the one-run-per-company lock (`runsService.busy`, answers 409). The CSP stays `script-src 'self'` with vendored htmx: the ticket's "pinned htmx CDN" wording is superseded (CC-1001 owner-reviewed deviation). `gosec` already runs inside `golangci-lint` (`.golangci.yml`) and `govulncheck` in `.github/workflows/ci.yml`; both are in `make check` / `make vuln`. **Do not edit `.github/**`** (protected); the ticket's `ci.yml` line is satisfied as it stands. Report any gosec/govulncheck finding; fix it only inside the declared files.
- Requirements carried from earlier G5 reviews (`tasks/hardening.md`):
  - **CC-1006:** `Asker`'s reroute cap cannot limit `/api/ask` (the handler sends no `RunID`), so the per-user bucket is the only cap on questions and LLM spend. `/api/ask` may use a tighter bucket than the rest of the API (suggest 1 request per second, burst 3) as it costs a model call.
  - **CC-1001:** `POST /login` costs a bcrypt compare and the login CSRF cookie is free, so login is a CPU-exhaustion target: add per-IP and per-username failure limits with a lockout. Optionally require one bcrypt cost for all users (`Users.maxCost`) so the dummy-hash timing stays uniform; skip it if it needs `config/users.yaml` edits (protected).
  - **Run concurrency:** the lock is in memory per process; a global cap of 2 running closes is added in `runsService.start`.
- Design decisions (spec, pending owner review):
  - **Client IP is `r.RemoteAddr` only.** Never read `X-Forwarded-For`/`Forwarded`: a header is attacker-chosen. A configured proxy setting belongs to CC-1201 (public deploy), not here; say so in a code comment.
  - **Per-user limit key is the authenticated user name** (`principal.user.Name`), the same for cookie and bearer callers, so one user cannot double the allowance by mixing both. Applied after `authenticate` and only on `/api/*` (the htmx progress polling on pages must not be throttled). Defaults: 5/s, burst 10; ask: 1/s, burst 3. Constants in `ratelimit.go`, overridable through new optional `Options` fields (zero value = default) so tests need no sleeping. Use the server clock (`s.now`) with `Limiter.AllowN(now, 1)` / `ReserveN` so tests drive time with `fakeClock`.
  - **429 shape on the API:** `writeJSON(w, 429, {"error":"rate limit exceeded"})` plus `Retry-After: <whole seconds, at least 1>`. On HTML routes (login) `http.Error` plain text 429 with `Retry-After`.
  - **Login limiter:** failed attempts only count (a success doesn't consume). Per-IP (suggest 10 failures per minute) and per-normalised-username (lowercase, trimmed, capped to 64 bytes; suggest 5 failures per 15 minutes then lockout for the remainder). Check the limiter *before* the bcrypt compare and refuse with 429 (do not run bcrypt for a locked key). A locked username answers the same 429 whether or not the user exists, so it leaks nothing. A successful login for the same IP never clears another username's lockout.
  - **Bounded memory:** every limiter map is capped (suggest 10,000 keys) and evicts idle entries (sweep on insert or when a key's bucket is full again). An attacker rotating usernames or addresses must not grow memory without bound. Test it.
  - **Global run cap:** a new `errTooManyRuns`; `start` refuses when 2 runs are in flight (checked under `rs.mu`, same place as `busy`) with 429 + `Retry-After: 30` on the JSON API and the form route. A cap refusal creates no row (as the busy path today). The per-company 409 stays first.
  - **MCP:** one limiter per token (key = SHA-256 of the presented bearer token, hex; never the token), applied inside `RequireBearer`'s success path in `BuildHandler`, i.e. after the token verifies, so unauthenticated floods keep getting 401 and cannot fill the map. `/healthz` is exempt. Default on in `BuildHandler`: 50 requests per second, burst 100 per token (an agent run makes many tool calls; the default must not break a normal close, so pick generous and document it). `WithRateLimit(rps float64, burst int)` overrides it; `rps <= 0` disables. No change to `cmd/mcp-books` or `cmd/mcp-evidence` is needed, so both servers are limited by default. `/mcp-admin` gets the same per-token limit. 429 body is plain text "Too Many Requests" with `Retry-After`.
  - **Input validation audit:** every API handler already decodes with `DisallowUnknownFields` and rejects trailing JSON. Add what is missing: UUID path ids parse or answer 404/400 (check `{id}` handlers), `company` and `question` have length caps before use (`company` ≤ 64 bytes; leave the `question` cap to the Asker's `ErrQuestionTooLong`, but reject a body over 16 KiB for `/api/*` JSON routes with 413 via `http.MaxBytesReader`), and `Content-Type` need not be enforced. Do not change an existing status code a current test pins.
  - **No secrets in logs:** `logRequests` and the mcpkit access log never record headers, cookies, query strings or tokens. Add tests that run requests carrying a distinctive bearer token, cookie value, password and CSRF token (including a rate-limited and a failed-login request) and assert none of those strings appear in the captured log.
- New dependency: none to add. `golang.org/x/time` is already in `go.mod`; delete its placeholder line in `internal/deps/deps.go` (the file says to). Never edit `go.sum` by hand.

## Subtasks

- [ ] `internal/web/ratelimit.go`: keyed token-bucket store (`golang.org/x/time/rate`) with a key cap and idle eviction; `rateLimit(next)` middleware for `/api/*` keyed by user name, with the tighter bucket for `POST /api/ask`; 429 + `Retry-After`.
- [ ] Login failure limiter (per IP and per username) checked before bcrypt; lockout; same 429 for unknown and known users; log `event=login_locked`, never the username value beyond what `requestInfo` already holds.
- [ ] Global cap of 2 running closes in `runsService.start`, mapped to 429 + `Retry-After` on both start routes; existing 409 per company unchanged.
- [ ] `internal/mcpkit/ratelimit.go`: per-token limiter, `WithRateLimit`, default on in `BuildHandler`, `/healthz` exempt, key by token hash, bounded map.
- [ ] Body and input validation pass per "Input validation audit" above, with tests for each added check.
- [ ] Tests (names matter for acceptance):
  - `TestRateLimit*` (web): 10 requests pass, the 11th is 429 with `Retry-After`; refill after the fake clock advances; two users have separate buckets; cookie and bearer for the same user share one; `/api/ask` bucket is tighter; page routes and `/healthz` are not limited; the 429 carries the security headers.
  - `TestLoginLimit*`: per-IP and per-username lockout, locked user and unknown user answer identically, bcrypt not run while locked (count via a hook or by timing-free assertion on a fake), one IP's lockout doesn't block a different IP trying a different username, a locked username stays locked from any IP, map stays bounded under 20,000 rotating usernames.
  - `TestRunsGlobalCap`: two companies running, a third is 429 with `Retry-After` and creates no row; a slot frees when a run returns.
  - `TestLoadNo5xx` (web and mcpkit): fire at least 200 concurrent requests (goroutines against `httptest.NewServer`) at an API route and at an MCP route: every status is in {200, 401, 403, 429} (route dependent), at least one is 429, none is 5xx. `-race` clean.
  - `TestNoSecretsInLogs` (web and mcpkit) as described above.
  - mcpkit `TestRateLimit*`: over-limit 429 + `Retry-After`; a different token has its own bucket; a bad token still gets 401 and creates no limiter entry; `/healthz` exempt; `WithRateLimit(0, 0)` disables; the token string never appears in logs.

## Acceptance (human-readable)

- Past the limit the API and both MCP servers answer 429 with `Retry-After`; a hammering client never produces a 5xx.
- A normal close run's burst of MCP tool calls is not throttled by the defaults (the owner can confirm on the next browser or integration run; state the numbers chosen in the PR summary).
- `make check` (includes gosec through golangci-lint) and `make vuln` report nothing new.

## Out of scope

- A trusted-proxy / public-origin setting, HSTS, TLS and per-user company lists (CC-1201 and the owner decision recorded under CC-1006).
- Distributed (multi-process) limits: limiters and the run cap are per process, as the per-company lock is.
- `.github/**` changes, `config/users.yaml` edits, `docs/**`.
- The `Asker.routes` memory growth and shutdown notes from CC-1006 (llm-engineer, `internal/agent`).
- Running `hey`/`vegeta` by hand; the Go load tests stand in for them.

## Notes

- Never log or return a token, cookie, password or username lockout detail beyond "rate limit exceeded".
- A limiter that evicts must not let an attacker reset their own bucket by forcing eviction: evict only idle entries (bucket full) and refuse new keys over the cap with 429 rather than dropping an active one.
- Keep the in-memory limiter state out of `Users` so `SetUsers` hot-reload does not reset buckets.
