# CC-702 · MCP client tool registry

## Goal

The agent connects to both MCP servers, discovers their tools and exposes them as `llm.ToolSpec`s plus an executor. MCP-backed `BooksReader` and `EvidenceReader` let the existing checks run unchanged over MCP.

## Context

- **Ticket:** `docs/implementation-tickets.md`, section `CC-702`. Plan row: "Direct and MCP readers give identical findings".
- **Invariant, enforced by the `noerpimport` analyzer (transitively, test files included):** `internal/agent` must never import `internal/frappe`, not even through another package.
  - `internal/books` and `internal/checks/direct` import frappe, so the agent may import neither, in code or in tests.
  - The agent may import `internal/checks`, `internal/ledger`, `internal/company`, `internal/store`, `internal/money`, `internal/llm`, `internal/config`, `internal/httpx` and `internal/evidence`, which are all frappe-free since CC-601a.
  - Check with `go list -deps ./internal/agent | grep -E 'internal/(frappe|books|seed)$'`, which must print nothing.
- **Tool output types:**
  - The books tools' output structs (`books.GLEntriesOutput` and others in `internal/books/tools.go`) live in a package the agent can't import.
  - Decode `StructuredContent` into **private structs in `readers.go`** that mirror the JSON, then convert them to `ledger` types.
  - The contract is pinned by CC-505's schema goldens: `internal/books/testdata/schemas/*.json` and `internal/evidence/testdata/schemas/*.json`.
  - A test in `readers_test.go` reads those golden files (a file read, not an import) and asserts that every property in each tool's `outputSchema` maps to a JSON tag in the matching private struct, and vice versa. Schema drift then fails here.
- **Readers to implement** (the interfaces are in `internal/checks/readers.go`):
  - `MCPBooks` uses the seven books tools: `get_trial_balance`, `list_gl_entries`, `list_purchase_invoices`, `list_sales_invoices`, `list_payments`, `get_account_history` and `list_recurring_suppliers`.
  - Follow `next_cursor` until it is empty, so `GLEntries` and the other list methods return every row.
  - `MCPEvidence` uses `list_bank_lines` and returns `[]store.BankLine`. The output schema is an **array**, not an object (CC-503 behaviour, recorded in the golden).
  - Amounts are integer paise. Never decode money into a float. Use `json.Number` or `int64`; the `nofloat` analyzer applies.
  - Dates use `YYYY-MM-DD` on the wire and `time.Time` at UTC midnight inside.
- **Registry:**
  - `NewRegistry(ctx, cfg config.Config, log *slog.Logger, opts...)` connects to `cfg.BooksMCPURL` and `cfg.EvidenceMCPURL` with `mcp.NewClient` and `mcp.StreamableClientTransport`.
  - It uses an HTTP client from `httpx.New(cfg, ...)`, which must allow those hosts, and adds a `Authorization: Bearer <MCPTokenAgent>` header through a RoundTripper. Read the token only through `config.Secret`'s accessor.
  - **Never connect to `/mcp-admin`.** Refuse a configured URL whose path is not exactly `/mcp`, and never read `MCPTokenAdmin`. The `admintoken` analyzer applies.
  - Call `ListTools` on startup. Name each tool `<server>__<tool>` (`books__list_gl_entries`, `evidence__list_bank_lines`) and pass the server's `inputSchema` through unchanged as `llm.ToolSpec.InputSchema`.
  - Build an **allowlist** of the discovered tools and keep only those annotated read-only. Refuse to start if any tool lacks `readOnlyHint: true`. Log the final tool list with slog: one JSON line naming every tool.
  - `Specs() []llm.ToolSpec`, sorted by name.
  - `Execute(ctx, call llm.ToolCall) llm.ToolResultBlock`:
    - An unknown or unlisted name, an MCP tool error (`IsError`), a transport error or a timeout all come back as an error result (`IsError: true`) with short fixed text. Never panic, and never return raw transport error text that might echo the URL or the token.
    - The timeout is 10 s per call through `context.WithTimeout`.
  - Reconnect once on a transport failure before reporting the error.
  - `Close()` closes both sessions.
  - Readers and `Execute` share one session per server.
- **Unit tests (`internal/agent`, no Docker, no network):**
  - Run both real servers in-process behind `httptest.NewServer(mcpkit.BuildHandler(...))`, as CC-505's contract tests do.
  - **The agent's tests cannot import `books`.** Run the registry against small in-test MCP servers built with the SDK (`mcp.NewServer` plus `mcp.AddTool`) that mimic the two servers' tool names and schemas. That is enough for registry behaviour: prefixing, allowlist, refusal of a non-read-only tool, errors returned as results, timeouts, 401 handling and the refused `/mcp-admin` path.
  - For decoding, feed recorded `StructuredContent` JSON from `internal/agent/testdata/` through the readers.
- **Parity tests (`internal/checks/direct`, which may import frappe, books and agent):**
  - `parity_test.go`, `TestParityBooks`, unit test:
    - Build one fake ERPNext with `httptest`. Reuse or extend the `fakeERP` in `internal/checks/direct/books_test.go`, which is in the same package.
    - Populate it with a synthetic month: purchase, sales and payment entries, GL rows across more than one page, and a recurring supplier history.
    - Read it twice: through `direct.Books` (frappe client), and through `agent.MCPBooks` → books MCP server (`books.RegisterTools` over a frappe client pointed at the same fake) → fake.
    - Every `BooksReader` method must return deep-equal results both ways.
  - `parity_integration_test.go`, `TestParityFindings`, behind `//go:build integration`:
    - Start Postgres with testcontainers, as `internal/store/store_integration_test.go` does, and load synthetic bank lines.
    - Run `checks.Runner` with the existing checks (bank reconciliation, CC-602) once with `direct.Books` + `checks.DirectEvidence`, and once with `agent.MCPBooks` + `agent.MCPEvidence` over in-process servers.
    - Findings must be identical, apart from IDs and timestamps that differ by construction (compare with those fields cleared).
    - Include the three planted bank charges.
  - **Data:** synthetic only. Use the seeded company IDs (`sharma` and the like) and checksum-valid made-up GSTINs. Never use real company data.
- **Hardening notes that apply** (`tasks/hardening.md`, "Notes for later specs"):
  - Build every HTTP client through `internal/httpx`, and read secrets only through `config.Secret`.
  - Books tool results carry untrusted ERPNext free text: `remarks`, `description`, `against`, `bill_no`, `reference_no` and the party names.
    - This registry passes results straight through, and fencing them belongs to CC-706/CC-1103. Don't add fencing here.
    - **Don't log tool result content.** Log tool names, durations and error classes only.
- **No new dependencies.** The MCP SDK is already in `go.mod`.

## Subtasks

- [ ] `internal/agent/registry.go`: connect, discover, allowlist, prefix, `Specs`, `Execute`, reconnect once, timeout, startup log, `Close`.
- [ ] `internal/agent/readers.go`: `MCPBooks` and `MCPEvidence` over the registry's sessions, private wire structs, conversion to `ledger` and `store` types, cursor paging.
- [ ] `registry_test.go`: prefixing and sorted specs; a non-read-only tool refuses startup; a URL path other than `/mcp` (such as `/mcp-admin`) is refused; an unknown tool, a tool error, a timeout and a 401 each come back as `IsError` results; the startup log names every tool and holds no token.
- [ ] `readers_test.go`: decoding from `testdata/`; schema-golden field coverage both ways; paging across `next_cursor`; paise exactness (no float path).
- [ ] `internal/checks/direct/parity_test.go`: `TestParityBooks`.
- [ ] `internal/checks/direct/parity_integration_test.go`: `TestParityFindings`.

## Acceptance (human-readable)

- The agent's tool list is logged once on startup and contains the books and evidence tools only, with no admin tool.
- Direct and MCP readers give identical results (unit) and identical findings (integration).
- `go list -deps ./internal/agent` contains no `internal/frappe`, `internal/books` or `internal/seed`, and `go run ./gates/cmd/lint ./...` passes.
