# UI-07 · Finding detail rework with side-by-side evidence and Propose entry

## Goal

The finding page reads like a reviewer's workspace: facts and verification up top, the explanation and citations, evidence tables beside the proposed journal entry, the investigation trail, and clear buttons for what the user's role may do, with every control and check on the server unchanged.

## Context

- Ticket: `tasks/frontend-plan.md` sections 4 and 10 (`UI-07`).
- Routes, handlers, roles, CSRF and status codes do not change (`routes.go`, `approvals.go` and `internal/approvals/**` are untouched; the last acceptance line checks). The page still posts to `/findings/{id}/accept`, `/findings/{id}/dismiss` and `/findings/{id}/proposals`; the server decides who may.
- **Hooks that existing tests rely on must survive.** Run `go test ./internal/web/ -run Finding -v` and read `finding_test.go` for the selectors it uses before editing. At least: sections with ids `#header`, `#review`, `#explanation`, `#citations`, `#evidence`, `#trail`, `#proposal`, `#actions`; `data-severity` on the header; `dd.type`, `dd.severity`, `dd.amount`, `dd.status`; `.explanation` and `.action` paragraphs; the `Needs review` banner reasons; citation `<details>` entries; evidence blocks with `.args`, `.ids`, `.note` and `table.evidence` with the `Source` column and its `rel="noopener noreferrer" target="_blank"` links; trail `<li>` lines; proposal `.balanced`, `.error` (unbalanced), `tr.totals`; forms with `action` ending `/accept`, `/dismiss` and `/proposals`, hidden `csrf_token`, `textarea[name=reason]` with `required` and `maxlength="500"`; the `Status:` line for users who cannot decide. Where a component's markup differs from today's, add the old class or id as an extra hook (`Cell.Class`, `Attrs`). If a test asserts exact old visible text or markup that changes only cosmetically, adapt the component output first and the assertion only if unavoidable; list every changed assertion in the PR summary. No assertion about behaviour, escaping, links or roles is weakened or removed.
- ERPNext links come from the existing page data and keep `rel="noopener noreferrer" target="_blank"`; nothing new is linked.
- Escaping and CSP as in UI-01/02. All finding, evidence and explanation text is data: escaped.
- Shared files are owned by UI-03a: do not edit `ui*.templ`, `ui.go`, `components.css`, `app.css` or `design_test.go`. Page rules go in `static/css/finding.css`.

## Layout

- `PageHeader`: the finding title; subtitle "Company Month · back to findings"; header facts in a `Facts` list (Type, Severity as `SeverityBadge`, Amount right-aligned and tabular, Status as `StatusChip`, Verified as `VerifiedBadge`); the "Back to findings" link stays.
- Needs-review banner: a `Card` with tone `warn`, same text and reasons.
- Explanation `Card`: the text, then "Suggested action" as a distinct labelled line. Empty: the existing "no explanation yet" text inside an `EmptyState`-style paragraph.
- Citations `Card`: each citation a `<details>` (keep) showing document and section; the existing "snippet not stored on the finding" note stays until UI-11 links to the documents browser.
- **Evidence and proposal side by side:** a wrapping two-column grid (`finding.css`: evidence left, proposal right; one column under 56rem). Left: evidence blocks as `DataTable`s (heading, args, ids, note, "n more not shown" kept). Right: when a proposal exists, a `Card` "Proposed entry" with its status chip, maker, posting date, remark, the lines table (account, debit, credit, totals row), a Balanced or Unbalanced notice with the difference, and the ERPNext journal entry link. When there is none, the right column shows an empty-state card "No entry proposed yet" with the Propose entry button for users who may create one.
- Investigation trail: a `Timeline` (call as title, args and row count as detail), keeping the `<li>` hooks.
- **Actions `Card`** (`#actions`):
  - **Propose entry** (shown when `Actions.CreateButton` and `CanDecide`, as today): a primary `Button` in a POST form to `/findings/{id}/proposals` with the CSRF token (the existing "Create proposal" form, relabelled).
  - **Mark accepted**: secondary `Button` in its POST form.
  - **Dismiss**: a danger `OpenDialogButton` opening a `ConfirmModal` whose form posts to `/findings/{id}/dismiss`; the dialog's `Extra` slot holds the required reason `TextareaField` (`name=reason`, `required`, `maxlength=500`, `rows=3`, prefilled with `Actions.Reason` after a failed post); the dialog body restates the finding title and amount. The modal is in the markup so `dialog form[action$=/dismiss] textarea[name=reason]` exists for tests and a user without script cannot dismiss by accident but still reaches the same server rule.
  - Users who cannot decide see the status line as today, without buttons. A failed action shows its error as an alert at the top of the card.

## Acceptance (human-readable)

- A maker opens a bank-charge finding, sees the evidence next to the entry that would fix it, clicks Propose entry, and sees the proposal appear; a dismissal asks for a reason in a dialog.
- A viewer or checker sees the same facts, evidence and proposal without action buttons.
- Every existing test passes; the PR summary lists any assertion that had to change and why.

## Out of scope
