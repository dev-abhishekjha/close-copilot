# CC-706 · Exceptions investigator agent

## Goal

A bounded, tool-using agent explains each `unmatched_bank_line` finding the rules could not classify (for example a gateway settlement paid out net of fees), using only read tools from the books and evidence servers, and finishes through `emit_resolution`.

## Context

- Ticket: `docs/implementation-tickets.md`, section `CC-706` (don't open it; everything needed is quoted here).
- Plan row: Phase 2, llm-engineer, data-sensitive. Check: "Registry test: allowlist has no retrieval tool; 0 calls outside it". Next ticket CC-1103 depends on this one.
- **What it does.** The path to an answer isn't known in advance, so this is a loop: call the model with the tool specs, execute the read tools it requests, feed results back, stop when it calls `emit_resolution`. Example: a ₹97,640 deposit with narration "PG SETTL 0915". The agent lists gateway receipts in the clearing account for the days before (₹1,00,000 in total), sees the ₹2,360 difference (2% fee plus 18% GST on it), and proposes: debit Bank ₹97,640, debit Gateway Fees ₹2,000, debit Input GST ₹360, credit Payment Gateway Clearing ₹1,00,000.
- **Allowlist.** Exactly these registry tools (names are `server__tool`): `books__get_trial_balance`, `books__list_gl_entries`, `books__list_purchase_invoices`, `books__list_sales_invoices`, `books__list_payments`, `books__get_account_history`, `books__list_recurring_suppliers`, `evidence__list_bank_lines`, `evidence__list_gstr2b_entries`, plus the finishing tool `emit_resolution`. No `search_documents`, no `/mcp-admin` tool, no other name. The registry's `Specs()` returns every discovered tool, so the investigator filters by this fixed name set and refuses any call outside it with `MsgUnknownTool` (counted, never executed). A registry test asserts the set contains no retrieval tool and no admin tool, and that a registry offering `evidence__search_documents` still yields no such spec.
- **Limits per item** (breach marks the finding `needs_review` with the partial trail, never fails the run): at most 8 tool calls, 90 seconds, 30,000 tokens (input + output, from `llm.Response.Usage`). A refused or unknown-tool call counts as a call.
- **`emit_resolution` schema:** `resolution_type` (enum `gateway_settlement`, `timing_difference`, `unrecorded_charge`, `unknown`), `explanation`, `evidence_ids[]`, optional `proposal` (same balanced-journal shape as the explainer's `proposal`; reuse its validator, `explain.go:826`).
- **Verifier.** Run the existing `CodeVerifier` on the result, unchanged. It reads an `ExplanationArtifact` (`explain.go:255`) and traces amounts against the finding's evidence, so: (1) store the result as an `ExplanationArtifact` (`SuggestedAction` `investigate` or `book_entry` as the proposal warrants; `AccountsRef` from a `books__get_trial_balance` snapshot taken for the run, as the explainer does at `explain.go:291`); (2) store each tool result the agent saw as a `tool_result` artifact and append it to the finding's evidence as `store.EvidenceRef`, so the verifier can ground amounts in what the agent actually read. Store the resolution type in the finding's keys as `"resolution"` (CC-902 scores it against `expected_resolution`).
- **Tool results are projected before the model sees them** (free text is where injected instructions hide). Drop: `remarks`, `description` (invoice lines), `against`, `bill_no`, `reference_no`, `supplier_name`, `customer_name`, `party_name`. Cap bank `narration` at 120 runes and wrap it in an unforgeable fence (as the explainer fences JSON sections, `explain.go:738`). Tool-error text is fixed per class, so it is not free text.
- **Quoted G5 notes to apply here** (from `tasks/hardening.md`):
  - Fence or drop the ERPNext free-text fields above; cap `Finding.Keys` with `capStrings` (`explain.go:699`) before it goes into a prompt; if ACCOUNTS is placed in a system prompt, drop names longer than `maxAccountRunes` or outside the safe character set, cap the list at 500, and label it as data.
  - Wrap the investigator's provider with `WrapRedacting` (`redact.go:374`) outermost, inside the recording wrapper, so stored prompts stay token-only. `Workflow.stepModel` (`workflow.go:1099`) doesn't apply it today; the investigator step must (build a `Redactor` as the explainer path does, with the fail-closed `PSEUDONYM_KEY` check `cmd/agent` already enforces).
  - The explainer/investigator prompt must say to put ₹ before every amount, so the verifier reads them all.
  - The registry turns every tool error into `MsgToolError`, so the model never sees the `out_of_scope` reason. Decide whether to pass that one fixed class through; it holds only the run's own window and a capped echo. If you change it, do it in the investigator (not `registry.go`, which is not in `files`); otherwise say in Notes that you left it.
  - Tool `Description`s come from first-party servers and go to the model unchanged; acceptable, note it.
- **Scope.** Every call runs under the run's scope context (`scopeRun`, `workflow.go:460`; `WithRunScope`, `registry.go:626`), so another company or month returns a tool error (CC-506). The scope window ends the month after the run month; don't widen it.
- **Workflow wiring.** Today the workflow records `investigate/close` as skipped with `reasonInvestigate` (`workflow.go:587`, `:109`). Replace that with: for each `unmatched_bank_line` finding (in `sortFindings` order, bounded by the workflow's existing `parallel()`), one `investigate/<finding id>` step (`store.StepKindInvestigate`), then a verify step. Keep a single `investigate/close` skipped step only when there are no such findings or no model. The step is resumable like explain/verify (see `drive` and the begin/finish helpers). A breach, an unknown-tool refusal burst or a failed verification leaves the finding `needs_review`; the run stays `done`/`partial` as today.
- **Finding fields used** (`store.Finding`, `runs.go:78`): `Type`, `Keys` (`bank_txn_id`, optional `hint=gateway`, now also `resolution`), `Evidence []EvidenceRef{Server, Tool, Args, IDs, Artifact}`, `Status` (`open | needs_review | accepted | dismissed`), `Verified`.
- **Shared HTTP/MCP specs:** MCP tool inputs (all amounts paise, dates `YYYY-MM-DD`): `list_bank_lines(company, from_date, to_date, min_amount?)`, `list_gl_entries(company, from_date, to_date, account?, party?, cursor?)`, `get_account_history(company, account, months)`, and the others named above. The agent's token is bound to one company and month; out-of-scope arguments return a tool error.
