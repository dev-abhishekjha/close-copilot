# CC-1007 · Dedicated ERPNext posting key for the admin route

## Goal

The only write path to ERPNext (`post_approved_journal_entry` on `/mcp-admin`) runs on its own ERPNext user and key, with a role that can create and submit Journal Entries and nothing else, so the shared `copilot-bot` key has no write path through Close Copilot.

## Context

- Not in `docs/implementation-tickets.md`. Source: owner decision 2026-10-14, recorded in `tasks/hardening.md` ("Dedicated ERPNext posting key"; CC-504b follow-ups: "A dedicated posting key would narrow it; that is a new key and needs the owner"; the open decision "resolve before CC-1004 builds on the write path"). It blocks CC-1004 (`specs/CC-1004.md`, now `depends_on` this ticket). Plan context: guardrail row "Write-capable MCP tools stay out of the answer path".
- Today: `cmd/mcp-books/main.go` `booksDeps` builds one `frappe.Client` from `ERP_API_KEY`/`ERP_API_SECRET` (the `copilot-bot@example.com` user, role Accounts User) and `httpRoutes` hands that same client to the read tools and to `books.RegisterAdminTools`. `deploy/erpnext/api-users.sh` (CC-201) creates the bot and the seeder's Administrator keys and writes `ERP_BASE_URL`, `ERP_SITE`, `ERP_API_KEY`, `ERP_API_SECRET`, `ERP_SEED_API_KEY`, `ERP_SEED_API_SECRET` to `tmp/erp-keys.env` (git-ignored, mode 600). It is idempotent, supports `--rotate`, never prints a secret, refuses xtrace, passes values to `bench execute` as Python literals (JSON of strings, integers and `None` only), and checks a user's `enabled`, `user_type` and exact role set.
- The admin tool's ERPNext calls (CC-504b, `internal/books/admin.go`, protected, **do not edit**): `frappe.List` and `frappe.Get` on Journal Entry (lookup by `copilot_ext_id`, re-check after submit), `frappe.Insert` of a Journal Entry with child rows `accounts`, `frappe.Submit`. It needs nothing else.
- Decisions made in this spec (flag any you disagree with in the PR summary):
  - **Env vars:** `ERP_POST_API_KEY`, `ERP_POST_API_SECRET`. Same `Secret` handling and masking as the bot pair. Neither is in the `cli.Main` required list (stdio mode and other binaries don't need them); `httpRoutes` fails closed instead (below).
  - **Role:** a custom Role named `Copilot Poster` with permissions on Journal Entry only: `read, write, create, submit` (no `cancel`, `delete`, `amend`, `export`, `share`, `report`, `print`, `email`). **How to grant them matters:** in Frappe, once any Custom DocPerm row exists for a DocType, only Custom DocPerm rows apply and the standard rows are ignored, so inserting a Custom DocPerm document directly would strip Journal Entry rights from Accounts User, Accounts Manager and every other role on the shared ERPNext. Use `frappe.permissions.add_permission("Journal Entry", "Copilot Poster", 0)` then `frappe.permissions.update_permission_property("Journal Entry", "Copilot Poster", 0, <flag>, 1)` for each wanted flag, then set every forbidden flag to 0 the same way (`export`, `share`, `print`, `email`, `report`, `import`, `delete`, `cancel`, `amend`: this ERPNext's Custom DocPerm defaults to `read=1` and `export=1`, so a row from `add_permission` carries `export` until you clear it) and verify the exact set; `update_permission_property` does nothing when the row is missing, so the verification is what proves the grant (they call `setup_custom_perms`, which copies the standard rows first); never insert a `Custom DocPerm` document. The same rule applies to any extra `read` DocPerm on a master DocType. `user copilot-poster@example.com`: enabled, System User, exactly that one role, no User Permissions. If ERPNext refuses a post for this role because a Link target or a validation needs another DocType permission, add the **smallest** extra `read` DocPerm (for example Account, Company, Fiscal Year, Cost Center), name each one in the script's header comment and the PR summary, and re-run; if the posting needs more than read access on a handful of master DocTypes, or any write outside Journal Entry (and its child table), **stop and report to the owner**.
  - **What "refused on reads" means:** the admin tool must read Journal Entries (ext-ID lookup), so JE read stays. The posting key must be refused for reads of other transactional DocTypes (`Sales Invoice`, `Purchase Invoice`, `Payment Entry`, `GL Entry`, `Bank Transaction`) and for any insert, update, submit or delete outside Journal Entry (`Sales Invoice`, `Payment Entry`, `Account`, cancel or delete of a Journal Entry).
  - **"copilot-bot is refused on the admin tool"** is enforced where this repo can enforce it: `/mcp-admin`'s ERPNext client never uses the bot key, and the server refuses to start when the posting key is missing, or equals the bot key, or equals the seeder key. This ticket does **not** change the bot's role (Accounts User, which can still create Journal Entries in ERPNext itself). Whether to narrow the bot to a read-only role is an owner decision and a separate follow-up; the integration test records ERPNext's answer to a bot-key Journal Entry insert in its log, without asserting on it, and the PR summary reports it.
  - Local development only: like the seeder keys, the posting key pair goes to `tmp/erp-keys.env`. Production key handling is CC-1201.
- Quoted conventions: secrets come only from environment variables; `.env.example` lists every variable; never read `.env`; unit tests never call ERPNext, Docker or a real model; integration tests carry the `integration` build tag; new dependencies go in the spec notes.
