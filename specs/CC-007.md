# CC-007 · Score a clean month's expected and investigation findings as correct

## Goal

A clean control month stops counting a finding as a false alarm when that month's own ground truth lists it as an `expected` or `investigations` item, so `clean.false_alarms==0` can hold on `suite-skeleton`.

## Context

- Ticket: `tasks/hardening.md`, section `CC-007` (not in `docs/implementation-tickets.md`). It comes from the Gate B run of 2026-10-11.
- Shared specs it relies on: CC-902's scoring rules (`specs/CC-902.md` lines 57 to 96) and CC-306's ground truth (`specs/CC-306.md` line 54).
- Plan row: Phase 1, eval-engineer, regulated, `human_review`. Check: gateway settlement findings in the clean month are not false alarms; an unrelated clean-month finding still is.
- What happened (`results/suite-skeleton/20261011T095154Z/score.md`): recall 3/3, precision 5/8, clean-month false alarms 3. The clean month `sharma 2026-08` raised three `unmatched_bank_line` findings with keys `bank_txn_id` and `hint=gateway`: `BNK-20260811-002`, `BNK-20260818-002`, `BNK-20260825-002`.
- Why the detector and the seeder are right: CC-602 raises a bank line whose narration starts with `PG SETTL` as `unmatched_bank_line` with `hint=gateway`. The books never record gateway settlements (`internal/seed/books.go` `BookDocType` returns "" for `gateway_settlement`). `internal/seed/truth.go` lists every settlement under `investigations` with `expected_resolution: "gateway_settlement"`, and `evals/scenarios/suite-skeleton/ground_truth/sharma-2026-08.json` has them as X01 to X03 (`"clean": true`, `"planted": []`).
- Why the scorer is wrong: in `ScoreMonths` the control-month branch counts every scored finding as a `clean_month` false alarm and skips grading the month's investigations ("not graded there"). The truth says the findings are expected.
- Existing rules that stay: a clean month's truth has no planted items (`LoadGroundTruth` rejects one that has); unscored types (`variance`, `unmatched_ledger_entry`) are listed but never false alarms; each truth item matches at most one finding and each finding at most one item; a second finding for a matched item is a false alarm.

## Subtasks

- [ ] In the control-month branch of `ScoreMonths`, run `matchMonth(m.Truth, scored)`. A finding with a target (`byFind[fi] >= 0`) is correct for its type (`ts(f.Type).Correct++`). A finding with no target stays a `ReasonCleanMonth` false alarm (`Clean.FalseAlarms++`, `ts(f.Type).FalseAlarms++`, one `falseAlarm(...)` entry, in the existing sorted order). **Every unmatched clean-month finding, a duplicate included, keeps reason `ReasonCleanMonth`; never `ReasonNoMatch` or `ReasonDuplicate`.** `Compare` (`internal/evals/baseline.go:413-419`) reports a clean-month regression only for that reason, so a different reason would silently stop `--compare` from failing. Keep the control-month finding loop separate from the normal-month one (score.go:763-777).
- [ ] Grade the control month's investigations the way a normal month does (`surfaced`, `not_surfaced`, `unmatchable`), so the report lists them. Reuse the code, not a copy: factor the shared investigation and item loops into a helper if that is the smaller change.
- [ ] `Clean.Findings` stays the number of scored findings in control months; `Clean.FalseAlarms` counts only unmatched ones. Planted items cannot exist in a clean month; if `matchMonth` returns a planted target there, that is already rejected at load time, so do not add handling for it.
- [ ] Unit tests in `score_test.go`: (a) a clean month with one finding matching an investigation item: no false alarm, `Clean.FalseAlarms == 0`, `Types[unmatched_bank_line].Correct == 1`, the investigation is `surfaced`; (b) the same finding with no truth item: one `clean_month` false alarm; (c) a finding matching an `expected` item: not a false alarm; (d) two findings with the same keys for one investigation item: the first is correct, the second a `clean_month` false alarm; (e) a clean-month `unmatched_bank_line` whose keys differ from every item: false alarm; (f) an unscored type is unchanged; (g) `--require clean.false_alarms==0` passes in (a) and fails in (b); (h) `Compare` returns a `CompareCleanFalseAlarm` entry for (b) and (d) and none for (a), and `Clean.FalseAlarms` equals the number of `ReasonCleanMonth` false alarms in every case. Name every new test `TestScoreClean...` (for example `TestScoreCleanInvestigationSurfaced`, `TestScoreCleanDuplicate`), so the second acceptance command runs them.
- [ ] Add a `testdata/score` run folder plus a golden report only if a test needs a full report; otherwise use `monthIn` helpers. Existing golden files must not change.

- [ ] Update the two comments that the change makes wrong: `ReasonCleanMonth` at `score.go:41` ("any scored finding in the clean control month") and the control-branch comment ("its investigations, if any, are not graded there"). Leave `baseline.go:326` for a later ticket.
