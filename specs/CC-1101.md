# CC-1101 · Resilience and fault injection

## Goal

The system degrades predictably when a dependency is slow or down, and injected faults prove it.

## Context

- Ticket: docs/implementation-tickets.md, section `CC-1101`. Plan row: Phase 5, IMP, standard; gate-run check "Precision holds with 10% injected errors".
- Ticket text (quoted):
  - Circuit breaker around the frappe client: open after 5 consecutive failures, half-open after 30 s. `github.com/sony/gobreaker` or a small hand-written one.
  - `FAULTS="erp:latency=2s:rate=0.2,erp:error=503:rate=0.1"` parsed into an `http.RoundTripper` wrapper used only in tests and eval runs.
  - Timeouts end to end: ERPNext 15 s, MCP tool calls 10 s, LLM 60 s, run 10 min; each context-cancelled path tested.
  - Workflow: a failed check marks the run `partial` and names the check; other checks still finish.
  - Eval under faults: run the suite with 10% injected errors and record the scores beside the baseline.
  - A run that loses a dependency ends `partial` or `failed` with a clear reason and never reports findings it couldn't verify.
- Acceptance (ticket): with ERPNext stopped, a run ends `failed` within 30 seconds with "ERPNext unavailable". With 10% injected errors, precision stays at baseline (no invented findings); any recall loss is listed in `docs/benchmarks.md`.
- What exists already (do not rebuild): per-request ERPNext timeout 15 s (`requestTimeout`), whole-request `DefaultDeadline` 60 s with GET retries on 429/502/503/504 and transport errors, MCP tool call `DefaultCallTimeout` 10 s (`internal/agent/registry.go:62`), run `DefaultRunTimeout` 10 min (`internal/agent/workflow.go:111`), Anthropic call timeout 60 s (`internal/llm/anthropic.go:22`). The claude-cli default is 120 s (`internal/llm/claudecli.go:23`); `internal/llm` is not in this spec's files, so record that gap in Notes rather than change it.
- Current workflow behaviour: `stages` (`internal/agent/workflow.go:615`) returns the first `runCheck` error, so one failed check fails the run. Preflight (`preflightReason`, line 882) already refuses a run when books or evidence are unreachable, with the reason `books are unreachable: <err>`; the run then ends `failed` wrapping `ErrRunFailed`.
- The agent never imports `internal/frappe` (CLAUDE.md invariant). ERPNext failures reach the agent as MCP tool errors; the breaker lives in the frappe client used by `cmd/mcp-books` (`cmd/mcp-books/main.go:172`).
- Egress: HTTP clients are built through `internal/httpx` (`httpx.New(cfg, ...)`), enforced by the `egress` analyzer. The fault transport wraps an existing `http.RoundTripper` and builds no client itself.
- Env var to add to `.env.example`: `FAULTS` (testing only, never in production; empty means off). Spec syntax: comma-separated `target:kind=value:rate=r`; target `erp`; kinds `latency=<duration>` and `error=<http status>`; `rate` in (0,1].
- Money, dates, logging, error-wrapping conventions: CLAUDE.md "Conventions".

## Subtasks

- [ ] `internal/frappe/breaker.go`: hand-written breaker (no new dependency). Closed → open after 5 consecutive failures (transport errors and 5xx count; 4xx and context cancellation by the caller do not); open fails fast with `ErrUnavailable` and no request; after 30 s one half-open probe: success closes, failure reopens. Clock injectable for tests. Safe for concurrent use.
- [ ] Wire it into `Client.request` so a fast failure carries the text `ERPNext unavailable`. Write calls go through it too.
- [ ] `internal/faults`: `Parse(string) ([]Spec, error)` (rejects unknown target, kind, bad rate, bad duration), `Transport` (an `http.RoundTripper` wrapper with seeded randomness, injectable sleep and clock) and `FromEnv`. It never turns on from config files, only from `FAULTS` or `--faults`.
- [ ] Timeouts: confirm each of ERPNext 15 s, MCP call 10 s, LLM 60 s, run 10 min ends on context cancellation with a clear error. Add the missing tests in packages this spec owns (frappe, agent); name any gap in a package it does not own in Notes.
- [ ] Workflow: a check that errors (not cancellation, not a store failure) ends its step `failed` with reason `check <name> failed: ...`, the remaining checks still run, no finding from the failed check exists, and the run ends `partial` with a note naming the check. A run whose preflight cannot reach books or evidence stays `failed`, and its reason contains `ERPNext unavailable` when the cause is the breaker. Never explain or report a finding the run could not verify.
- [ ] `eval run --faults ... --seed N`: run the suite with faults through the replay path, score it, and write the scores for faults off and on, plus any recall lost, to `evals/faults/results.md` (not `evals/baseline.json`, which stays untouched).
- [ ] Add `FAULTS` to `.env.example` with the testing-only warning.

## Acceptance (human-readable)

- With a fake ERPNext that refuses every connection, a run ends `failed` in under 30 s with "ERPNext unavailable" (unit test with a fake clock or short breaker settings; no Docker).
- After 5 consecutive failures the next call fails without a request; after the cooldown one probe is sent.
- A failing check leaves a `partial` run that names the check and still stores the other checks' findings.
- At `erp:error=503:rate=0.1` the replayed suite has no false alarms and no unauthorized writes (precision at baseline, no invented findings). Recall loss is allowed and is written to `evals/faults/results.md`.
- The orchestrator copies the recall-loss lines into `docs/benchmarks.md` after the owner approves (`docs/**` is protected; the worker does not edit it).

## Out of scope

- Changing `internal/llm` timeouts (claude-cli default 120 s), the MCP registry or the books server.
- Faults on the LLM or MCP transports; only `erp` is a target for now.
- Live fault runs against ERPNext (needs the lock; replay covers the scoring claim).
- Editing `evals/baseline.json` or `docs/benchmarks.md`.

## Notes

- No new dependency: the breaker is hand-written, so `go.mod` is untouched.
- Precision "at baseline" means no false findings beyond the baseline's; the acceptance command asserts zero false alarms; if the suite baseline itself has false alarms, compare to the baseline's count instead.
- Faults must be impossible to enable by accident in the product binaries: `cmd/agent` and the MCP servers must not read `FAULTS`; only `cmd/eval` and tests do.
- Tier-2 `verified_rate` is unstable on identical code (see memory); if G4-tier2 fails only on that, run a control on `main` before blaming this ticket.
