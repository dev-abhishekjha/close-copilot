# CC-504b · Admin tool: post an approved journal entry

## Goal

The only write tool posts a journal entry that a human approved, exactly once.

## Context

- Ticket: docs/implementation-tickets.md, section `CC-504b`. Plan row: Phase 4, INT, regulated, `human_review: true`, ERPNext lock; check "Unapproved or self-approved proposals refused; second call doesn't double-post". Guardrail row "Write-capable MCP tools stay out of the answer path": the tool exists only at `/mcp-admin` with its own token, takes only a proposal ID, reads the lines from Postgres; checker != maker; G5 "agent token gets 401"; G6 for every change to `admin.go`.
- Quoted from the ticket: the tool "takes nothing but a proposal ID. The entry's lines come from the approved row in Postgres, never from the caller, so even a compromised caller can't post an arbitrary entry." `internal/books/admin.go` is a protected path.
- Quoted from the shared spec, `journal_proposals`: `id uuid PK, finding_id uuid, company_id text NOT NULL, payload jsonb (posting_date, lines[{account, debit, credit}], remark), status text NOT NULL -- proposed|approved|posted|rejected, maker text NOT NULL, checker text, reason text, erp_name text, created_at, decided_at, posted_at`. Amounts in `payload` are `money.Paise` (int64 paise).
- `audit_log` is append-only and every tool call writes one row via `mcpkit.AddTool` (CC-504a). The admin server has no audit today: `cmd/mcp-books/main.go` builds `adminServer` with no `EnableAudit` and no tools.
- External-ID field: `seed.ExtIDField = "copilot_ext_id"` is a Custom Field on Journal Entry (created by the CC-303 bootstrap). Set it to the proposal ID; it is how a half-finished post is recognised and how the eval's unauthorized-writes check (a later ticket) finds Journal Entries with no posted proposal.

  - `internal/evals/writes.go` pins strings about "admin route is not audited until CC-504b" in `score_test.go` and `report_test.go`. **Do not edit `internal/evals/**`**; the eval-side extension is a follow-up ticket (Notes).

  - Input struct has exactly one field, `proposal_id` (UUID string), and the schema forbids additional properties. Output: `{proposal_id, erp_name, status: "posted", already_posted bool}`. Annotations: not read-only, `DestructiveHint` false, `IdempotentHint` true.
  - Inside `WithProposalLock`, in this order:
    0. A `proposal_id` that isn't a UUID is refused as `invalid_proposal_id` before any lock; a missing row is `not_found`.
    1. `erp_name` already set: return it with `already_posted: true`, no ERPNext call. (A row with `erp_name` but a status other than `posted` is repaired to `posted` only if `status = approved` and the step 3 checker check also passes; any other status with an `erp_name` is an error.)
    2. Require `status = approved`; else refuse (`proposed`, `rejected` and `posted` without `erp_name` all refuse).
    3. Require `checker` set, non-blank, and different from `maker` after `strings.TrimSpace` and case folding; require `decided_at` set. Refuse otherwise.
    4. Validate the payload: `posting_date` is `YYYY-MM-DD`; at least two lines; every line has exactly one of debit or credit, positive; total debit equals total credit, both non-zero (int64 paise, overflow-checked); `company_id` resolves through `Companies`. Refuse otherwise, without any ERPNext call.
    5. Look for an existing Journal Entry with `copilot_ext_id = <proposal id>` using `frappe.List` with `Limit: 2` (any docstatus). More than one match, or a match with docstatus 2 (cancelled), is an error for a human (`erp_conflict`), with no write. For a single match, `Get` it and require: exactly `len(payload.lines)` rows; the multiset of `(account, debit paise, credit paise)` equals the payload's (order-independent; amounts decoded as `json.Number` and converted with `money.FromJSONNumber`, never float); each row has exactly one of debit or credit non-zero; `voucher_type` is `Journal Entry`; `company` equals the resolved ERP name; `posting_date` equal. Any mismatch returns `erp_mismatch` with no write. Then: submitted: record it; draft: submit it. None found: `frappe.Insert` a draft (`voucher_type`, `company`, `posting_date`, `user_remark`, `copilot_ext_id`, `accounts[...]` with rupee strings from `Paise.Rupees()`; see `seed.amount` at `internal/seed/books.go:536`), then `frappe.Submit`. After `Submit`, check the returned document against the same rules before `save`. A mismatch after `Submit` returns `erp_mismatch`, does not `save`, and logs `proposal_id` and `erp_name` at Error for a human; the row stays `approved` and a retry refuses with `erp_mismatch` again.
    6. `save` the row with `status = posted`, `erp_name`, `posted_at = Now()`.
  - The whole handler runs under one deadline (90 s). Once `Submit` has succeeded, `save` and the commit run under `context.WithoutCancel` with a 10 s timeout, so a cancelled caller can't leave a submitted entry with a `approved` row. Unit-test both.
  - The audit row is written after the handler returns, so if the audit insert fails after a post the caller sees an error although the entry is posted. The handler logs one Info line with `proposal_id` and `erp_name` (never the payload) on every successful post or record, before returning, so the pair is on record if the audit insert then fails; mention it in the PR summary; a retry returns `already_posted` and writes its own row.
  - Refusals are tool errors with a fixed, non-secret message that names the rule (`not_approved`, `self_approved`, `unbalanced`, `unknown_company`, ...); the full error goes to `Logger`. Nothing in an error or log carries the payload lines or a secret.
  - The handler calls `mcpkit.SetAuditActor(ctx, *checker)` once the row is loaded and the checker is known, so the audit row names the checker. Rows for refusals before the checker is known keep the route actor.
  - Never read the payload, company or lines from the input; never log the payload.

## Acceptance (human-readable)

- The agent token gets 401 on `/mcp-admin`.
- An approved proposal posts once, as a submitted Journal Entry; unapproved and self-approved proposals are refused; a second call returns the first call's entry.
- The audit row for a post names the checker as actor, `books-admin` as server, and the proposal ID in its args.
- G6 (the orchestrator's full-diff review, `ticket-reviewer`): the tool takes only a proposal ID; lines come only from the row; every refusal path makes no ERPNext write; no path posts without the row lock; no secret or payload in logs or errors; the tool is registered on `/mcp-admin` only; `admin.go` imports no `internal/agent` and does not touch `MCP_TOKEN_ADMIN`.

## Notes

- Regulated: `approved_by` stays empty here; `/build` records the owner's delegated approval after `ticket-reviewer` passes the spec.
- Design choice: `FOR UPDATE` row lock held across the ERPNext calls (a few seconds at most) so two calls can't both post, plus the `copilot_ext_id` lookup so a crash between submit and `save` is repaired instead of double-posted. Frappe has no transactional link to Postgres, so the ext-ID lookup is the recovery path, not the lock.
- Risk: the bot key (Accounts User) posts the entry. That widens what the bot key can do on the books server; the read route stays read-only because the write tool exists only on the admin server. Owner to confirm at G6; if ERPNext refuses the role, stop.
- Follow-up tickets to raise in the PR summary: (a) CC-012's writes check counts `books-admin` audit rows with no matching approved proposal inside a run window, plus Journal Entries carrying `copilot_ext_id` with no `posted` proposal (tasks/hardening.md, "CC-504b (from the CC-012 spec review)"); (b) CC-1004 must pass the admin token only from `internal/approvals`.
- No new dependencies.
