# CC-704 · Explainer

## Goal

One model call per finding returns a short explanation, a suggested action, the amounts it used, citations and an optional balanced journal entry, through a single forced tool, `emit_explanation`.

## Context

- **Ticket:** `docs/implementation-tickets.md`, section `CC-704`. It includes the starting system prompt; put it in `internal/agent/prompts/explain.txt` and embed it with `//go:embed` from `prompts/embed.go`.
- **It plugs into CC-703 (merged).** Implement `agent.Explainer` (`internal/agent/workflow.go`): `Explain(ctx, ExplainRequest) (StepResult, error)`.
  - Use `req.Model` for every call. It is already a `RecordingProvider` that enforces the token cap (`ErrRunTokenCap`). Never build a provider of your own inside the explainer.
  - When `req.Model` is nil, return a skipped result.
- **G5 invariant: the explainer's allowlist is exactly `{emit_explanation}`.**
  - `llm.Request.Tools` holds only that tool and `ForceTool` is set to it.
  - The explainer never receives the MCP registry and never calls a reader tool.
  - Add a test asserting the request's tool list is exactly that one tool, for every attempt.
- **Inputs:**
  - Evidence comes from `req.EvidenceRefs`. Load the snapshots with `store.GetArtifact`, which verifies the hash, and build the user message as compact JSON: `FINDING`, `EVIDENCE` and `DOCUMENTS` (empty until CC-806).
  - **ACCOUNTS** is the company's account names from the month's trial balance through the books reader. Put them in the cached system block, after the static rules (`llm.Block{Cacheable: true}`).
  - The explainer's dependencies are small interfaces (an artifact getter, an account lister) declared in `explain.go`, so unit tests use fakes.
- **Output:**
  - `emit_explanation` input schema: `explanation` (≤ 600 chars), `suggested_action` (the enum `book_entry | accrue | reclassify | follow_up_supplier | investigate | no_action`; reuse the constants in `internal/checks/finding.go`), `action_note` (one line), `cited_amounts_paise[]` (int64), `citations[] {doc_id, section}`, `needs_review` (bool), and an optional `proposal {posting_date YYYY-MM-DD, lines[{account, debit_paise, credit_paise}], remark}`.
  - Decode the tool call's args with `json.Decoder.UseNumber`. Amounts go into `money.Paise` (no floats; the `nofloat` analyzer applies).
  - Validate in Go:
    - the action is in the enum;
    - every cited amount appears in EVIDENCE, or is a sum or difference of evidence amounts (keep this check simple and exact: it's the verifier's job in CC-705, so here only check that cited amounts are integers ≥ 0);
    - the proposal's debits equal its credits, each line has exactly one side > 0, and every account is in ACCOUNTS;
    - the posting date is within the month;
    - citations have non-empty fields.
  - **Malformed output** (no tool call, a decode error or a validation failure) is retried once with the same model and a short corrective user turn naming the problem's field. A second malformed answer makes the step fail with a fixed reason.
- **Model choice:**
  - Use `cfg.LLMModelFast` through the request's `Model` field.
  - When `req.Attempt >= 3` (verification failed twice, CC-705), use `cfg.LLMModelStrong`.
  - `req.Feedback` (the verifier's violations) is appended to the user message as data when present.
- **Storing the result:**
  - The validated output is stored as an `explanation` artifact (`store.PutArtifact`) and returned in `StepResult.OutputRefs`.
  - Also add `store.SetFindingExplanation(ctx, findingID, explanation, action, citations, proposal)` in the new `internal/store/explanations.go`. It updates the `explanation`, `action`, `citations` and `proposal` columns; don't edit `runs.go`. The explainer calls it after the artifact is stored, so the UI can read the findings table.
  - Prompts and responses are recorded by `RecordingProvider` already. Never log prompt, evidence or response text.
- **Pseudonymisation (CC-710, phase 2) isn't built yet.** Add a `Pseudonymiser` hook in `explain.go`: `Mask(json []byte) ([]byte, func([]byte) []byte, error)` applied to the user message, plus an unmask for the explanation text. The default is identity, and it logs once (`slog.Warn`, no content) that identifiers go unmasked. All data in this project is synthetic. CC-710 will supply the real one.
- **Report and cost:** extend `report.go` so each finding shows its explanation and action, and the run report shows the average cost per explained finding (from `llm_calls` via the store, computed in SQL or as a decimal string; never a float in `internal/agent`). Update the goldens.
- **CLI (`cmd/agent`):**
  - `close` and `resume` build an `LLMExplainer` when `cfg.CheckLLM()` passes. `LLM_PROVIDER=claude-cli` is the default, so no API key is needed in development.
  - `--no-explain` keeps the CC-703 behaviour (explain steps skipped, run `partial`).
  - The integration tests in `cmd/agent` must not call a real model. Give them `--no-explain`, or a fake provider through an env-selected test seam, whichever is simpler; say which.
- **Tests:**
  - Unit tests use `llm.FakeProvider` with scripted tool calls:
    - a valid answer;
    - a malformed answer, then a valid one (one retry);
    - two malformed answers (the step fails);
    - an unbalanced proposal (malformed);
    - an account not in the list (malformed);
    - an action outside the enum (malformed);
    - `Attempt` 3 uses the strong model;
    - feedback appears in the prompt;
    - the tool list is exactly `emit_explanation`;
    - a nil `Model` is skipped;
    - the cache block holds ACCOUNTS.
  - Integration (`TestExplain*`, plus the existing `TestWorkflow*`): a skeleton month through the workflow with the fake provider ends `done`. Every finding has an explanation artifact and a filled `findings.explanation`, and every call has an `llm_calls` row.
  - Synthetic data only.
- **No real model in any automated test.** A live check (`LLM_PROVIDER=claude-cli make up && go run ./cmd/agent close --company sharma --month 2026-09`) is a manual step for the owner and costs real budget; don't run it.
- No new dependencies.
