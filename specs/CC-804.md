# CC-804 · Hybrid search with RRF and reranking

## Goal

`Search(ctx, query, company, docTypes, k)` combines vector and full-text results with Reciprocal Rank Fusion, then reranks the top 20 with the TEI cross-encoder, and never returns a chunk of another company.

## Context

- Ticket: docs/implementation-tickets.md, section `CC-804` (do not open it; everything needed is quoted here).
- Plan row: phase 3, implementer, data-sensitive, depends on CC-803. Check: "A Sharma query never returns a Mehta chunk; recall@5 reported". Guardrail row 12: the tenant filter sits inside the retrieval SQL, before ranking, so top-k never contains another company's chunks.
- **Search returns data only and calls no model.** Retrieved text must never reach a model that can call tools. TEI embed and rerank are local, non-generative models and are fine. `internal/retrieval` must not import `internal/agent`, `internal/llm` or `internal/frappe`.
- Signature (ticket): `Search(ctx, query, company, docTypes, k)`; `k` defaults to 5 when 0. Rerank the top 20 RRF candidates, return the top `k`.
- Table (migrations/0003_docs.sql): `doc_chunks(id bigserial, doc_id text, doc_type text, company_id text NULL, section text NULL, title text NULL, content text, content_hash text, embedding vector(384), tsv tsvector GENERATED (english, title || ' ' || content))`, HNSW index `vector_cosine_ops`, GIN index on `tsv`. `doc_type` is `policy | contract | close_note`. `company_id` is NULL only for the shared policy (`POL-001`), which every company may read; company ids are `sharma` and `mehta`.
- Reference SQL from the ticket. Keep the company filter in **both** CTEs; add the `doc_type = ANY($4)` filter to both too when `docTypes` is non-empty (also inside, before ranking). Add `section`, `title`, `content`, `doc_id`, `doc_type`, `company_id` to the final select (join back on `id`):

```sql
WITH v AS (
  SELECT id, row_number() OVER (ORDER BY embedding <=> $1) AS r
  FROM doc_chunks
  WHERE company_id IS NULL OR company_id = $2
  ORDER BY embedding <=> $1
  LIMIT 40
), t AS (
  SELECT id, row_number() OVER (ORDER BY ts_rank_cd(tsv, q) DESC) AS r
  FROM doc_chunks, websearch_to_tsquery('english', $3) AS q
  WHERE tsv @@ q AND (company_id IS NULL OR company_id = $2)
  ORDER BY ts_rank_cd(tsv, q) DESC
  LIMIT 40
)
SELECT id, sum(1.0 / (60 + r)) AS rrf
FROM (SELECT id, r FROM v UNION ALL SELECT id, r FROM t) AS ranked
GROUP BY id
ORDER BY rrf DESC
LIMIT 20;
```

  Parameter $1 is `pgvector.NewVector(queryVec)` (pgvector-go v0.4.1, already in go.mod). Write the `OR` as `(company_id IS NULL OR company_id = $2)` with parentheses so it can never be combined wrongly with the `doc_type` predicate.
- Dev set (ticket): 20 hand-written queries with the expected `(doc_id, section)` in `evals/dev/retrieval.yaml`; report recall@5 for **vector only, hybrid, and hybrid plus rerank**. The protected 60-query golden set arrives in CC-907 and the numbers go into `docs/benchmarks.md` in CC-906; **do not touch `docs/**`, `evals/golden/**` or `evals/baseline.json`**. Print the numbers from the integration test (`t.Logf` / stdout with `-v`) so they can be copied.

## Decisions (owner notes from the CC-803 review)

1. **Stale chunks.** Chunks of documents removed from `corpus/` stay in `doc_chunks` (ingestion only warns; `IngestStats.Stale`). Decision for CC-804: **search does not filter them and ingestion is not changed.** Search cannot tell a stale document from a live one (no marker column, no corpus access), and having ingestion delete would put a destructive step in CC-803's code with a wrong-directory risk. Stale chunks are still company-filtered, so this is a freshness issue, not a leak. Say so in the `Search` doc comment. Deleting stale documents is a follow-up for the owner's list (report it); do not edit `ingest.go` or `internal/store`.
2. **Heading levels.** Real docling output puts every heading at `##` (see the sample). Tests that need realistic chunks use `internal/retrieval/testdata/docling_policy_sample.md` through `ChunkMarkdown`; the worker must not assume nested levels.
3. **pipelineVersion** (`ingest.go:23`, `"chunk-v1/bge-small-en-v1.5"`) is not changed here because chunking and the embedding model are not changed. Queries must be embedded with the same model and no extra prefix, exactly like the ingested chunks (`TEI.Embed`). If the worker finds it must change chunking or the model, stop and report instead.
4. **Shared test database.** `TestIntegrationIngest` runs `DELETE FROM doc_chunks`. The live search test uses the same database selection (`TEST_DATABASE_URL`, falling back to `DATABASE_URL`) and must not run in parallel with it: never run `go test -tags=integration ./...` with both in one invocation across packages; both tests live in package `retrieval`, so one `go test` run executes them sequentially. The search test must **not** delete other rows; it seeds its own rows under doc ids prefixed `test-cc804-` (own cleanup in `t.Cleanup`) and, for the recall report, uses the ingested corpus if present (skip the recall part with a message if `doc_chunks` has no `POL-001` rows, telling the reader to run `cmd/ingest`).
5. **Tier 2 skipped.** G4-tier2 is not in `gates`: nothing in the eval path reads search results until CC-806, search calls no model, and the recall report is produced by the integration test without a model. The G4-tier1 harness does not read retrieval either.

## Subtasks

- [ ] `search.go`: `Searcher{db, Embedder, Reranker}`, `NewSearcher`, `Hit{ChunkID, DocID, DocType, CompanyID *string, Section, Title, Content string, RRF float64, RerankScore float32}`, `Search(ctx, query, company string, docTypes []string, k int) ([]Hit, error)`. Reject an empty `company` with an error (never fall back to "all companies"); `company` is a bind parameter, never concatenated into SQL.
- [ ] Embed the query, run the fused SQL (company and doc_type filters inside both CTEs), take the top 20, rerank the contents with TEI, sort by rerank score descending, return the top `k` (default 5). Empty query or no candidates returns an empty slice and no error. If rerank fails, return the error (do not silently return unreranked hits).
- [ ] A mode switch used by the recall report only (`vector`, `hybrid`, `hybrid+rerank`); the public `Search` is always hybrid + rerank.
- [ ] `evals/dev/retrieval.yaml`: 20 queries (company, query, expected `doc_id` and `section`), covering paraphrase queries, exact-term queries ("GSTR-2B", a supplier name), both companies, and the shared policy. Write expected sections by reading the `.md` sources.

## Notes

- No new dependencies expected (pgvector-go and pgx are already in go.mod). Report any that appear.
- The HNSW index with a `WHERE` filter can return fewer than 40 rows (post-filtering by the index scan). That is acceptable at this corpus size; note it in the code comment and do not weaken the filter to work around it. If recall looks low for a company with few chunks, report it rather than moving the filter.
- Rerank scores are TEI's raw scores; do not normalise them or mix them with RRF scores.
- Logs: `slog` only, never log chunk content or the query text at info level (document text is data-sensitive); log counts and ids.
