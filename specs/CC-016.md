# CC-016 · Baseline file holds one section per suite

## Goal

`evals/baseline.json` can hold the baseline of several suites, and the scorer judges a score against the section of its own suite.

## Context

- Today `evals/baseline.json` is `{"version":2,"tiers":{"replay":Baseline|null,"llm":Baseline|null}}` and each `Baseline` carries a `suite` field. `Compare` rejects a baseline for another suite ("baseline is for suite suite-skeleton, the score for suite-v1"), so `suite-v1` can't be gated. The `suite-v1` fixtures are committed and replay clean.
- **Owner decision (delegated to the orchestrator, 2026-10-12):** one file, version 3: `{"version":3,"suites":{"<suite>":{"replay":Baseline|null,"llm":Baseline|null}}}`. The loader still reads version 2, so the order of the follow-up commits (CC-016a: the workflow and the `suite-v1` baseline) does not matter.
- The scorer is built from the base ref in CI, so this lands before CC-016a. Do not touch `.github/**`, `evals/baseline.json`, `evals/scenarios/**`, `gates/**` or `CLAUDE.md`: the owner commits the baseline in its own `baseline-update` commit.
- Invariant to keep: the scorer never writes `evals/baseline.json` (`CheckOutputPath`, `internal/evals/baseline.go:181`). `--baseline-out` still refuses that path and anything under `evals/scenarios/`, `evals/golden/`, `gates/`.

## Subtasks

- [ ] `BaselineVersion = 3`. Keep a `legacyBaselineVersion = 2` that `LoadBaseline` accepts. `BaselineFile` becomes `{Version int; Suites map[string]BaselineTiers}` (the in-memory shape for both versions). Keep `omitempty` off the tier pointers so an absent section is written as `null`, as today. JSON key order must be stable (sorted suites) so a baseline file diffs cleanly.
- [ ] `LoadBaseline`: read the version first, leniently, as today. Version 3: strict decode into `{Version, Suites}`, then per section the existing checks (suite name valid, `items` present, `agent` matches the tier) plus: the section's `suite` equals the key it sits under, else an error naming both. A v3 file whose `suites` is missing, null or empty is an error; every suite key must match `nameRe`; a suite with both tiers null is an error; a v3 file with a `tiers` field is rejected (unknown field). Version 2: strict decode into an unexported legacy struct `{Version int; Tiers BaselineTiers}` (a v2 file with a `suites` field is rejected), run the existing per-section checks, then convert to one suite taken from the sections' `suite` fields; both sections must name the same suite (a null section is skipped; two different names are an error); a v2 file with both sections null is an error. Any other version is an error naming the version and the two accepted ones.
- [ ] `WriteBaseline`: always writes version 3. If the file at `path` exists, load it (v2 or v3), replace only `suites[b.Suite]`'s tier section for `b.Agent`, keep every other suite and tier; if absent, create it. Keep the atomic write and `CheckOutputPath`. An existing file that fails to load (any version, corrupt or not) is an error and is never replaced. `Set` creates the `Suites` map when it is nil.
- [ ] `Section(suite string, agent bool)` and `Set(b Baseline)` (uses `b.Suite`). `CompareTier` judges `s` against `Suites[s.Suite]`; a missing suite or a missing tier is the same fail-closed `CompareTierMissing` failure (keep the kind string `baseline_tier_missing`), with key `<suite>/<tier>`, evidence `baseline suites/<suite>/<tier>` (also in `compareConfig`), and the message naming both. `compareAll` and `cmd/eval/score.go` pass the suite through; the `--baseline-out` message prints the suite and tier. Update the help text.
- [ ] Tests, using these names (the acceptance command runs them): `TestLoadBaselineV2` (becomes one suite; a v2 file with two suite names is rejected); `TestLoadBaselineV3MultiSuite` (two suites, a score for each, round trip: write, load, equal, sorted stable output); `TestLoadBaselineV3Invalid` (`{"version":3}`, `{"version":3,"suites":{}}`, a bad suite key, both tiers null, a mismatched section suite, `tiers` in a v3 file, version 1 and version 4 all rejected); `TestWriteBaselineUpgradesV2` (writing into a v2 file gives v3 and keeps its other tier); `TestWriteBaselineKeepsOtherSuite`; `TestWriteBaselineKeepsBadFile` (a corrupt or version 1 file at the path: error, bytes unchanged); `TestWriteBaselineRefusesProtected` (a v2 file at `<tmp>/evals/baseline.json`: `ErrProtectedBaseline`, bytes identical before and after); `TestCompareTierMissingSuite` (fails closed with key `<suite>/<tier>`); `TestLoadCommittedBaseline` (loads `../../evals/baseline.json` read-only and asserts `Section("suite-skeleton", false)` succeeds, without asserting the version, so it still passes after CC-016a). Add test data under `internal/evals/testdata/` only if a test needs a file.
