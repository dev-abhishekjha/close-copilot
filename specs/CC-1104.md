# CC-1104 · Cost and latency optimisation

## Goal

Cheaper and faster close runs at the same scores, with measured before and after numbers in `docs/benchmarks.md`.

## Context

- Ticket: docs/implementation-tickets.md, section `CC-1104` (you need not open it; the subtasks are below).
- Plan row: phase 5, LLM, standard, depends on CC-904, CC-906. Check: "Cost per run and p95 both drop; Gate 4 still passes".
- Acceptance (ticket): cost per run and p95 duration both drop, with recall and precision within the CI gate's tolerance.
- Description (ticket): measure first (Langfuse traces from CC-904, or the `llm_calls` table / eval score output); the usual wins are caching the static prompt prefix, routing simple findings to the fast model, sending less evidence, and running explanations concurrently.
- Findings from CC-906 (`docs/benchmarks.md`) that you must act on or explain:
  - Benchmark 4: haiku explains as faithfully as sonnet at about a quarter of the cost. Fast is already the default; sonnet serves attempt 3 onwards (`LLMExplainer.model`).
  - Benchmark 2: retrieval cited an expected section in only 2 of 6 cases with `buildQuery` (finding type, supplier, account) and top-3. The weakness is the query, not the index. Improving it is in scope only if you can show it does not raise cost per run; it is a quality fix, not a cost win, so treat it as optional and report the effect.
  - Benchmark 3: the retrieval modes are not separable on the current set; do not tune retrieval modes.
- Env (`.env.example`): `LLM_PROVIDER=claude-cli` (default), `LLM_MODEL_FAST=haiku`, `LLM_MODEL_STRONG=sonnet`, `LLM_DAILY_BUDGET_USD=2.00` (never raise), `LLM_RUN_TOKEN_CAP=200000`. Pricing in `config/pricing.yaml` (read only here; has `cache_write_per_million`, `cache_read_per_million`).
- `llm.Usage` fields: `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `cost_usd`.
- Eval commands:
  - `make eval-replay SUITE=suite-skeleton`: no model (Tier 1), compares with `evals/baseline.json`. Run it as the regression check; it cannot measure cost or latency.
  - `go run ./cmd/eval run --suite suite-skeleton [--model-fast X]` then `go run ./cmd/eval score <results-dir> --compare evals/baseline.json`: Tier 2 with the model. `score` reports `runs.duration_ms.{total,mean,p95}` and `runs.cost_usd.{total,mean,p95}`; the CI gate flags a p95 rise (`CompareLatencyP95`) and a cost rise.
- Token budget rules (CLAUDE.md): develop with fakes and replay; use the model only for the baseline and after measurement, the smallest run that gives a stable number. Tier-2 `verified_rate` is unstable (0/8 to 3/8 on identical code): run before and after at least twice each and report ranges, and run a control on unchanged code before blaming this ticket for a score change.
- Invariants that must still hold: retrieved text never reaches a tool-calling model; the explainer's only tool is `emit_explanation`; pseudonymisation happens before any model call (CC-710); every call is recorded (`RecordingProvider`); `internal/agent` never imports `internal/frappe`.

## Subtasks

- [ ] Baseline: run Tier 2 on `suite-skeleton` at least twice on unchanged code. Record per-run cost, tokens per finding (input, output, cache read, cache write), p50 and p95 run duration, and the Tier 1 and Tier 2 aggregates from `eval score`. Put raw outputs in `tmp/reports/`, not in the repo. Also find the most expensive step from the `llm_calls` data or traces.
- [ ] Prompt caching: add a unit test that two explain requests in one run have a byte-identical cacheable system prefix, and a test (fake provider) that the second and later calls are built to read it. Confirm with a live run that `cache_read_tokens` > 0 on the second and later calls; if `claude-cli` cannot report cache reads, say so in the write-up and verify with `LLM_PROVIDER=anthropic` only if the owner has an API key set (do not ask for one).
- [ ] Routing: the fast model by default; the strong model only after a failed verification (attempt >= 3, already so) or for investigations. Confirm each call site against this rule, change only what contradicts it, and add a test per call site asserting the model it requests.
- [ ] Evidence trimming: lower the per-finding row cap and drop columns the explanation never cites before prompting. Prove with a test that the trimmed evidence still contains every record the finding's `Evidence` refs name and every number the verifier traces; the verifier's pass rate must not fall.
- [ ] Concurrency: tune `DefaultExplainParallel` within 4 to 8 against the measured rate-limit errors and retries; keep `SetLimit`. If a higher value causes 429s or CLI failures in the run, keep 4 and say why.
- [ ] Re-run the suite twice; run `make eval-replay SUITE=suite-skeleton` (must be clean against the baseline); record before and after in `docs/benchmarks.md` under a new `## CC-1104: cost and latency` section: a table of metrics (cost per run, tokens per finding, cache read tokens, p50, p95, recall, precision, verified rate) with before and after ranges, one line per change saying what moved, and a **Decision:** paragraph. Do not touch the existing Benchmark 1 to 4 sections, except a one-line pointer where Benchmark 2 or 3 names CC-1104.
