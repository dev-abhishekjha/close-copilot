## Goal

## Subtasks

### 1. Recorder and replayer (`internal/evals/fixtures.go`)

- `RecordingBooks` / `RecordingEvidence` wrap a live `checks.BooksReader` / `checks.EvidenceReader`.
- Each call writes one file, `<dir>/<suite>/<company>-<month>/<tool>-<argshash>.json`.
  - `<tool>` is the MCP tool name the method maps to: `get_trial_balance`, `list_gl_entries`, `list_purchase_invoices`, `list_sales_invoices`, `list_payment_entries`, `get_account_history`, `list_recurring_suppliers`, `list_bank_lines` and `list_gstr2b_entries`. Use whatever names `internal/agent` uses for the MCP calls.
  - `<argshash>` is the first 16 hex characters of the sha256 of the canonical args JSON. Args have sorted keys, dates as `YYYY-MM-DD`, and months as `YYYY-MM`.
  - The `<suite>/` level is a deliberate departure from the ticket's `evals/fixtures/<company>-<month>/`. The same company-month holds different data in different suites.
- File body: `{"tool":…, "args":{…}, "result":…}`, written with `marshalSorted`. Money stays `int64` paise, so the JSON numbers are exact.
- A live error during recording **aborts the recording**: errors are never recorded. Writes are atomic: temp file, then rename.
- `ReplayBooks` / `ReplayEvidence` serve those files.
  - Decode with `DisallowUnknownFields`. Check that the stored `args` equal the requested args, which guards against hash collisions.
  - A missing fixture is an error that names the tool and its args, `ErrFixtureMissing`. It **never** falls through to a live reader. Replay types hold no live reader at all.
- **Index:** `<dir>/<suite>/index.json` lists every fixture file with its sha256. It also records:
  - the suite file's sha256;
  - the sha256 of every ground-truth file the suite uses (`evals/scenarios/<suite>/ground_truth/<company>-<month>.json`);
  - the seeder commit (`buildinfo`);
  - the recording time.
- **Replay checks before any month runs:**
  - Every fixture's hash must match the index, and no file may be unlisted: an extra file is an error.
  - The current suite and ground-truth hashes must equal the index's. Otherwise fail with "fixtures are stale: re-record after seeding (make record-fixtures)".

### 2. Secret and identifier scan (`internal/evals/scan.go`)

`ScanFixtures(ctx, dir, profiles, extra []string)` takes an explicit extra allowlist: only the integration tests pass the fakeerp identifiers (`internal/testsupport/fakeerp/month.go:20-21`); the CLI passes none. The seeded allowlist is derived with `Profile.GSTIN`, `SupplierPAN` and `SupplierGSTIN`. Anchor the PAN regex with word boundaries and the 4th-letter entity set. It fails on:
- secret-looking strings: `sk-ant-`, `Bearer `, `token `/`token=`, `api_key`, `password`, `postgres://user:pass@`, AWS-style keys, `-----BEGIN`;
- **any GSTIN or PAN pattern that isn't in the synthetic allowlist.** The allowlist comes from `config/companies/*.yaml` and the seeder's derivation (`company.GSTIN`, `company.PAN`; read `internal/company`).
  - The fixtures carry seeded GSTINs, PANs and party names, which are synthetic but checksum-valid, so a plain pattern scan would flag every file.
  - Real identifiers can't appear, because the data is synthetic and recordings come only from the seeded ERPNext.

The recorder runs the scan before it writes the index, and `TestScanFixtures` runs it over `evals/fixtures/` when that folder exists. CI also runs gitleaks over `evals/fixtures/**` (see 5).

Pseudonymisation (CC-710) doesn't apply to fixtures: they are tool responses, not model inputs. CC-710 masks at the model boundary, and the fixtures must keep the real seeded values so the checks find the same records.

- **Manifest:** records `flags.replay`, `flags.record`, the fixtures index sha256 and the fixtures dir. The scorer must not read the fixtures dir.
- **Tier 2: wire the explainer into `eval run`** (deferred from CC-901 and CC-902):

### 4. Gate rules (`internal/evals/baseline.go`, `require.go`, `score.go`, `report.go`)

These close the CC-902 G5 notes copied from `tasks/hardening.md`:

- **One protected baseline file, one section per tier.** `evals/baseline.json` becomes `{"version":2,"tiers":{"replay":Baseline,"llm":Baseline}}`; `Compare` selects the section by the score's `agent` flag (Tier 1 is `agent:false`, `--replay --no-llm`, no verifier; Tier 2 is `agent:true`). No baseline exists yet, so the format bump is free, and every existing protection (`gates/protected.go`, CODEOWNERS, the guard hook, `CheckOutputPath`, the acceptance grep) still covers it. A second file is not allowed: it would be unprotected. It changes only in a `baseline-update` commit. `TestScoreCLIProtectedOutputs` still refuses `evals/baseline.json` as an output. `--baseline-out` writes or replaces only the score's own tier section and keeps the other unchanged (creating the file if absent); bump `BaselineVersion` to 2 and reject version 1 on read; `TestBaseline` round-trips a replay section then an llm section and checks both survive. A missing section for the score's tier fails closed.
- `Compare` **fails on an empty baseline** (`items: {}`) and when the baseline's `agent` flag or fast and strong model IDs differ from the score's (for `agent:false`, model IDs are not compared). It reports which, with `repro` and `evidence`. `TestCompare` has a row for each tier.
- **Latency and cost (Tier 2 only; Tier 1 never passes these flags):**
  - Add `CompareLatencyP95` and `CompareCost`, with integer-percent thresholds passed explicitly as flags: `--max-p95-increase-pct N` and `--max-cost-increase-pct N`, plus `--min-latency-delta-ms N` (an absolute floor: increases below N ms are ignored).
  - The workflow passes 25, 15 and 1000. 25 and 15 are owner-confirmed; the 1000 ms floor is new and goes on the owner's check list.
  - A zero baseline cost passes when the current cost is 0 and fails when it is above 0.
  - Use integer and big-decimal math only, no floats.
  - A flag that isn't passed skips that rule, and the report says so.
  - Boundary tests: exactly 25% passes, 25% + 1 ms fails (above the floor); a delta under the floor passes; zero-cost cases.
  - Baselines are measured from a CI `workflow_dispatch` run, not the laptop. The workflow uploads the results and the candidate baseline with `actions/upload-artifact` on dispatch.
- **Verifier rejects (CC-705 G5 note):** in Tier 2, `score.json` and `score.md` report `verifier_rejects` and the retry count. The runner (`runner.go`) writes the counts into `Result` from the run's verdicts and steps, and the scorer sums them.
- **Count requirements** (`caught`, `missed`, `false_alarms`) fail when the subject type has `planted == 0` (a renamed or empty type) unless the expression is `false_alarms`.
  - `X.false_alarms==0` stays legal with no planted items. A clean type is a real claim.
  - `missed==0` and `caught>=N` are not legal with no planted items, because they can't fail.
  - Document this in the `score` usage text.
- **`ScoreMonths`** repeats the control/clean and result-control checks that `LoadMonths` does, so a direct caller can't skip them.
- **Run error text** (`Result.Error` / `Reason`) in `score.json` and `score.md`:
  - cap it at 200 runes;
  - redact anything URL-like or DSN-like (`scheme://…`, `user:pass@`) to `[redacted-url]`;
  - add a pointer to the result file.
- **Job summary:** `score.md` plus the compare failures (each with item ID, outcome, `repro` and `evidence`) go into a single `summary.md`, which the workflow appends to `$GITHUB_STEP_SUMMARY`.

### 5. Workflow (`.github/workflows/eval.yml`, protected)

- **One job, `eval`, named `eval (G4)`.** `TestCIWorkflow` demands that every job has a name listed in `BRANCH_PROTECTION.md` and no job-level `if:`. A required check that is skipped counts as passing (CC-004 finding 5), so the job always runs.
- **Triggers:** `pull_request` (opened, synchronize, reopened), `schedule` (nightly), `workflow_dispatch`. Never `pull_request_target`. Use `permissions: contents: read` and its own concurrency group.
- **Steps decide the tier**, using step-level `if:` or script logic:
  - **PR, Tier 1:** when the PR changes paths under `internal/checks`, `internal/seed`, `internal/evidence`, `internal/books`, `internal/store`, `internal/evals`, `cmd/eval`, `evals/` or `go.mod`/`go.sum`, or the workflow itself. Otherwise print "eval (G4): no eval-relevant paths changed" in the job summary and pass.
  - **Tier 2 never runs on `pull_request`.** The ticket's PR Tier 2 run is cut (owner check): PR code would run with the API key in its environment. The owner dispatches it on a PR branch when needed. `TestEvalWorkflow` asserts that no step reading `ANTHROPIC_API_KEY` can run on `pull_request`.
  - **Schedule and dispatch:** Tier 2, three runs, then `eval noise`.
  - **Secrets:** Tier 2 reads `ANTHROPIC_API_KEY` from a repository secret, sets `LLM_PROVIDER=anthropic`, and takes `LLM_DAILY_BUDGET_USD` from a repository variable. Tier 1 steps get no secrets.
- **The scorer is built from the base ref.** Check out the base SHA into `base/` with `persist-credentials: false` and no restored cache, and `go build -o "$RUNNER_TEMP/evalbase/eval" ./cmd/eval` there. Run `eval run --replay` from the PR checkout, since that's the code under test, and `eval score` / `--compare` with the base binary. This keeps a PR from loosening the measuring stick that judges it, mirroring CC-004 finding 1.
  - Don't put the word `gates/` in these commands: `TestCIWorkflow` treats `go build … gates/` specially.
  - On `schedule` or `workflow_dispatch` the base is the default branch.
- **Baseline missing: fail closed.** When `evals/baseline.json` (or the tier's section in it) or the suite's fixtures index is absent, a run that should score **fails**, printing a loud notice with the bootstrap steps. This happens on Tier 1 relevant paths, on Tier 2, and always on schedule.
  - Why fail rather than skip: a green skip is exactly the hole CC-004 finding 5 closed. Today merges go through the orchestrator's local merge queue, not GitHub, so a red check blocks nothing until the owner commits the baseline and turns on the required check.
- **Layout and trust:** PR checkout in `pr/`, base in `base/`; `go mod verify` before the build; setup-go with `cache: false`. Run the replay and score steps with `working-directory: pr`, and pass `--compare "$GITHUB_WORKSPACE/base/evals/baseline.json"`. The base-built scorer reads the baseline from the base tree, because the PR tree's copy is guarded by `protected.yml`. `TestEvalWorkflow` asserts this, and the summary step is `if: always()` so `score.md` is appended even when the baseline step fails closed.
- **Tier 2 budget and key:** use a dedicated key with a hard spend cap. `LLM_DAILY_BUDGET_USD` is summed from Postgres `llm_calls`, and a CI job starts with a fresh database, so the cap applies per job; owner checks note both points. Postgres image: `pgvector/pgvector:pg17`.
- **Gate expression for `suite-skeleton`:** Tier 1: `--compare "$GITHUB_WORKSPACE/base/evals/baseline.json"`, `--require 'unrecorded_bank_charge.recall>=3/3'`, `--require 'clean.false_alarms==0'`, no latency or cost flags. Tier 2: the same, plus `--max-p95-increase-pct 25 --max-cost-increase-pct 15 --min-latency-delta-ms 1000`.
  - Injection, retrieval, tenant-leak, citation and unauthorized-write rules join in Phase 2, when their metrics exist. Don't add `--require unauthorized_writes==0` yet: it fails closed while the count is unchecked.
- **Gitleaks** over `evals/fixtures/**`: pin a release binary by version and verify its sha256 checksum. Don't use a third-party action. List it as a new CI tool in the PR summary.
- **`BRANCH_PROTECTION.md`:** add `eval (G4)` to the required-checks table. Note that it becomes required in GitHub only after the owner's first `baseline-update` commit.

- **Determinism:** the fixtures key on args alone. If any reader call takes a time-dependent argument (like `now`), the round-trip test will show it. Fix it at the call site only if the call site is in this ticket's files; otherwise report it.
- **Risks:**
  - Replay hides an ERPNext behaviour change. That's by design: re-record after seeder or ERPNext changes. The stale-hash check catches seeder changes but not ERPNext-version changes; note this in the README.
  - The base-ref scorer means a PR that changes the scorer's flags is judged by the old binary. Document it: a scorer-flag change lands in two PRs.
