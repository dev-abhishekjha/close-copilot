# CC-1001 · Web app skeleton, login and roles

> **Protected path.** `config/users.yaml` is on the CLAUDE.md protected list. This ticket is regulated and owner-reviewed: the file is declared here only because the spec is approved (`approved_by` records the owner, or the orchestrator under the owner's build-phase delegation) and the ticket stays on the owner's end-of-day review list. It changes in no other ticket without the owner. No other protected path may change (`internal/approvals/**`, `internal/mcpkit/auth*.go`, `docs/**`, `.claude/**`, `gates/**`, `.github/**`).

## Goal

The agent service serves HTML pages and the JSON API from the shared specs behind a login with three roles (`viewer`, `maker`, `checker`). Every route declares its minimum role and the check runs in middleware, not in templates.

## Context

- Ticket: docs/implementation-tickets.md, section `CC-1001` (you don't need to open it; it is quoted here).
- Plan row: phase 4, implementer ("IMP, you review"), regulated, depends on CC-703 (merged). Check: "Viewer gets 403 on maker routes".
- Env vars (`.env.example`, already parsed by `internal/config`): `APP_ADDR` (default `:8000`) and `APP_SESSION_KEY` (the raw string, at least 32 bytes, no decoding; `NewServer` refuses an empty or shorter key; a `config.Secret`; read it with `.Reveal()` only inside `internal/web/auth.go`; never log it).
- Users live in `config/users.yaml`: `username`, bcrypt `password_hash`, `role` (`viewer` | `maker` | `checker`). Seed `asha` (maker), `ravi` (checker), `demo` (viewer). Optional per-user `token_sha256` (hex SHA-256 of a bearer token) for scripts; leave it empty in the seed file, so bearer auth is off for a user until the owner sets one. Plaintext tokens and passwords are never stored.
- Role order: `viewer` < `maker` < `checker`? **No.** Roles are not a ladder for writes: a checker approves and a maker proposes (separation of duties). Model it as explicit allowed sets: `viewer` routes allow all three roles; `maker` routes allow `maker` only; `checker` routes allow `checker` only. `requireRole(roles ...Role)` takes the allowed set. A checker gets 403 on maker routes and vice versa. (CC-1004 enforces checker ≠ maker on each proposal; this ticket only provides the role split.)
- HTTP API, quoted from the shared spec. Register every row now with its role; handlers for rows owned by later tickets return `501 Not Implemented` JSON (`{"error":"not implemented"}`) *after* the role check, so the role matrix is testable today:

  | Method | Path | Role | Purpose |
  | --- | --- | --- | --- |
  | POST | `/api/close-runs` | maker | Start a run: `{company, month}` returns `{run_id}` (CC-1002) |
  | GET | `/api/close-runs/{id}` | viewer | Status, finding counts, tokens, cost (CC-1002) |
  | GET | `/api/close-runs/{id}/findings` | viewer | Findings with evidence and citations (CC-1002) |
  | POST | `/api/findings/{id}/proposals` | maker | Finding's proposed entry into a journal proposal (CC-1004) |
  | POST | `/api/proposals/{id}/approve` | checker | Approve and post (CC-1004) |
  | POST | `/api/proposals/{id}/reject` | checker | Reject with a reason (CC-1004) |
  | POST | `/api/ask` | viewer | Question in, answer out (stretch; CC-707/708) |
  | GET | `/healthz` | none | Liveness |

- Router: Go `net/http` `ServeMux` with method-and-path patterns (`mux.HandleFunc("POST /api/close-runs", ...)`). No third-party router.
- Session: stateless, signed (HMAC-SHA256 over a payload with username, issued-at, expiry and a short fingerprint of the user's `password_hash` and `token_sha256`). The role is **not** trusted from the cookie: re-resolve user, role and fingerprint from the users file on every request, so a removed user, a changed role or a rotated hash ends that user's sessions. Server-side TTL 8 h, checked from the signed payload. Cookie flags: `HttpOnly`, `SameSite=Lax`, `Path=/`, and always `Secure` (browsers keep it on `http://localhost`); an explicit `Server` option may turn it off for tests, default on, never inferred from the request. Logout only clears the browser's copy (sessions are stateless); say so in a code comment.
- CSRF: every request with an unsafe method (anything but GET, HEAD, OPTIONS) that is authenticated by the session cookie must carry a valid per-session token (header `X-CSRF-Token` or form field `csrf_token`), whatever its Content-Type or other headers, compared in constant time. `POST /login` has no session yet: use a pre-session double-submit CSRF cookie issued on `GET /login` and also reject it when `Sec-Fetch-Site`/`Origin` is present and not same-origin.
- Bearer: accepted only on `/api/*`. On non-`/api/` routes the `Authorization` header is ignored entirely and the cookie decides. On `/api/*`, if an `Authorization` header is present the cookie is ignored; an unknown or bad token returns 401 with no fallback to the cookie. CSRF is skipped only when the bearer token itself authenticated. Bearer never creates a cookie and never bypasses role checks.
- Public routes: `/login`, `/static/*`, `/healthz`. Everything else needs a session (or bearer for `/api/*`).
- Anonymous: HTML routes redirect (303) to `/login?next=<path>`; `next` must be a same-site relative path (reject `//`, schemes, backslashes). `/api/*` anonymous requests get `401` JSON, not a redirect. A logged-in user lacking the role gets `403`.
- Invariants that apply: `internal/web` must not import `internal/frappe`; it does not use the MCP admin token. Don't write `internal/approvals`, `MCP_TOKEN*` or `MCPTokenAdmin` anywhere in `internal/web`, comments included; acceptance greps for them. Passwords are checked with `golang.org/x/crypto/bcrypt` (already in go.mod); an unknown user still runs a bcrypt compare against a dummy hash of the same cost as the real ones so login timing doesn't reveal usernames. Login errors say "invalid username or password" for both cases. Money is not touched here.
- templ: all `.templ` files go in `internal/web/templates/` (package `templates`), so generated `*_templ.go` files fall under the declared `files`. `make generate` already exists (`go tool templ generate`; templ is in go.mod's `tool` block). Commit the generated `*_templ.go` files. htmx is loaded from a pinned CDN URL with a Subresource Integrity hash in the base layout (pin an exact version, e.g. `htmx.org@2.0.x`, and put `integrity=` and `crossorigin="anonymous"`); if you can't compute the hash offline, say so in the PR summary rather than omitting it silently.

## Acceptance (human-readable)

- Each of the three users can log in and sees only the actions their role allows (owner checks by hand after merge; tests cover the logic).
- `TestHomeActions`: the home page per role shows maker-only links only for maker and checker-only links only for checker; viewer sees neither.
- `TestAnonymous`: anonymous HTML request: 303 to `/login`. Anonymous `/api/*`: 401.
- `TestViewerForbiddenOnMakerRoutes`: viewer gets 403 on every maker and checker route; maker gets 403 on checker routes; checker gets 403 on maker routes; viewer routes work for all three roles.
- `TestRoleMatrix`: a table over every row of the route table x {anonymous, viewer, maker, checker, bearer viewer, bearer maker, bearer checker} asserting 401/403/501 (or 200 for `/healthz`).
- `TestSessionCookieFlags`: `HttpOnly`, `SameSite=Lax`, `Secure` by default, `Path=/`, expiry set.
- `TestSessionTamper` (tampered cookie or other key), `TestSessionExpiry`, `TestRemovedUser`, `TestCredentialRotationKillsSession` (changed `password_hash` or `token_sha256`): each is treated as anonymous. `TestShortSessionKey`: empty and 31-byte keys are refused.
- `TestCSRF`: a cookie-authenticated POST without or with a wrong token gets 403 even for an authorised role, including a JSON and a `text/plain` POST to a maker API route; with the token it passes the check; bearer-authenticated requests skip CSRF; a bad bearer plus a valid cookie gets 401. `TestLoginCSRF`: `POST /login` without the pre-session token, or with a cross-site `Sec-Fetch-Site`, is refused.
- `TestBearer`: on a non-`/api/` route an `Authorization` header is ignored and the cookie decides (assert both: valid cookie + bad bearer works; bearer alone is anonymous); valid token authenticates as its user and role; wrong token 401; a user with no `token_sha256` can't use bearer.
- `TestLogout`: `POST /logout` without CSRF gets 403; with CSRF it sets an expired cookie (Max-Age < 0). It does not assert server-side revocation (sessions are stateless).
- `TestUsersFile` (the file is loaded from `../../config/users.yaml`): the real `config/users.yaml` loads, has exactly `asha`/maker, `ravi`/checker, `demo`/viewer, and every hash is bcrypt cost >= 10.
- `TestOpenRedirect`: `next=//evil.example`, `https://evil.example`, `/\evil.example`, `/%2F%2Fevil.example`, `javascript:alert(1)` and empty all fall back to `/`.
- `TestNoSecretsInLogs`: logs and responses never contain the session key, a password, a hash or a token (a test captures the log buffer).
