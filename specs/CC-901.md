# CC-901 · Eval runner

## Goal

`make eval SUITE=suite-v1` (`go run ./cmd/eval run --suite suite-v1`) runs a close for every evaluated company-month and the clean control month, and saves every finding and the run metadata to a results folder, unattended.

## Context

- **Ticket:** `docs/implementation-tickets.md`, section `CC-901`.
  - The runner calls the **same** `agent.Workflow.RunClose` as the app (CC-703, merged), so it evaluates the real system.
  - It assumes the suite is already seeded and loaded (`make erp-reset seed load ingest`).
  - Months run one after another.
- **Suite files:**
  - `evals/scenarios/<suite>.yaml` is **protected and read-only for you**. Look at `suite-skeleton.yaml` and `suite-v1.yaml`: `suite`, `history_months`, `evaluated: [{company, months: []}]`, `clean_control: {company, month}`, `errors`, `small`.
  - `LoadSuite(path)` in `internal/evals/suite.go` parses what the runner needs (evaluated months plus the clean control month). It rejects unknown suites, bad months (`YYYY-MM`) and duplicates.
  - Record the sha256 of the file bytes for the manifest.
  - Never edit the scenarios, golden sets or `evals/baseline.json`.
- **Runner (`internal/evals/runner.go`):**
  - `Runner` takes a small `Closer` interface (`RunClose(ctx, company, month) (agent.Result, error)`) plus a reader for the run's findings, run row and LLM calls, so unit tests use fakes. `*agent.Workflow` and `*store.Store` satisfy them.
  - For each month in order, with `--only company:month` filtering:
    1. call `RunClose`;
    2. export to `results/<suite>/<timestamp>/<company>-<month>.json`: the run ID, status, reason, findings (as stored, with evidence refs and artifacts), tokens, cost (as the decimal string the store keeps), duration, model IDs (fast and strong from config, plus distinct models from `llm_calls`), the git commit (`internal/buildinfo`) and the trace ID (null until CC-904).
  - `<timestamp>` is UTC `20060102T150405Z`.
  - Write `manifest.json` last: the suite name and sha256, the config **without secrets** (use the non-secret fields only; `config.Secret` values must never be serialised), the flags, the git commit, the start and end times, and the list of result files with each status.
  - Write files atomically (temp file plus rename) with sorted keys and a 2-space indent.
  - **Exit non-zero if any run ends `failed`.** `partial` (no explainer yet) is not a failure. Keep going after a failed month and report it at the end.
  - No floats in `internal/evals` that touch money: cost comes as a string from the store.
- **CLI (`cmd/eval`):**
  - `eval run --suite <name> [--only sharma:2026-09] [--model-fast X] [--no-agent] [--results-dir results] [--scenarios-dir evals/scenarios] [--config-dir config]`.
  - Build the workflow the way `cmd/agent/main.go` does (registry, MCP readers, profiles, rules, store). Duplicate that wiring in `cmd/eval`; don't edit `cmd/agent`, which another ticket (CC-704) is changing in parallel.
  - `--model-fast` overrides `cfg.LLMModelFast` for this run only.
  - `--no-agent` runs with no explainer or verifier. Until the explainer is wired into the eval path in a later ticket, the runner always runs with none; record `agent: false` in the manifest, and say so in the help text.
  - The model only runs inside the workflow. The eval CLI calls no model itself.
  - `cmd/eval` must not import `internal/frappe`, `internal/books` or `internal/seed` in production code. Add a `go list -deps` test as `cmd/agent/deps_test.go` does.
- **Tests:**
  - Unit (no Docker): a fake `Closer` covering ordering, `--only`, a failed month continuing with a non-zero exit, the result and manifest contents and shape, no secrets in the manifest, atomic writes, and suite parsing including the real `suite-skeleton.yaml` and `suite-v1.yaml`, read only.
  - Integration (`TestRunner*`, `TestEvalCLI`):
    - Postgres via testcontainers.
    - The in-process books and evidence MCP servers over `internal/testsupport/fakeerp` (`internal/evals` isn't under `noerpimport`, so tests may import `fakeerp`; production code must not, which the fakeerp import check enforces).
    - Use a temp suite file whose month matches fakeerp's synthetic month.
    - Assert one result file per month plus the manifest, the three planted bank-charge findings, and the CLI exit code.
  - No real model and no real ERPNext.
- No new dependencies.

## Subtasks

- [ ] `suite.go`: `LoadSuite` and the file hash.
- [ ] `runner.go` and `result.go`: the run loop, export, manifest and atomic writes.
- [ ] `cmd/eval`: the `run` command, flags, workflow wiring and deps test.
- [ ] Unit and integration tests.

## Acceptance (human-readable)

- A suite run finishes unattended and writes one result file per month plus the manifest. It exits non-zero if any run failed.
- A full `suite-v1` run against the real stack is a manual owner step (it needs a seeded ERPNext). The automated proof uses fakeerp.

- Wiring the explainer into the eval path. Do it in the first ticket after CC-704 that touches `cmd/eval`, and record it in that ticket's spec.
