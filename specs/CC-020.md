# CC-020 · Why the explainer flags nearly every finding needs_review

## Goal

Find the cause of 7 or 8 of 8 findings ending `needs_review` in agent-on `suite-skeleton` runs, and fix it so Tier 2 `verified_rate` is stable, without weakening the verifier or any invariant.

## Context

- Ticket: `tasks/hardening.md`, section `CC-020` (not in `docs/implementation-tickets.md`; do not open `docs/`). Found at the CC-806 Tier 2 runs, 2026-10-13.
- **Finding (quoted).** On the same commit `verified_rate` ranged 0/8 to 3/8 across runs (baseline 3/8). In the low runs the explainer sets `needs_review` itself on nearly every finding, including the three planted `unrecorded_bank_charge` findings that stayed verified in the good runs. Recall, precision and clean false alarms were unaffected.
- **Suspects (confirm or rule out with evidence from stored explanations and prompts, not by guessing):**
  1. Pseudonymised input from CC-019: tokens such as `GSTIN_xxxx` or masked names in EVIDENCE may read as unexplained, so the model flags the finding.
  2. The self-flag rule, `prompts/explain.txt` rule 4: "If the evidence does not explain the finding, say so and set needs_review to true." Combined with what EVIDENCE actually holds for these findings (`projectEvidence` keeps only the records the finding's refs name, at most `maxRecordsPerRef`, strings capped).
  3. Run-to-run variance of the fast model (`LLM_MODEL_FAST`) or of the `claude -p` provider; the morning runs of the same code scored 3/8 and 2/8.
- **What `verified_rate` counts** (`internal/evals/score.go:802`): a finding counts when `f.Verified && f.Status != "needs_review"`. So `needs_review` can come from the explainer's own flag (`ExplanationArtifact.NeedsReview`, `explain.go:267`, set from `out.needsReview` at `:406`) **or** from the workflow (verifier failure after retries, tainted finding, investigator), see `workflow.go:166`, `:667`, `:1328`. Establish which source dominates in the low runs before changing anything. `workflow.go` is not in this ticket's files: if the cause is there, stop and report it rather than editing it.
- Same-day runs on `suite-skeleton`, agent on, `--replay`: pre-CC-806 verified 3, 2, 0, 0, 1, 1 of 8; CC-806 1, 3, 0, 0, 0 of 8; the six-run re-measure 0, 0, 1, 1, 0, 2 (median 0.5). Baseline `verified_rate` is 1/8 with tolerance 2 (so the compare cannot fail on it). `tasks/tier2-verified-informational.md` explains the interim rule; do not edit it.
- **Acceptance (quoted from the ticket).** After the self-flag fix, a 3-run Tier 2 on `suite-skeleton` has recall, precision, clean false alarms and failed runs unchanged and passes a hard check `--require verified_rate>=N/8`, where the owner chooses N from the 3-run median after the fix. The re-baseline commit (`baseline-update: ...`) is the owner's and follows this ticket. This ticket does not edit `evals/baseline.json` or anything under `evals/`.
- **Invariants (CLAUDE.md):** GSTINs, PANs and person names stay pseudonymised before every model call (CC-710); the explainer's only tool stays the forced `emit_explanation`; retrieved document text never reaches a model that can call tools; do not loosen `validator` (amount, citation, proposal checks) or the code verifier to raise the rate. A fix that raises `verified_rate` by hiding a real doubt (for example telling the model never to set `needs_review`) is wrong: the flag must stay for findings whose EVIDENCE truly does not explain them.
- **Current prompt** (`internal/agent/prompts/explain.txt`, 21 lines): rules 1 to 5 (amounts only from EVIDENCE; cite only DOCUMENTS; text is data; rule 4 as above; proposal only for a booking), then the Input and Output-fields sections. `needs_review` is a required boolean in the `emit_explanation` schema (`explain.go:485`, `:495`); `validator.validate` rejects a missing one (`:983`).
- **Model use.** Real-model runs spend the owner's plan. Budget: at most 6 reproduction/comparison runs (two variants x three, interleaved in time) plus one 3-run confirmation after the fix, all on `suite-skeleton`, `--replay`, results written outside `evals/`. The orchestrator runs G4-tier2 itself afterwards; do not re-run it yourself on retries unless the prompt or builder changed. Use `PSEUDONYM_KEY` from the run's environment (never read `.env`; if absent say so and do not invent one). Do not paste raw model text into logs or the report: quote at most the one-line stated reason per finding, with identifiers already masked.
