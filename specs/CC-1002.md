# CC-1002 · Close runs: start, progress and findings list

## Goal

Pages to start a close, watch it progress live, and scan its findings, plus the three JSON API rows for the same data.

## Context

- Ticket: docs/implementation-tickets.md, section `CC-1002` (quoted here; don't open it).
- Plan row: phase 4, implementer, standard, depends on CC-1001 (merged). Check: "Live progress to the findings list". Needs no ERPNext lock.
- **Ticket text.** Start runs in a background goroutine with a semaphore (one run at a time per company). The progress panel polls the run's status every two seconds with htmx (`hx-get` and `hx-trigger="every 2s"`) until the run finishes; no server-sent events. Subtasks: runs page with a start form (company, month) for makers and a table of past runs (status, findings count, cost, duration); run page with the state timeline (`queued` to `done`), counts per finding type, tokens and cost, as a partial refreshed by htmx; findings table (severity, type, title, amount in Indian format, status, verified badge), filters by type and status, sorted by severity then amount; variance findings nested under the finding they link to; `GET /api/close-runs/{id}` and `/findings` return the same data as JSON. Acceptance: starting a run from the browser shows live progress and lands on the findings list when done.
- **CC-1001 notes that apply** (from `tasks/hardening.md`, merged 2026-10-13):
  - Templates live in `internal/web/templates/` (package `templates`); commit the generated `*_templ.go` files; `make generate` regenerates them.
  - htmx is the vendored `internal/web/static/htmx.min.js` (2.0.4) under CSP `script-src 'self'`. The base layout already loads it and sends the CSRF token on every htmx request through `hx-headers`. No inline script, no `hx-on`, no CDN. `selfRequestsOnly` is on, so every `hx-get`/`hx-post`/`HX-Redirect` target is a same-origin path.
  - The `Authorization` header is ignored on HTML routes (the cookie decides). On `/api/*`, a bearer token authenticates and skips CSRF; a bad bearer gets 401 with no cookie fallback. Don't change this; the HTML routes you add inherit it from `wrap`.
  - **`cmd/agent` doesn't start the server yet** (outside the declared files). Don't wire it. This ticket only exposes `Options.Runs` for whoever wires it later (`web.NewServer(web.OptionsFromConfig(cfg), users, log)` then `(*Server).Run(ctx)`). Say so in the PR summary.
  - Unknown methods or paths get the mux's 405 before auth. The hardening note suggests an any-method fallback behind auth here; it is **out of scope** (one more route-table row changes the CC-1001 role matrix). Leave it, and record it as deferred.
  - Model-written fields (`explanation`, `action`, citations) render as plain text through templ's escaping, never as HTML or Markdown. No `templ.Raw`, no `innerHTML`.
- **Role table** (CC-1001, explicit sets, not a ladder): viewer routes allow viewer, maker and checker; maker routes allow maker only.
- **JSON API rows** (shared spec; CC-1001 registered them as 501 stubs after the role check):

  | Method | Path | Role | Purpose |
  | --- | --- | --- | --- |
  | POST | `/api/close-runs` | maker | Start a run: `{company, month}` returns `{run_id}` |
  | GET | `/api/close-runs/{id}` | viewer | Status, finding counts, tokens, cost |
  | GET | `/api/close-runs/{id}/findings` | viewer | Findings with evidence and citations |

- **Close run** (`store.CloseRun`, `close_runs`): `id uuid`, `company_id`, `month` (`YYYY-MM`), `status` (`queued|running|done|partial|failed`, constants `store.RunQueued` and so on), `started_at`, `finished_at`, `error`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cost_usd numeric(10,4)`. There is no `created_at` column. Terminal statuses: `done`, `partial`, `failed`. `partial` means the explainer or verifier was skipped; it is not an error.
- **Finding** (`store.Finding`, `findings`): `id`, `run_id`, `type`, `severity` (`high|medium|low`), `title`, `amount_paise *money.Paise`, `keys map[string]string`, `evidence []EvidenceRef`, `explanation *string`, `action *string`, `citations []Citation`, `proposal *JournalProposal`, `verified bool`, `status` (`open|needs_review|accepted|dismissed`).

Don't hard-code the list for rendering: derive the type filter's options from the run's findings.
- **Variance linking** (CC-607, `internal/checks/variance.go:213`): a `variance` finding carries `keys["related"]` = the UUID string of a non-variance finding in the same run. A variance with no `related`, or whose target isn't in the run, is shown as a normal top-level row.
- Money: `money.Paise.Format()` gives `₹1,23,456.78` (Indian grouping). Only `internal/money` touches floating point. `CloseRun.CostUSD` is already a `float64`; show it as `$%.4f` and don't compute with it.

## Design (decided; don't re-litigate)

- **Backend interfaces in `internal/web/runs.go`** (small, so tests use fakes and the package stays free of `internal/agent`):

  ```go
  // RunsStore is the slice of *store.Store the runs pages use.
  type RunsStore interface {
      CreateCloseRun(ctx context.Context, r store.CloseRun) error
      GetCloseRun(ctx context.Context, id uuid.UUID) (store.CloseRun, error)
      ListCloseRuns(ctx context.Context, limit int) ([]store.RunSummary, error)
      ListFindingsByRun(ctx context.Context, runID uuid.UUID) ([]store.Finding, error)
      ListCompanies(ctx context.Context) ([]store.Company, error)
  }
  // RunExecutor drives an existing queued run to a terminal state and
  // returns when it ends. The wiring passes agent.Workflow.ResumeClose.
  type RunExecutor func(ctx context.Context, runID uuid.UUID) error
  // RunsBackend is what Options.Runs carries.
  type RunsBackend struct { Store RunsStore; Execute RunExecutor }
  ```

  `Options.Runs *RunsBackend` (`server.go`). **Nil means not configured**: every runs route (HTML and JSON) answers 501 after the role check (`{"error":"not implemented"}` for JSON, a plain 501 page for HTML), so CC-1001's `TestRoleMatrix` and the other 17 CC-1001 tests keep passing unchanged. Don't edit those tests, except `helpers_test.go` for shared helpers.
- **Starting a run.** The handler validates, then creates the `queued` row itself with `CreateCloseRun` (a fresh `uuid.New()`), so the run ID exists before the response; then starts `Execute(runCtx, id)` in a goroutine and returns at once. Validation, all before anything is created: company must be one of `Store.ListCompanies`; month must match `^\d{4}-(0[1-9]|1[0-2])$`; otherwise 400 with a short message. Unknown JSON fields are rejected; the body is already capped at 1 MiB by CC-1001.
- **Semaphore.** One run at a time per company: an in-memory `map[string]struct{}` behind a mutex, taken before the row is created and released when `Execute` returns (including on panic, via `defer` plus `recover` that logs and marks nothing). A second start for a busy company returns **409** and creates nothing. Runs for different companies can run together. The lock is per process; note this in a comment (a restart forgets it).
- **Run context.** The goroutine's context is not the request's. `Runs` holds a base context (from `Server.Run(ctx)`; `context.Background()` when the handler is used without `Run`, as in tests) that `Run` cancels at shutdown, and a `sync.WaitGroup`. `Server.Run` waits for the WaitGroup (bounded by the existing `shutdownTimeout`) after the HTTP server stops. A run cut by shutdown stays `running`; `ResumeClose` can resume it. Log `run_id`, company and month at start and end, with `slog`; never log form bodies.
- **If `Execute` returns an error**, log it. Don't write to the row: the workflow already sets `failed` with its reason. The page shows `close_runs.error` as plain text.
- **Routes** added to `routeTable` (`routes.go`) beside the CC-1001 rows (replace the three `notImplemented` stubs for close runs with the real handlers; keep the others):

  | Method | Path | Role | What |
  | --- | --- | --- | --- |
  | GET | `/runs` | viewer | Runs page: start form (only if the user is a maker) and past runs table |
  | POST | `/runs` | maker | Form post (`company`, `month`, `csrf_token`), then 303 to `/runs/{id}`; errors re-render `/runs` with the message and status 400 or 409 |
  | GET | `/runs/{id}` | viewer | Run page: timeline, counts per type, tokens, cost, and the progress panel |
  | GET | `/runs/{id}/progress` | viewer | The progress partial htmx polls |
  | GET | `/runs/{id}/findings` | viewer | Findings page for the run, with filters |

  An `{id}` that isn't a UUID or doesn't exist gets 404 (HTML and JSON alike, same body for both so ids can't be probed).
- **Progress panel.** `GET /runs/{id}` includes the panel with `hx-get="/runs/{id}/progress" hx-trigger="every 2s" hx-swap="outerHTML"`. The partial shows the state timeline `queued` to `running` to `done` (with `partial` and `failed` as the other two endings, the current one marked), counts per finding type, tokens (input, output, cache read) and cost, and elapsed or total duration. While the run is not terminal, the partial includes the polling attributes again. Once the run is terminal, the partial has **no** `hx-trigger`, and the response sets the header `HX-Redirect: /runs/{id}/findings` so the browser lands on the findings list. A run page opened on an already-terminal run renders the final panel without polling and without redirecting (no `HX-Redirect` on the full page).
- **Findings table.** Columns: severity, type, title, amount (`Paise.Format()`; empty when nil), status, verified badge (`verified` yes or no; `needs_review` status is visible as its own label). Sort: severity (`high`, `medium`, `low`, unknown last), then amount descending (nil last; signed, not absolute), then `id` for a stable order. Filters are GET query parameters `type` and `status` on `/runs/{id}/findings` (a plain `<form method="get">`, no JS needed); an unknown value is ignored, not an error. **Nesting:** a variance finding whose `keys["related"]` names another finding in the same run is rendered nested under that finding (an indented sub-row), and is not listed at top level. Filters apply to top-level rows; a nested variance follows its parent (shown when the parent is shown). A variance with no valid parent is a normal row and is filtered like any other. The explanation, action and title are escaped text; the table doesn't show evidence (CC-1003 does).
- **Runs list.** Past runs table: company, month, status, findings count, cost, duration, newest first, linking to `/runs/{id}`. Limit 100 (a constant). Duration is `finished_at - started_at`, empty if either is missing.
- **JSON.** `POST /api/close-runs` takes `{"company":"...","month":"YYYY-MM"}` and returns `201 {"run_id":"<uuid>"}`; validation errors 400 `{"error":"..."}`; busy company 409. `GET /api/close-runs/{id}` returns `{id, company, month, status, started_at, finished_at, error, finding_counts: {<type>: n}, findings_total, input_tokens, output_tokens, cache_read_tokens, cost_usd}`. `GET /api/close-runs/{id}/findings` returns `{"findings":[...]}` with each finding's full `store.Finding` JSON (it already has the tags), in the same order as the HTML table (flat, not nested; the `related` key lets clients group) and honours the same `type` and `status` query filters. Bearer callers on `/api/*` skip CSRF (CC-1001); cookie callers need the token as before.
- **Store.** `internal/store/runlist.go`:

  ```go
  // RunSummary is a close run with its findings count, for the runs list.
  type RunSummary struct { CloseRun; Findings int `json:"findings"` }
  // ListCloseRuns returns the newest runs first (started_at descending,
  // nulls first so queued runs lead, then id), at most limit rows.
  func (s *Store) ListCloseRuns(ctx context.Context, limit int) ([]RunSummary, error)
  ```

  One query with a `LEFT JOIN` (or a lateral count) on `findings`; clamp `limit` to 1..500. This is the only store change, and it is a **declared exception**: the ticket's own Files line doesn't list `internal/store`, but the runs table can't be built without it (no list method exists). It overlaps no in-flight ticket (CC-804 touches only `internal/retrieval`). Mention it in the PR summary.
- **Home page.** Add a "Close runs" link (`/runs`) to `home.templ` for every role. Keep `TestHomeActions` passing; don't change its expectations.
