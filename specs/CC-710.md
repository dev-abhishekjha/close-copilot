# CC-710 · Pseudonymise identifiers before LLM calls

## Goal

No GSTIN, PAN or individual's name leaves the machine in a prompt, while the accountant still sees the real values in stored explanations and proposals.

## Context

- **Ticket:** `docs/implementation-tickets.md`, section `CC-710` (a worker should not need to open it). Plan row (phase 2, LLM, data-sensitive, depends on CC-704): "Scan of stored prompt artifacts finds no GSTIN or PAN pattern; restored explanations match". Guardrail: CC-710 pseudonymises GSTINs, PANs and person names before any model call; G5 scans stored prompt artifacts. Invariant in CLAUDE.md: "GSTINs, PANs and person names are pseudonymised before any model call (CC-710)."
- **Why:** embeddings run on local TEI, so the LLM is the only third party that sees data. A GSTIN contains its holder's PAN, personal data when the supplier is a sole proprietor. Amounts are never touched (the verifier traces them).
- **Ticket design:** identifiers become stable tokens before the call and are restored in the response. Tokens are an HMAC of the run ID and the value (stable across retries and resumes): `GSTIN_3fa9c1`, `PAN_08b2de`, `PERSON_c41e77`. Key: env var `PSEUDONYM_KEY` (32 random bytes, hex), already in `config.Config.PseudonymKey` (a `config.Secret`; read it only with `.Reveal()`).
- **Patterns (from the ticket):**

```go
var (
	gstinRe = regexp.MustCompile(`\b\d{2}[A-Z]{5}\d{4}[A-Z][1-9A-Z]Z[0-9A-Z]\b`)
	panRe   = regexp.MustCompile(`\b[A-Z]{5}\d{4}[A-Z]\b`)   // run after GSTINs are replaced
)
```

- **Person names** come from parties marked `individual: true` in the company profile.
- **Hardening notes for CC-710 (tasks/hardening.md, copied here):**
  - From the CC-502 review: the books tools return raw GSTINs (`supplier_gstin`, `company_gstin`), party and customer names, and GL `party` and `against`. Pseudonymise them before any model call.
  - From the CC-704 post-merge G5: the explainer masks only the user message. ACCOUNTS (trial-balance names from ERPNext, in the system block built by `explainSystem`) must go through the pseudonymiser too. Validate proposal accounts against the masked list, unmask them before storing, and test with an account name the fake masker rewrites.
- **Where the recording sits.** `Workflow.stepModel` (`internal/agent/workflow.go:968`) builds `cappedProvider{NewRecordingProvider(w.Model, ...)}` per step, so the recording is created inside the workflow, not in `cmd/agent`. The ticket's `redact.Wrap(record.Wrap(anthropic))` therefore cannot be built in `cmd/agent` as written. The stored prompt (`RecordingProvider.Complete`, `llmrecord.go:67`) is the `llm.Request` the explainer passes in, so **masking inside the explainer, before it builds the request, is what keeps stored prompts token-only**. That is the path this ticket wires. `WrapRedacting` is built and tested as the decorator the ticket asks for, for callers that don't mask themselves (investigator CC-706, router CC-707), but it is not wired into `Workflow` here (`workflow.go` is outside this spec's files). See Notes.

## Subtasks

- [ ] `internal/agent/redact.go`:
  - `type Redactor` built by `NewRedactor(key []byte, runID uuid.UUID, names []string) *Redactor`. Token = `PREFIX_` + first 6 hex chars of `HMAC-SHA256(key, runID || 0x00 || kind || 0x00 || value)`; on a collision between two different values in one Redactor, lengthen the later one's token (never reuse). Keep a mutex-guarded reverse map for unmasking.
  - Masks, in order: GSTINs (replace first), then PANs (so the PAN inside a GSTIN is gone before the PAN pass), then each individual name (case-insensitive, whole-word, longest first; bank narrations are upper case). Unmask replaces tokens back to the original text from the reverse map; an unknown token-shaped string is left unchanged.

It must keep JSON valid and the top-level keys unchanged (tokens are `[A-Z0-9_]`, so no escaping issue; handle names containing characters JSON escapes by working on decoded strings, not raw bytes, or by proving the byte replacement is safe). Tool specs, `Model`, amounts and counts are untouched. Errors from the inner provider pass through unchanged (including `llm.ErrUnpricedModel` with its Response).

## Notes

- **No new dependencies.** HMAC and SHA-256 come from the standard library (`crypto/hmac`, `crypto/sha256`).
- **Token length.** Six hex chars is 24 bits, so a collision is possible in a large run; the collision rule above makes tokens unique within a Redactor. Because tokens come from the HMAC (not a counter), a resumed run rebuilds the same tokens without stored state.
- **Prompt cache.** Tokens are stable per run, so the cached system block stays identical across a run's findings; do not put per-finding values in it.
- **Hardening (CC-704 G5 and CC-502 review, copied above):** the explainer used to mask only the user message; now ACCOUNTS is masked, validation runs on the masked list, and unmasking happens before storing. The test with an account name the fake masker rewrites is `TestExplainMasksAccounts`.
- **Risk:** this is a data-sensitive ticket. Do not log the key, tokens' source values or names. G5 reviews the scan test, the key handling (fail closed, never printed) and that unmasked values never reach `ArtifactPrompt`.
- **Known gap:** other callers' tool output (investigator, router) is not masked until `WrapRedacting` is wired in their tickets; say so in the PR summary.
- Case of restored names: a name matched case-insensitively is restored in the profile's casing, which can differ from the narration's casing; that is acceptable for display.
